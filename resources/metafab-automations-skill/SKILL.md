# Metafab automations

`.factory/automations/` is this factory's set of automations, and a harness holds a copy of each one's schedule: Orca as an automation, Amp as a schedule. This skill makes that copy match the files. The files decide; the harness is changed only to match them.

`<factory>` is `name` in `.factory/factory.yaml`. `<repo>` is the `owner/name` of the repository's `origin`. `<trunk>` is the branch the person names, or else the remote's default branch (`git symbolic-ref --short refs/remotes/origin/HEAD`, without `origin/`).

## Orca

Run `metafab automations sync orca --dry-run`, show the changes, then run it without `--dry-run`. Pass `--agent` the first time, such as `--agent opencode`, because Orca needs to know which agent runs each automation. Report the output lines.

## Amp

Amp's schedules can be changed only by an agent's tools inside an Amp thread, so Metafab cannot write them. `metafab automations plan amp --branch <trunk> --json` prints the desired set for `AMP_USER_EMAIL`. This section applies that set with Amp's schedule and thread tools. Pass the same `<trunk>` to `plan amp`, so the checkout and the stubs name one trunk.

1. **Read the desired set.** Put the checkout on the trunk first, so a stale branch cannot install an old prompt or clear a live schedule. In a clean checkout (`git status --porcelain --untracked-files=all` prints nothing), run `git fetch origin && git switch --detach origin/<trunk>`. In a checkout with changes, leave it alone: run `git fetch origin && git worktree add --detach <tmp> origin/<trunk>`, run every command below in `<tmp>`, and remove it with `git worktree remove <tmp>` at the end. Then run `metafab automations plan amp --branch <trunk> --json` and read `.entries` from its JSON. If it fails, stop and report its errors, changing nothing. Without `AMP_USER_EMAIL` it prints one line saying so, and that line is the whole report.
2. **Read what is installed.** `list_schedules` returns every schedule and event trigger in the account, across all its projects, in an `automations` array, so a title alone proves nothing. An entry may not carry the schedule's ID: take the ID from the entry when it has one, and otherwise from `get_schedule` on the holding thread, which lists a thread's schedules when it holds several. A thread can hold several schedules, so every schedule tool call in this procedure passes the schedule's `schedule_id` together with its holding `thread`, and never relies on a thread's "only schedule". An installed entry is **managed** (the only kind this procedure updates, clears or archives) when all five hold:
   1. its title starts with `automation: `;
   2. it is a recurring schedule, not an event trigger;
   3. its holding thread belongs to the Amp project for `<repo>`, read from the thread;
   4. its saved prompt, read with `get_schedule` and its `schedule_id`, has as its first line exactly ``Run the factory automation `<name>` from the `<factory>` factory.``, where `<name>` is the name in its title;
   5. its holding thread's title is exactly the schedule's title, and its first message, read with `read_thread` from its current context, is exactly ``This thread holds the `automation: <name>` schedule of the `<factory>` factory for metafab automations sync. Do nothing and end.`` (the **holding marker**). It names the factory, so two factories that share a project and its parent thread never take each other's holding threads, even after a schedule is gone.

   An entry titled `automation: ` that fails any of 2 to 5 is reported as `left alone: <title>` and read no further. A schedule with any other title is a person's own: it is never read further, compared or changed. For each managed schedule, read its prompt, recurrence, label, whether it is paused, and its run mode. When two managed schedules carry the same title (two syncs overlapped), keep the oldest and give up the others: clear each one by its `schedule_id` and retire its holding thread (step 6). They are reported as cleared.
3. **Put the holding threads under one parent.** `create_thread` makes a thread a child of the thread that called it, so without this step every holding thread would sit under whichever run made it.
   1. *Find it.* Search with `find_thread` for `"Factory automations" author:me archived:false repo:<repo>`, and keep the threads titled exactly `Factory automations`. The oldest is the parent. A younger one whose first message is the parent prompt in item 3 (only overlapping syncs make one) is archived once item 4 has moved its children out, and reported as cleared. Any other is a person's own and is left alone.
   2. *Adopt one when there is none.* For each kept managed holding thread, read the thread it was started from (`origin.sourceThreadID` in its `find_thread` entry) and list that thread's children with `find_thread` and `parent:<id>`. A source thread that is the account's own, unarchived, in this project, not itself a holding thread, and whose children include every kept managed holding thread is adopted: retitle it `Factory automations` with `update_thread` and leave it where it is. At most one can qualify. A person who keeps the holding threads under some other thread retitles it `Factory automations` before the sync, and item 1 finds it.
   3. *Create one when there is still none.* Create a thread in the project titled `Factory automations`, whose only message is `This thread holds the factory automation holding threads for metafab automations sync. Do nothing and end.`, then make it top level with `update_thread` and `parent_thread: null`.
   4. *Move the strays.* List the parent's children with `find_thread` and `parent:<parent id>`, and move each kept managed holding thread that is not among them under the parent with `update_thread` and `parent_thread: <parent id>`. A kept holding thread is a managed one that step 2 does not give up and step 6 does not clear. Nothing else moves.
4. **Create the missing ones.** For each entry with no managed schedule, first look for an **empty holding thread** for it: any thread `find_thread` returns for `"automation: <name>" author:me archived:false repo:<repo>`, wherever it sits, that is titled exactly `automation: <name>`, whose first message is the holding marker for that name and this factory, and that holds no schedule (`get_schedule` returns null). A sync interrupted after creating the thread, before or after moving it under the parent, leaves one, and `list_schedules` never shows it. Reuse the oldest such thread and move it under the parent when it is not there already. When there is none, create a thread in the project titled `automation: <name>`, whose only message is the holding marker, written exactly, because the next sync reads it back as proof, and move it under the parent with `update_thread`. Then set its schedule with `set_schedule` on that thread, taking `title`, `prompt`, `schedule`, `schedule_label` and `run_mode` from the entry, and pass the entry's `schedule` as given, `DTSTART;TZID=` line included, because Amp anchors a schedule without a `DTSTART` in the browser's time zone. The thread exists only to hold the schedule, and each firing starts a fresh child thread of its own. Every other empty holding thread with this factory's holding marker, found by `find_thread` for `"automation: " author:me archived:false repo:<repo>`, is retired (step 6): one for a name with no entry, or a younger one for a name whose thread was reused.
5. **Update the ones that differ.** Compare each managed schedule with its entry by title, and update it with `update_schedule`, its `schedule_id` and its holding `thread`, passing only the values that differ: prompt (trailing whitespace trimmed on both sides, because Amp trims what it stores), label, the `TZID` of `DTSTART`, and the whole `RRULE`, which `update_schedule` takes together in its `schedule` field. Never compare the date or time in `DTSTART`: it only says which firing comes first, and it moves on its own as the clock passes (`0 7,20 * * *` planned at 19:59 Sydney gives 20:00, and at 20:01 gives 07:00 the next day, with the same `RRULE`). A schedule that is paused (`enabled: true` resumes it), or whose run mode is not `fresh`, also differs. Anything equal is left alone.
6. **Clear the ones that are gone.** For each managed schedule with no entry (the automation was deleted, is now `enabled: false`, or now names another owner), clear it with `clear_schedule`, its `schedule_id` and its holding `thread`. Then **retire** the holding thread:
   - When it still holds another schedule (`get_schedule` on the thread is not null), leave it unarchived and report `kept: <thread> holds another schedule`.
   - Its children are the runs its schedule started. List them with `find_thread` and `parent:<thread>`, and check each unarchived one with `get_thread_status`. When one is still working, leave the holding thread unarchived this time and report `kept: <thread> has a run in progress`. It is now an empty holding thread, so a later sync finds it in step 4 and retires it then. The sync never stops a run.
   - Otherwise archive each unarchived child, whose work is over because the automation no longer runs from this account, and then archive the holding thread, each with `update_thread` and `archived: true`. Archiving keeps every thread readable. Amp archives a thread after the threads under it: the option to archive a thread that still has unarchived children applies to the current thread alone, so the finished runs go first and the holding thread last.
7. **Report the diff, and nothing else.** One line each for `created`, `updated`, `cleared`, `moved` and `kept` that has anything in it, naming the automations (`moved` names holding threads). One line `parent: adopted <thread>` or `parent: created <thread>` when step 3 did either. One line naming the schedules that were already right, so a person sees the whole set whenever something changed. One `left alone: <title>` line per entry step 2 left alone. And the single line `no changes` when every schedule already matched, every holding thread was already under the parent, and nothing was left alone.

### Rules

- **Only managed schedules are this procedure's to change.** Every other schedule and event trigger in the account belongs to whoever made it, including an `automation: ` one from another project or another factory. It is never updated, cleared, archived or adopted.
- **A schedule belongs to the account that holds it, and every run of it acts as that person.** So a sync installs only the automations its account owns or that are `"*"`, never installs into another account, and never picks an owner. Moving an automation to another owner is a merged change to `owner`: the old owner's next sync clears it and the new owner's installs it. A factory's own sync automation is the exception: once it names someone else, the old owner's firing stops at the owner check before it can clear anything, so the old owner runs the sync by hand once. The same holds when the sync automation itself is turned off.
- **One parent thread per account and project** (step 3). The sync retitles only a thread it adopts as that parent, and moves only managed holding threads.
- **A second run in a row changes nothing.** Every step compares before it writes.
- **The files decide; the account is only read.** Nobody edits the account by hand to add or remove a run.

### Unattended runs

Amp lets a run read, set, update or clear a schedule on another thread only when the current request asks for it, and a firing's saved prompt is the whole of what it is asked. So: when an automation's body asks for this sync, that body is the owner's standing, explicit request to manage the `automation: <name>` schedules on their holding threads, to retire a holding thread whose schedule it clears or that holds none, together with the finished runs under it, to find, adopt or create the `Factory automations` parent, to move holding threads under it and to archive a younger duplicate parent, and nothing else. An automation whose body asks for a sync writes that request into its body, in those words. An unattended run asks nothing and messages nobody beyond what the run instructions say. A hand run carries the same request from the person who asked for it.
