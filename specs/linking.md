# Linking a factory

`metafab link` compiles `.factory/` into the files and directories that agent tools read.

Edit `.factory/`, then run `metafab link`. Do not edit installed copies.

The installed output is committed. A fresh clone therefore contains the same factory for every team member and agent, with no install step.

## Installed output

| Source | Destination | Target |
| --- | --- | --- |
| Each factory skill | `.claude/skills/<name>/` | `claude` |
| Each factory skill | `.agents/skills/<name>/` | `codex`, `opencode`, and compatible tools |
| Each factory skill | `.cursor/skills/<name>/` | `cursor`, pending confirmation |
| Standing instructions, workflows, and pipeline | Generated block in root `AGENTS.md` | All targets |
| Generated factory import | Root `CLAUDE.md` | `claude` |
| Built-in `metafab` skill | Each target's skill directory | All targets unless disabled |

A factory skill is any directory below `.factory/` that contains `SKILL.md`.

Metafab creates one installed entry for each unique destination. For example, `codex` and `opencode` share `.agents/skills/`.

## Target selection

`agents` in [`.factory/metafab.yaml`](configuration.md) stores the default targets:

```yaml
agents: [claude, codex]
```

Target selection follows these rules:

1. `agents: all` selects every target supported by version 1.
2. On the first interactive run, `link` asks for targets when `agents` is absent.
3. On a non-interactive first run, `link` uses `all` when `agents` is absent.
4. `--agents claude,cursor` overrides the configuration for one command.
5. `--save` stores the command-line selection in `metafab.yaml`.
6. The next `link` removes owned output for targets removed from the configuration.

## Compiled skills

Every installed skill is a generated copy. Metafab does not use symlinks, so installation works the same way on every platform and in every agent tool.

For each factory skill, `link` performs these steps:

1. Copy the skill directory, including all supporting files.
2. Remove `uses` and `bundle` from the frontmatter of `SKILL.md`. Keep all other frontmatter unchanged.
3. Add a generated-file comment after the frontmatter.
4. Resolve the skill's dependencies, as defined in [Skill dependencies](factory-format.md#skill-dependencies).
5. Add a reference section for each dependency with `bundle: reference`.
6. Append the body of each dependency with `bundle: inline`.

Agent tools use a flat skill namespace. A nested skill such as `.factory/review/security/` installs as `security`. All skill names must therefore be unique across the factory.

### Dependency order

Metafab orders dependencies so that each one appears after the skills it uses:

1. Visit the skill's `uses` list in the written order.
2. For each dependency, visit its own `uses` list first.
3. Include each skill once, at its first position.

### Example

Source `.factory/workflows/build-slice/SKILL.md`:

```markdown
---
name: build-slice
description: Build one slice of an approved plan on its own branch. Use when a person picks a ready slice.
uses: [git-conventions, our-api]
---

# Build slice

1. Create the slice branch.
...
```

`git-conventions` has `bundle: inline`. `our-api` uses the default, `reference`.

Installed `.claude/skills/build-slice/SKILL.md`:

```markdown
---
name: build-slice
description: Build one slice of an approved plan on its own branch. Use when a person picks a ready slice.
---
<!-- Generated by metafab link from .factory/workflows/build-slice/. Edit the source, then run metafab link. -->

<!-- factory:uses:start -->
Before you start, read these skills in full:

- `.factory/skills/our-api/SKILL.md`: How the API layer is structured and tested.
<!-- factory:uses:end -->

# Build slice

1. Create the slice branch.
...

<!-- factory:inline:start git-conventions -->
## Included skill: git-conventions

(body of .factory/skills/git-conventions/SKILL.md)
<!-- factory:inline:end git-conventions -->
```

### Reference sections

A reference section lists each `reference` dependency with its source path and `description`. It appears at the start of the body, so the agent reads it before the skill's own steps.

The path points to the source file in `.factory/`. That path is the same for every agent tool. The source file still contains `uses` and `bundle`, which agents can ignore.

### Inline sections

An inline section contains the dependency's body without its frontmatter. Inline sections appear at the end of the body, so the skill's own steps come first.

Metafab rewrites relative paths in an inlined body so that they still resolve. It rewrites a Markdown link target or a code span when:

1. The value is a relative path.
2. The path resolves to an existing file in the dependency's directory.

The rewritten path is repository-relative, such as `.factory/skills/git-conventions/check-branch.sh`. Metafab does not change any other text.

### Ownership

Metafab records each installed path and its content hash in `.factory/metafab.lock`. It changes or removes only recorded paths.

If an unowned destination has the same name as a factory skill, `link` stops with exit code 5. It does not replace that destination.

When a skill is removed from `.factory/`, the next `link` removes its installed entries.

`metafab check` fails when an installed copy differs from the output that `link` would write. This includes manual edits and stale copies.

### Review of generated changes

A change to one skill can change many installed copies. For example, an edit to an inlined `git-conventions` changes every skill that uses it.

Review the source change in `.factory/`. The installed copies are derived from it, and `metafab check` confirms that they match.

## Root `AGENTS.md`

`metafab link` manages one block in the root `AGENTS.md`:

```markdown
<!-- factory:start -->
<!-- Generated by metafab link from .factory/. Edit .factory/, then run metafab link. -->

(contents of .factory/AGENTS.md)

## Workflows

Load the workflow that matches the request.

| Workflow | Use when |
| --- | --- |
| `file-work` | A person reports a bug, idea, or feedback |
| `review-slice` | A slice PR is ready for review |
| `fix-flaky-test` | A test fails intermittently |

## Pipeline

Work moves through these workflows in order. When one ends, suggest the next.

1. `file-work`
2. `triage-ideas`. Then stop: the product lead picks the next item.
3. `plan-feature`. Then stop: the tech lead approves the plan as a documentation PR.
4. `build-slice`
5. `review-slice`. Then stop: the code owner approves the PR.
6. `finish-slice`

## Factory source

This repository stores its factory in `.factory/`. Edit that directory and run `metafab link`.
Do not edit installed copies in `.claude/` or `.agents/`.
<!-- factory:end -->
```

Metafab applies these rules to the block:

1. It creates `AGENTS.md` when the file does not exist.
2. It appends the block when the markers do not exist.
3. It replaces only the text between existing markers.
4. It preserves all text outside the markers.
5. It lists every workflow with its `description`, in pipeline order and then in name order.
6. It omits other skills because agent tools discover them through skill directories.
7. It includes the pipeline only when `factory.yaml` defines one.
8. It warns when the generated block exceeds 300 lines.

The marker format is part of the open factory format. Other tools can generate the same block.

## Root `CLAUDE.md`

Claude Code reads `CLAUDE.md`. The `claude` target makes it import the root `AGENTS.md`.

`link` handles the file as follows:

1. If `CLAUDE.md` does not exist, create it with `@AGENTS.md`.
2. If it already imports `AGENTS.md`, leave it unchanged.
3. Otherwise, add `@AGENTS.md` in a marked factory block at the start of the file.

## Built-in `metafab` skill

`link` installs a built-in `metafab` skill for each target. The CLI supplies this skill. It does not come from `.factory/`.

The skill tells an agent how to:

- Find and edit factory source files
- Create workflows and skills, and connect them with `uses`
- Add workflows to the pipeline
- Run `metafab link` after an edit
- Run `metafab check` and resolve each reported problem
- Keep factory changes in a reviewable commit or PR
- Review upstream changes from `metafab update`
- Design a factory by asking how work moves today, where people decide, and what goes wrong

The design guidance recommends a pipeline of four to eight workflows to start.

The basic rule, "edit `.factory/`, then run `metafab link`", is also in the `AGENTS.md` block. Agents therefore know it without loading this skill.

Disable this skill in `metafab.yaml`:

```yaml
metafab-skill: false
```

The next `link` removes the installed copies.

`metafab check` detects an outdated built-in skill. `metafab link` replaces it with the current CLI version.

## Repeatability

`metafab link` writes, updates, or removes only out-of-date owned output. It reports every changed path.

A second run with unchanged inputs makes no changes.

`metafab check` fails when `link` would change a file. Teams can run it in CI or a pre-commit hook:

```sh
npx @seasb/metafab check
```
