# meta-harness

This repository builds **Metafab**: the `metafab` CLI, published as `@seasb/metafab`. It records a software factory in `.factory/`, installs it for agent tools, validates it, and shares it as a fab.

## Read first

- `docs/specs/`: what v1 does. The specs are the acceptance standard for every change.
- `docs/roadmap.md`: where we are. One checkbox per plan; it is the source of truth for progress.
- `docs/plans/`: how each piece is built. One plan is one pull request.
- `docs/factory.md`: this repository's factory settings. The workflows and scripts read it.
- `prototype/`, and `assets/` are earlier prototypes and material. Do not read or change them unless the person asks.

## Commands

```bash
npm install
npm run verify          # typecheck, tests, build, factory: run before every push
npm run factory         # metafab build and check, then the docs check; fails when the AGENTS.md block is stale
node dist/cli.js <cmd>  # the CLI from this checkout
node .factory/scripts/check.mjs   # validates plans, roadmap, intake and changelog
node .factory/scripts/next.mjs    # plans that can be built next
```

In this repository `metafab` is `node dist/cli.js`: run `npm run build` first.

## Rules

- **Specs first.** When the code has to differ from a spec, change the spec in the same pull request and say so in its body. Never let them drift.
- **One plan, one pull request.** Change only the paths in the plan's `owns`; widen `owns` in the plan when you must, and say why.
- Conventional Commits with no scope: `feat`, `fix`, `refactor`, `docs`, `chore`, `test`, `ci`, `build`. Branches are `<type>/<slug>`. A plan's branch carries its number: `<type>/<plan file name without .md>`, such as `feat/1.005-check`.
- Code reaches `main` only through a pull request; see "Publishing docs changes" for what counts as docs.
- Coding sub-agents run as `subagent_type: "agent-coding"` and review sub-agents as `subagent_type: "agent-review"`, both defined in `opencode.json`, even when the Agent tool does not list them. In Amp, each sub-agent is a separate thread on the same models; `build-plan` says how.
- Run child processes with `execFile` and an argument list, never through a shell.
- Tests use temporary directories and local fixtures (a local registry, local bare Git repositories). No test reaches the network.

## Publishing docs changes

Docs are `docs/`. They still go straight to `main`, and so does a `metafab update` that leaves `.factory/scripts/` alone. When the person asks you to save, publish, commit or push docs changes, do the round trip yourself:

```bash
git switch main && git pull --ff-only
npm run build && node dist/cli.js build                         # regenerates the root blocks from .factory/
git add docs/<files> AGENTS.md                                  # stage the regenerated root block too
git diff --cached --name-only | grep -vE '^(docs/|AGENTS\.md$)'   # must print nothing
node dist/cli.js diff                                           # must print "No local edits since ..."
node .factory/scripts/check.mjs                                 # fix what it reports
npm run factory                                                 # builds and checks; passes once the regenerated root block is staged
git commit -m "docs: <what changed>"
git push
```

A docs-only commit runs `node .factory/scripts/check.mjs`. A `metafab update` also runs `npm run factory`, because the `AGENTS.md` block is committed and an update that changes it regenerates root `AGENTS.md`, which is staged with the update.

If anything outside `docs/`, `.factory/` (outside `.factory/scripts/`) and the `AGENTS.md` block the build regenerates is staged, it goes in a pull request instead. A change to `.factory/metafab.yaml` (for example `agents`) can regenerate `.gitignore`; that is not docs, so that change goes in a pull request.

### The factory is upstream-owned

`.factory/` arrives from [fab-basic](https://github.com/Traction-Team/fab-basic), whose `.factory/` is its source. Its workflows, skills, templates, scripts, `AGENTS.md` and `factory.yaml` are maintained there, and this repository's own values live in `docs/factory.md`, which an update never touches.

- **A factory change** — a workflow, a skill, a template, `.factory/AGENTS.md` or `factory.yaml` — is made in fab-basic (`github:Traction-Team/fab-basic`), released there as a new version, and taken here with `node dist/cli.js update`. Commit that update in a pull request when it touches `.factory/scripts/`, and straight to `main` otherwise.
- **A direct edit to `.factory/` outside `.factory/scripts/`** is a docs-only stopgap at most: `node dist/cli.js diff` lists it until it is upstreamed to fab-basic. Make one only to unblock the person, and say in the commit that it waits on an upstream change.
- **`.factory/scripts/` is never edited locally.** It is code, so it goes in a pull request in fab-basic.

Read `docs/factory.md` first. It holds this repository's settings. Every workflow and script reads it, and a branch, command or path written as a setting name means that setting's value: `trunk`, `verify`, `specs`, `plans`, `roadmap`.

The whole process is in [.factory/docs/process.md](.factory/docs/process.md): the words, the pipeline, claims, landing, stacking, features and releases.

## Rules

- **One plan, one pull request.** Change only the paths in the plan's `owns`. Widen `owns` in the plan when you must, and say why in the pull request.
- **A pull request that claims a plan changes only through `build-plan`.** Its first body line is `**Plan:** <plans>/<plan>.md`. Feedback, fixes, review comments, restacks and "done" all go through `build-plan`'s after-the-draft steps, in this session or any other, because every push refreshes the landing commit.
- **Specs first.** When `specs` names a directory, the specs in it are the acceptance standard for every change. When the code has to differ from a spec, change the spec in the same pull request and say so in its body. Never let them drift. When `specs` is empty, the spec steps in the workflows are skipped.
- **Conventional Commits, with no scope:** `feat`, `fix`, `refactor`, `docs`, `chore`, `test`, `ci`, `build`. A branch is `<type>/<slug>`. A plan's branch carries the plan file's stem: `feat/1.005-check` for `<plans>/1.005-check.md`, `feat/2026-11-02-onb-2-second` for a dated plan.
- **Code reaches `trunk` only through a pull request.** The `trunk` setting names that branch.
- **`.factory/scripts/` is code.** A change to it goes in a pull request, never straight to `trunk`.
- **Sub-agents.** Start task and fix sub-agents as `subagent_type: "<sub-agent-coding>"`, reviews as `subagent_type: "<sub-agent-review>"`, planning as `subagent_type: "<sub-agent-planning>"`. The values come from `docs/factory.md`; `opencode.json` defines them. The opencode-claude-bridge plugin replaces the Agent tool's list with Claude Code's built-ins (`general-purpose`, `Explore`, `Plan`), so those names may not appear: call them anyway, they run. Fall back to `general-purpose` only when the call fails with an unknown-agent error, and say so in one line. In Amp, each sub-agent is a separate thread; the workflows say how. How each harness starts a session or a sub-agent is in the `agent-harnesses` skill.

## Factory workflows

Delivery work runs through these workflows. Each is installed as a skill. When a request matches a row, load that workflow and follow it; do not do the work freehand. If two rows match, say which you chose and why in one line. If none matches, answer directly.

| Workflow | When to run it |
|---|---|
| `file-work` | A bug, idea, feedback, follow-up, spec gap, or any "we should...". Also every tooling problem and existing bug a build found, before its pull request merges |
| `prioritise-roadmap` | "What's next", re-ordering the roadmap, reviewing intake or open questions |
| `plan-feature` | "Plan <thing>", a roadmap line with no plan, or a bug too big for a bug plan |
| `review-plan` | After writing plans, always in a new sub-agent. "Cold review this plan", "poke holes in this plan" |
| `start-plan` | On `trunk`: "start the next plan", "pull the next chunk", "keep going", "what's ready". The orchestrator: one worker per plan, as a new Amp thread in its own orb, or an Orca worktree and OpenCode worker |
| `build-plan` | On a feature branch, usually as a worker in its own Amp thread or Orca worktree: "build docs/plans/<plan>.md". Stops at a merge-safe draft pull request and a TL;DR |
| `review-branch` | After any implementation, always in a new sub-agent. "Cold review this branch" |
| `finish-plan` | On a plan's branch, after the TL;DR: testing feedback, "looks good", review comments, "land it" |
| `release` | Only when the `release` setting is `on`: "release", "deploy", "ship a hotfix". Standalone, so the pipeline never suggests it; it stops at once when `release` is `off` |

## Publishing docs changes

Docs are `docs/`, and `.factory/` outside `scripts/`. How they reach `trunk` is the `docs-changes` setting.

**When root `AGENTS.md` has its own "Publishing docs changes" section, follow that section instead.** It knows this repository's checks and its own rule for what counts as docs. The rest of this section is the generic round trip.

- **`direct`** commits docs to `trunk` and pushes them:

  ```bash
  git switch <trunk> && git pull --ff-only
  git add docs/<files> .factory/<files> AGENTS.md   # `AGENTS.md` when a build regenerates its block
  git diff --cached --name-only | grep -vE '^(docs/|\.factory/|AGENTS\.md$)'   # must print nothing
  git diff --cached --name-only | grep '^\.factory/scripts/'                   # must print nothing: scripts are code
  node .factory/scripts/check.mjs                   # fix what it reports
  git commit -m "docs: <what changed>"
  git push
  ```

  When `metafab build` regenerates the block in root `AGENTS.md`, stage it with the `.factory/` file that changed it. Run `node .factory/scripts/check.mjs` before every docs commit.

- **`pull-request`** opens a docs pull request. Branch as `docs/<slug>`, commit as above, push, and open it with `gh pr create --base <trunk> --title "docs: <what changed>" --body-file <body>`. Send the person the link and a few plain lines on what it changes. **Merge it only when they have seen it and said to.** If they ask for changes, push to the same branch and ask again.

A change to `.factory/scripts/` is code and goes in a pull request either way. Files outside `docs/`, `.factory/` and the root `AGENTS.md` block belong to a code change: never mix them into a docs change.

## Pipeline

Work moves through these workflows in order. When one ends, suggest the next.

1. `file-work`
2. `prioritise-roadmap`. Then stop: The person running it agrees what is next on the roadmap.
3. `plan-feature`. Then stop: A person approves the plans.
4. `start-plan`. Then stop: A person confirms each wave.
5. `build-plan`
6. `finish-plan`. Then stop: The developer says done and a person merges the pull request.
