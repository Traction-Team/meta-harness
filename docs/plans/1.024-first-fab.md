# Plan 1.024: Publish the first fab and import it into this repository

Metafab needs one real fab before 1.0.0: something a team can import on day one, and proof that `import`, `update` and `diff` work on a factory people use every day. This plan builds that fab from two working factories, Dragonfly's (stacked pull requests, the remote review-bot loop, mark ready and watch CI, the release workflow, intake sightings, feature docs) and this repository's (`review-plan`, `finish-plan`, the main-green gate, merged-worktree cleanup), in Metafab format, with every repository-specific value moved into a settings file the importing repository owns. It is published from a new repository, `github:Traction-Team/fab-basic`, as `@seasb/fab-basic`. It carries this repository's Orca and OpenCode flow and, from PR #25, its Amp flow, as hand-written variants side by side. Then this repository replaces its hand-kept `.factory/` by importing the fab, so from here on our own factory arrives through `metafab update`. Dragonfly moves to the fab after 1.0 as separate work.

It also fixes the `next.mjs` unplanned-title bug, in the fab's `lib.mjs`, so the fix reaches this repository through the import.

The plan is in two parts. **Part A** is a separate repository (`github:Traction-Team/fab-basic`): its own commits, tests and CI, no pull request here. **Part B** is this repository's pull request, which imports Part A's tagged release and proves it here.

`factory.yaml`:

```yaml
format: 1
name: basic
description: Plan, build and review work one pull request at a time, with a person at each decision.

pipeline:
  - file-work
  - prioritise-roadmap: { stop: The person running it agrees what is next on the roadmap }
  - plan-feature: { stop: A person approves the plans }
  - start-plan: { stop: A person confirms each wave }
  - build-plan
  - finish-plan: { stop: The developer says done and a person merges the pull request }

requires:
  - path: docs/factory.md
    description: This repository's settings (trunk, verify command, Orca repo, docs paths) that the workflows and scripts read; set every <set me> value
```

**Settings reader (`lib.mjs`).** `readSettings(source)` reads `docs/factory.md` through the same `fileSource` (so `--ref origin/<trunk>` reads merged settings), finds the first table whose header row is `| Setting | Value |` (more columns allowed), splits each row on unescaped `|` only and turns `\|` into `|` (GitHub table rules, so a command such as `npm test \| tee results.log` survives), trims each cell, strips one pair of backticks, and returns an object with the defaults below for absent keys. CRLF and a BOM are accepted. A missing file returns the defaults and `check.mjs` reports `docs/factory.md is missing: copy .factory/templates/setup/factory.md there and set its values`. Unknown keys are warnings (`did you mean`), `<set me>` values are errors naming the key, and a key set twice is an error naming both lines (the reader keeps the first). The paths the scripts use (`PLANS_DIR`, `ROADMAP_FILE`, `INTAKE_DIR`, `CHANGELOG_DIR`, `FEATURES_DIR`, `TRUNK`) come from it instead of constants.
