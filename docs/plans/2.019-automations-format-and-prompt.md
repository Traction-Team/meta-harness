# Plan 2.019: A factory declares automations and metafab renders each run's prompt

A team wants some factory work to run on its own, such as a twice-weekly intake triage or a daily sync. The Dragonfly factory does this with `.factory/automations/<name>/automation.md` and a 762-line script. This plan brings the format into Metafab, made smaller and harness-neutral, as [Automations](../specs/automations.md) says. `metafab check` validates automations. `metafab automations list` shows them. `metafab automations prompt <name>` renders one run's instructions for the developer's environment, with `.factory/automations/run.md` and the body's `switch env.harness` blocks applied. `metafab automations stub <name> --target <t>` prints the short text a harness registers. Plan 2.020 registers the stubs in Orca and Amp.

## Specs

- [Automations](../specs/automations.md): Layout, `automation.md`, Run instructions, Directives, The prompt, The stub, the `list`, `prompt` and `stub` rows of Commands, Validation
- [Environments: Selecting an environment](../specs/environments.md#selecting-an-environment), [Rendering](../specs/environments.md#rendering), [Import](../specs/environments.md#import): reused for `run.md` and bodies
- [Building: Git hooks](../specs/building.md#git-hooks): the invocation order the stub reuses

### Spec edits this plan makes

**`factory-format.md`, Directory layout.** Add `automations/<name>/automation.md  format 2: work that runs on its own (see automations.md)`.

**`factory-format.md`, Reserved names.** Add `automations/` to the defined names with "(format 2; see [Automations](automations.md)). In a format 1 factory it is an ordinary directory, and skills in it install as before." Rule 11 is unchanged, because the automations spec forbids a `SKILL.md` anywhere below `automations/` in format 2, which is stricter.

**`environments.md`, Where directives apply.** Add the row `| .factory/automations/run.md and the body of every automation.md | All, rendered by metafab automations prompt for the selection |`.

**`cli.md`, Commands.** Add a "Run work on its own" table with the `list`, `prompt` and `stub` rows from [Automations: Commands](../specs/automations.md#commands), and a link to the spec. Plan 2.020 adds `plan` and `sync`.

**`README.md`.** Move the Automations row from its draft section into the Specifications table, and delete the draft section. This plan changes no other spec.

## Decisions

Agreed with the person on 2026-11-26:

| Topic | Choice | Reason |
| --- | --- | --- |
| What Metafab takes from Dragonfly | The file-per-automation layout, `owner`, `enabled`, cron with `tz`, `after` chains with loop and owner checks, the run guards (dirty checkout, trunk, off, not yours) and the Amp procedure (Plan 2.020). It leaves out `workflows`, `inputs`, `gates`, `notify`, `concurrency`, the `## Unattended run` rule and `## Who to ask` | Those are one factory's conventions. Here the body says them in prose, and `run.md` says how a harness asks and notifies |
| Registered text | A stub that renders the prompt when the run starts, not a full copy | A body edit then takes effect without a sync, and a registration cannot go stale |
| Harness text | `.factory/automations/run.md` and the bodies use env directives; Metafab's own prompt text names no harness | The environments feature already keeps per-harness text side by side and checked |
| Where a run happens | `checkout: worktree` (default) or `main` per automation | The person asked for it to be configurable in the automation |
| Format | Format 2 only; `automations/` is a reserved directory | It needs directives, and format 1 has no meaning for them |

**Dragonfly's source.** The design ports parts of `.factory/scripts/automations.mjs` in `dragonfly-au/dragonfly` at commit `681fb13df546bbf767b980efc651c771be1543e8`. That repository is private, so this plan states every behaviour it takes from it. A builder needs only this plan and the specs, and the tests below are the standard, not the Dragonfly code.

## Design

### Model (`src/core/automations/types.ts`, `load.ts`)

```ts
export type Trigger =
  | { kind: "schedule"; cron: string; tz: string; line: number }
  | { kind: "after"; names: string[]; line: number };

export interface Automation {
  name: string;
  file: string;              // ".factory/automations/<name>/automation.md", always with "/"
  owner: string;             // "*" or an email, trimmed
  description?: string;
  enabled: boolean;
  checkout: "worktree" | "main";
  triggers: Trigger[];
  body: string;              // raw, LF, below the frontmatter
  bodyLine: number;          // first body line, for directive problems
}

export interface Automations { list: Automation[]; runFile?: string; problems: Problem[] }

export async function loadAutomations(factoryDir: string, factory: Factory): Promise<Automations>;
```

`loadAutomations` reads `.factory/automations/` with the walker 1.015 shares (`DT_UNKNOWN` handled). It applies the layout rules, then parses each `automation.md` with `src/util/frontmatter.ts` and `src/util/yaml.ts`, the same reader skill frontmatter uses. So BOM, CRLF, duplicate keys and alias limits behave as they do for skills. Text is converted to LF with `toLF` before anything is rendered.

**Format 1 stays as it is.** `RESERVED_CONTAINERS` does not change. `validate.ts` gains `FORMAT_2_RESERVED = ["automations"]`. `discovery.ts` skips the `automations/` subtree only when `factory.yaml` says `format: 2`, so a format 1 factory's skills under `automations/` are still discovered and installed. In format 2, `create.ts` refuses a path that starts with `automations/`, using `FORMAT_2_RESERVED` and the factory's format, with `automations/ holds automations, not skills` and the fix `Create .factory/automations/<name>/automation.md by hand`. In format 1 it creates the skill as before.

`Factory` gains `automations?: Automations`. `loadFactory` calls `loadAutomations` only for `format: 2`. For format 1 with a non-empty `.factory/automations/`, it adds one warning on the directory: `.factory/automations/ needs format: 2`, with the fix `Set format: 2 in .factory/factory.yaml`.

### Validation (`src/core/automations/validate.ts`, `cron.ts`)

Every rule in the spec's Frontmatter and Layout sections is one problem with file, line and fix:

- Layout: a file other than `run.md` directly in `automations/`, a directory with no `automation.md`, a bad directory name, and a `SKILL.md` anywhere below `automations/`. The name check uses `SKILL_NAME_PATTERN` and `MAX_SKILL_NAME_LENGTH` from `validate.ts`, exported for it, with the `slugify` fix that `rule5NameFormat` uses. It does not call `rule5NameFormat`, which takes a `Skill`, and it does not apply rule 10's `metafab` prefix, which the automations spec does not reserve. Discovery skips the subtree in format 2, so the `SKILL.md` is reported here and never installed.
- Keys: unknown key, missing `owner` or `triggers`, `owner` that is not `"*"` or one email, `enabled` that is not a boolean, `checkout` that is not `worktree` or `main`, and `description` that is not a single-line string.
- Triggers: not a non-empty list; an entry with zero or two keys; a second `schedule`; equal triggers (compared after sorting `after` names and joining cron fields with single spaces); `after` naming an unknown automation or itself; an owner mismatch along an `after` edge. A child must be `"*"` or have its parent's owner compared without letter case, so a personal child after a `"*"` parent is an error. The message is `owner: <owner> cannot run after "<parent>", owned by <parent owner>: a chained run starts in its parent's account`, with the fix `Set owner to "*" or to <parent owner>`. A disabled parent still counts as a named target.
- Emails anywhere other than `owner`: the pattern `/[^\s@"]+@[^\s@"]+\.[^\s@"]+/`, tested against every other frontmatter string value, including strings nested in `triggers`. `@handle` and platform-ID checks are not added, because the spec restricts only emails.
- `cronProblem(cron)` in `cron.ts` reads the spec's grammar. The cron is trimmed and split on runs of whitespace. Anything but five fields is `the cron "<cron>" is not five fields`. Otherwise each field, with its range from `CRON_FIELDS` (`minute` 0–59, `hour` 0–23, `day of month` 1–31, `month` 1–12, `day of week` 0–7), is split on `,`, and the first bad part gives `the cron "<cron>" has a bad <field> part "<part>": <reason>`. The reasons, checked in this order: `more than one /step`; `the step is not a positive integer`; `it is not *, a number or a range` (this covers an empty part); `<n> is outside <min>-<max>`; `the range starts after it ends`. `validTimeZone(tz)` is true when `new Intl.DateTimeFormat("en-US", { timeZone: tz })` does not throw; otherwise the problem is `"<tz>" is not an IANA time zone`.
- Loops: the `after` graph has an edge from each named parent to the automation that runs after it. `findCycles` walks it depth-first from each automation in name order, and records the first path that returns to the start. Each member of a loop gets the error `cycle: a → b → a`, written from that member, on its `triggers` line.
- Empty body: `check` asks `rendersContent(document, { variables, selection: allValues(env) })` (see Rendering content below). When it is false, it is an error on the first body line: `The body of <name> is empty`. Rendering alone is not enough, because `renderDocument` adds a `**<label>:**` line before a block that applies to only some values, even when the block holds only blank lines. `check` does not try every selection. A selection that empties the body is caught by `prompt` at run time (spec, The prompt rule 2), because the combinations of every variable a body names are not bounded the way one block's are.

### Rendering content (`src/core/env/render.ts`)

```ts
export function rendersContent(document: MarkdownDocument, context: RenderContext): boolean;
```

It walks the nodes as `renderNodes` does, with the same `classify` calls, and returns true at the first text line that is not whitespace inside a block that applies. Label lines are never content, and nor are blank lines. `renderDocument` does not change. `prompt` uses the same function with the run's selection for its `has nothing to do in this environment` failure, so `check` and `prompt` agree on what empty means.

### Directives (`src/core/env/validate.ts`)

`environmentProblems` also walks `run.md` and each `automation.md` body (from `bodyLine`), with the rules it applies to skill Markdown: known directives, closed blocks, conditions, switches, imports, and no directives in frontmatter. `run.md` is resolved as a partial through `resolveImport`'s containment rules, so a link out of `.factory/` is the same error as for an import.

### Prompt (`src/core/automations/prompt.ts`)

```ts
export async function renderPrompt(factory: Factory, automation: Automation, selection: EnvSelection, after: string[]): Promise<string>;
export function afterOf(name: string, list: readonly Automation[]): string[];   // enabled automations whose after names it, sorted
```

The text is exactly the spec's [The prompt](../specs/automations.md#the-prompt). `run.md` is rendered like an import: frontmatter removed, then directives applied, using 2.013's import cache. The body is rendered with `renderDocument` for the selection. Label lines appear where the selection has more than one value, as in skills. The prompt ends with one `\n`.

`account(target)` in `src/core/automations/account.ts`: for `amp`, `process.env.AMP_USER_EMAIL` trimmed. For `orca`, `git config --get user.email` run with `runGit` in the factory's repository. An empty or missing result is `undefined`.

### Stub (`src/core/automations/stub.ts`)

```ts
export function renderStub(input: { factoryName: string; automation: Automation; target: Target; trunk: string; factoryRelDir: string; cliVersion: string }): string;
export async function defaultTrunk(repoRoot: string): Promise<string | undefined>;   // git symbolic-ref --short refs/remotes/origin/HEAD, without "origin/"
```

The text is exactly the spec's [The stub](../specs/automations.md#the-stub). For `--target amp` the stub always has the clean-checkout and detach steps. For `--target orca` they are left out only when `checkout` is `main`.

Plan 1.028 adds the private `cliLookup(factoryRelDir, cliVersion, args)` in `src/core/hooks/script.ts`, with its fourth tier (the main worktree's `node_modules/.bin/metafab`). That tier writes the factory directory inside double quotes (`"$main/<dir>/node_modules/.bin/metafab"`), which is not safe for a directory holding `"`, `$`, `` ` `` or `\`. This plan does not change the hooks: `sync.ts` reads the directory back out of an installed hook (`hookFactoryDir`) to upgrade or remove it, so any change to the hook text is a change to that parser too, which belongs to another plan. Instead, the lookup's main-worktree path becomes a parameter:

```ts
export function metafabInvocation(mainCli: string, cliVersion: string, args: string): string[];   // the four lookup lines; mainCli is shell text
```

`cliLookup(factoryRelDir, cliVersion, args)` stays private and calls it with `"$main/${factoryRelDir}/node_modules/.bin/metafab"`, exactly the text it writes today, so `hookScript` and `hookCommand` print the same bytes and 1.028's snapshots do not change. The stub calls it with `"$main"/<q>/node_modules/.bin/metafab`, where `<q>` is `shQuote(factoryRelDir)`, outside the double quotes. The stub's step 3 command is:

```sh
(cd "$(git rev-parse --show-toplevel)"/<q> && <the four lookup lines joined with "; ">; fi)
```

and the lookup runs `automations prompt <name> --target <target>`. At the repository root `factoryRelDir` is `.`, as in the hooks, which quotes to `'.'` and needs no special case. The command has no trailing `|| true`. `hookCommand` ends in `|| true` because a hook must never fail a checkout, but the stub needs the opposite: when `prompt` exits 1, the subshell exits 1 and the agent sees the failure and its stderr, as step 3 of the stub tells it to.

**Quoting.** Names and factory names are limited to `[a-z0-9-]`. The trunk and `factoryRelDir` are not, so both go through `shQuote(value)`, which wraps the value in `'…'` and writes each `'` as `'\''`, and both stand outside any double quotes: `"$(git rev-parse --show-toplevel)"/'my "fab" $x'` and `origin/'feat/a'\''b$c'`.

`--branch` is first checked with `git check-ref-format --branch <value>` through `runGit`, and a refusal exits 1 with `<value> is not a branch name`.

### Commands (`src/commands/automations-*.ts`, `src/cli.ts`, `src/help.ts`)

`automations` is a command group like `pipeline`: `metafab automations --help` lists `list`, `prompt` and `stub`, and Plan 2.020 adds the rest. Each command loads the factory with `loadFactory`. It exits 1 for format 1 (`Set format: 2`), and every command accepts `--json`.

- `list`: one block per automation in name order. Its first line is `<name>  (enabled)` or `<name>  (disabled)`, followed by an indented `  description: <text>` when there is one. Then one `  trigger:  schedule <cron> <tz>` or `  trigger:  after <a>, <b>` line per trigger, then `  checkout: <value>`, `  owner:    <value>` and `  after:    <names>` (or `none`). Labels are padded to the same width, and blocks are separated by one blank line. Prints `No automations.` when there are none. `--json` adds `automations: [{ name, file, owner, description, enabled, checkout, triggers, after }]`. It exits 1 with the problems when any automation has an error.
- `prompt <name> [--target] [--env]`: selection through `resolveSelection` with `--env`, as `build` does. Its failures are the spec's rule 2 and rule 3 messages, on stderr with exit 1 and nothing on stdout. It writes the prompt to stdout as is, not as a summary. **Which errors stop it:** `promptProblems(name, factory)` keeps the problems whose `file` is in the prompt's dependency set, plus any `cycle:` problem whose loop contains the name. All other problems are ignored, so one broken automation never stops another's run. The dependency set holds the automation's `automation.md`, `run.md`, the `automation.md` of each name on its `after` line, and, for every import reached while rendering the body or `run.md` (nested imports included), **every** name that file is known by on the walk: the lexical route name (the importing file's directory joined with the import's `path`, normalised to `.factory/<path>` with `/`, through any symlink), the name on the import node (`node.file`), and the realpath name the import cache records (`LoadedImport.file`). A problem in an imported file is reported under whichever name the validator saw it by, and they differ when a symlink is on the route. Keeping every name means a symlinked partial cannot hide an error from `prompt`. Comparison is on the repository-relative POSIX names that problems already carry.
- `stub <name> --target <orca|amp> [--branch]`: `--target` is required and is missing input (exit 2) without a terminal. A disabled automation still gets a stub, because the run itself reports that it is off. An unknown target exits 1 and lists the targets.

### Failure, repeat runs and Windows

- Every command is read-only, so a failure leaves the repository unchanged and a second run prints the same bytes.
- Problem `file` values use `/` on Windows (1.026). The stub is POSIX `sh` text. On Windows it is printed the same, and running it is the target's business (Orca and Amp run it on macOS or Linux).
- An `automations/` directory that cannot be read is one `Cannot read` error with exit 1, as for skills.
