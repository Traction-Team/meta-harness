# Plan 2.020: Metafab automations sync registers a factory's automations in Orca and Amp

After Plan 2.019 a factory declares automations and Metafab can print each one's stub, but nothing registers them in a harness. This plan registers them in two harnesses. `metafab automations sync orca` makes this machine's Orca automations match the files, through the `orca` CLI. Amp's schedules can be changed only by an agent's tools inside an Amp thread, so `metafab automations plan amp --json` prints the desired set. A new built-in skill, `metafab-automations`, holds Dragonfly's proven `sync-automations` procedure, generalised, so an Amp agent can apply that set. Both paths share one desired set and one definition of a managed registration, so a person can register the same automations in either harness or both.

- [Building: Built-in `metafab` skill](../specs/building.md#built-in-metafab-skill)

## Decisions

Agreed with the person on 2026-11-26:

| Topic | Choice | Reason |
| --- | --- | --- |
| Orca | Metafab runs the `orca` CLI with `execFile` and an argument list | Orca has a full `automations list/create/edit/remove --json` CLI |
| Amp | Metafab prints the desired set, and an agent applies it with Amp's tools by following a built-in skill | Amp has no schedule CLI; `set_schedule` and the thread tools exist only inside a thread |
| Where the Amp procedure lives | A built-in `metafab-automations` skill shipped with the CLI, not a fab workflow | It is tied to Metafab's output format and its marker, and every factory with automations needs it |
| Daily sync | Not built in. A factory adds its own `sync-automations` automation whose body runs the sync (fab-basic follow-up) | Dragonfly does it this way, and Metafab never schedules anything itself |

Proposed in this plan, for approval:

| Topic | Choice | Reason |
| --- | --- | --- |
| A disabled automation in Orca | `edit --disabled`, keeping run history; removed only when deleted or re-owned | Orca's `remove` deletes run history, which a person may still want |
| Orca agent | `--agent`, or the agent all managed registrations already share; otherwise exit 2 | The agent is a personal choice, and the CLI never guesses missing input |
| Skill installed only when needed | `metafab-automations` is installed only when the factory has at least one automation | A factory without automations does not need the text |

## Design

### Desired set (`src/core/automations/desired.ts`)

```ts
export type Target = "orca" | "amp";
export interface DesiredEntry { name: string; title: string; cron: string; tz: string; checkout: "worktree" | "main"; stub: string }
export async function desiredSet(factory: Factory, target: Target, account: string, trunk: string): Promise<DesiredEntry[]>;
export function isManaged(entry: { title: string; prompt: string }, factoryName: string): string | undefined;   // the automation name, or undefined
```

`desiredSet` takes the enabled automations that have a `schedule` trigger and an `owner` of `"*"` or `account` (compared without letter case), in name order. Their stubs come from `renderStub`. Any automation error stops it with the problems and exit 1, before the target is touched. `isManaged` checks that the title is `automation: <name>` and that the prompt's first line is the marker for that name and `factoryName`.

### Orca (`src/core/automations/orca.ts`)

```ts
export interface OrcaRunner { (args: string[]): Promise<{ exitCode: number; stdout: string; stderr: string }> }
export function createOrcaRunner(): OrcaRunner;   // execFile("orca", [...args, "--environment", "local", "--json"]), windowsHide, no shell
export async function planOrcaSync(input: { desired: DesiredEntry[]; installed: OrcaAutomation[]; repoRoot: string; factory: Factory; agent?: string }): Promise<OrcaChange[] | NeedsInput>;
export async function applyOrcaSync(changes: OrcaChange[], run: OrcaRunner): Promise<OrcaSyncResult>;
```

0. **Local only.** Every call passes `--environment local`, so `ORCA_ENVIRONMENT` or `ORCA_PAIRING_CODE` in the caller's environment cannot send the sync to a paired remote Orca. The spec's account and main checkout are this machine's. The runner also removes `ORCA_PAIRING_CODE` from the child's environment. If the first step finds that `local` does not pin it as documented, the runner removes both variables instead.
1. **First step of the build:** confirm the CLI's current shape with `orca automations create --help` and `orca agent-context --json`. Check the `--workspace` selector for the main checkout (expected `path:<root>`), the field that holds the run context path (seen as `runContext.path`), and whether `rrule` holds the cron as given (seen as `"0 9 * * 1,4"`). Write down anything different in `automations.md` in this pull request.
2. **Read:** `orca automations list --json`, then `result.automations`. The **main checkout** is the first `worktree ` line of `git -c core.quotePath=false worktree list --porcelain`, as Plan 1.028 decided, as a real path. The parent of `--git-common-dir` is wrong for `--separate-git-dir` and for submodules. So a sync run from a linked worktree still names the main checkout, and the factory directory inside it is the same relative path. When that line is missing, or names a bare repository or a directory that does not hold `.factory/` at that relative path (a bare repository, a submodule's linked worktree), sync exits 1 with `This repository has no main checkout for Orca to run in` and the fix `Run the sync from a normal clone`, changing nothing. Installed entries that belong to this repository have a `runContext.path` equal to the main checkout (case-insensitive on Windows and macOS, as `isInside` compares). Each such entry that passes `isManaged` is managed. Any other entry titled `automation: ` is reported in `leftAlone`.
3. **Plan:** keep the oldest managed entry of each title (`createdAt`) and remove the rest. For each desired entry:
   - With no managed entry, `create`: `--name <title> --trigger <cron> --timezone <tz> --prompt <stub> --provider <agent> --enabled --fresh-session`. For `worktree`, add `--repo path:<root> --base-branch origin/<trunk> --setup run`. For `main`, add `--workspace path:<main checkout>`. Here `<root>` is also the main checkout.
   - When the managed entry differs in prompt (trailing whitespace trimmed), cron (fields joined by one space), `timezone`, `agentId`, `enabled`, workspace mode, base branch, the workspace for `main` (the path part of `workspaceId`, after `::`, compared with the main checkout as above; live Orca data shows `runContext.path` can name the root while `workspaceId` names another checkout), setup policy (for `worktree`, which must be `run`) or session reuse (which must be off), `edit <id>` with only the flags that differ. A changed setup policy gets `--setup run`, and session reuse gets `--fresh-session`. The first step names the fields that hold the setup policy and session reuse; `launchSetup` and `reuseSession` are expected. A change between `worktree` and `main` is a `remove` plus a `create`, because the CLI does not move an automation between workspace modes.
   - A managed entry with no desired entry is `edit <id> --disabled` when its automation exists, is disabled and is owned by this account or `"*"`. Otherwise it is `remove <id>`. An entry that is already disabled is unchanged.
4. **Agent:** resolved before anything is planned. It is `--agent`, or else the single `agentId` all managed entries share. When the desired set is not empty and neither gives one (there are no managed entries, or they use different agents), sync returns `NeedsInput` with `required: ["agent"]` (exit 2) and changes nothing. Only when the desired set is empty is no agent needed, because sync then only disables or removes.
5. **Apply:** run the changes in plan order. Stop at the first failing call and exit 1 with Orca's stderr and the fix `Start Orca, then run the sync again`. The result lists what was done before the failure. `orca` missing (`ENOENT`) is exit 1 with `The orca command was not found` and the fix `Install Orca, or run the sync on a machine that has it`.
6. **Output:** the lines `+ automation: <name>`, `~ automation: <name> (cron, prompt)`, `- automation: <name>` and `off automation: <name>`, one line `left alone: <title>` for each foreign entry, and `Orca automations are up to date.` when nothing changed. `--json` adds `created`, `updated`, `disabled`, `removed`, `unchanged` and `leftAlone`. `--dry-run` prints the same and calls no command that writes.

The account is `account("orca")`. With none, exit 1 and the fix `Set git config user.email`. The trunk is `--branch` or `defaultTrunk`. With neither, exit 1 and the fix `Pass --branch <trunk>`.

### Amp schedules (`src/core/automations/amp-schedule.ts`)

`ampSchedule(cron, tz, now)` returns `{ schedule, label }` or `{ reason }`. It works like this:

1. **Fields.** The cron is trimmed and split on whitespace. Anything but five fields is `it is not five cron fields`.
2. **Minute and hour** (`plainNumbers`) must each be one number or a comma list of numbers, otherwise `its minute "<text>" is not a single number or a comma list of numbers` (or `hour`). A number outside 0–59 or 0–23 is `its <field> "<text>" has <n>, which is outside <min>-<max>`. The values are deduplicated and sorted.
3. **Day of month** must be `*` (`its day of month "<text>" must be *, because an Amp schedule repeats by day of the week, not by date`), and **month** must be `*` (`its month "<text>" must be *, because an Amp schedule repeats all year`).
4. **Day of week** (`dayCodes`): `*` means every day. Otherwise each comma part is a number or a range `a-b`, anything else being `its day of week "<text>" has "<part>", which is not a day or a range of days` (so `*/2` is refused). A day above 7 is `its day of week "<text>" has a day outside 0-7, where 0 and 7 are both Sunday`, and a backwards range is `its day of week "<text>" has the range "<part>", which starts after it ends`. Days map to `SU MO TU WE TH FR SA` by number mod 7, and are written once each in `MO TU WE TH FR SA SU` order.
5. **RRULE.** `FREQ=DAILY;BYHOUR=<hours>;BYMINUTE=<minutes>` for every day, or `FREQ=WEEKLY;BYDAY=<codes>;BYHOUR=<hours>;BYMINUTE=<minutes>`, with the lists comma-joined.
6. **DTSTART** (`firstFiring`). Read now's wall clock in `tz` with `Intl.DateTimeFormat` (`hourCycle: "h23"`). Then, for each day from today up to 14 days on (15 days in all, because a weekly time that falls in a spring-forward gap fires next a week later), on an allowed day, try every allowed hour and minute. Keep a candidate only when the zone reaches that wall clock (`firstInstant` below returns an instant) and that instant is at or after now. The first kept candidate in day, then time order gives the stamp `YYYYMMDDTHHMM00`. No candidate in 15 days is `no allowed day, hour and minute falls in the fortnight after now`. A zone `Intl` refuses is `"<tz>" is not an IANA time zone`. The line is `DTSTART;TZID=<tz>:<stamp>`, and `schedule` is that line, `\n`, and `RRULE:<rule>`.
7. **Label.** `<days>, <times> <tz>`. Days are `Every day`, `Weekdays` (exactly MO–FR), `Weekends` (exactly SA,SU), or the day names (`Mondays`, `Tuesdays`, …) joined as a list. Times are every hour and minute pair in order, as `h:mm AM` or `h:mm PM` on a 12-hour clock (0 is 12 AM, 12 is 12 PM), joined as a list. A list is `a`, `a and b`, or `a, b and c`. For example, `0 8 * * 1,4` in Sydney is `Mondays and Thursdays, 8:00 AM Australia/Sydney`, and `0 7,19 * * *` is `Every day, 7:00 AM and 7:00 PM Australia/Sydney`.

Two differences from Dragonfly's version:

- Dragonfly's `firstFiring` compares whole minutes, so at 09:00:30 it accepts 09:00:00, which is before now. Here a candidate is kept only when its instant is at or after `now.getTime()`.
- **A repeated wall-clock time means its first occurrence.** A `DTSTART;TZID=` stamp names a wall-clock time, and RFC 5545 reads a time that a fall-back change repeats as its first occurrence. So `firstInstant(wallClock, tz)` returns the earliest instant whose zone clock reads that time, or `undefined` when the zone skips it. It tries the zone's offsets a day before and a day after the time, keeps those that read back exactly, and returns the smallest. A candidate whose first occurrence has passed is not kept, even when its second occurrence is still ahead. The stamp then always means an instant at or after now, read the way Amp reads it. On a fall-back night this can skip the repeated hour's second firing for the first day only. The `RRULE` that follows is Amp's to expand.

`--json` gives the standard result object with `account` (the email) and `entries` (the array of entry objects above). The skill reads `.entries`. It returns `{ schedule, label }` or `{ reason }`. `plan amp` builds `{ name, title, schedule, schedule_label, run_mode: "fresh", prompt }` per desired entry, with `prompt` being the stub with trailing whitespace trimmed. One entry that cannot be expressed refuses the whole plan with exit 1, naming the automation and the reason. `plan amp` without `AMP_USER_EMAIL` exits 1 with `The Amp account is unknown: AMP_USER_EMAIL is not set, so this is not an Amp thread`.

`plan orca` prints the desired set and the changes `sync orca --dry-run` would make. The two share `planOrcaSync`.

### The `metafab-automations` skill (`resources/metafab-automations-skill/SKILL.md`)

It has the frontmatter `name: metafab-automations` and a harness-neutral description: "Registers this factory's automations in Orca or Amp so their schedules match .factory/automations/. Use when asked to sync automations, after a change under .factory/automations/ merges, or when an automation's body says to sync." It has two sections:

- **Orca.** Run `metafab automations sync orca --dry-run`, show the changes, then run it without `--dry-run`. Pass `--agent` the first time. Report the output lines.
- **Amp.** The procedure in [The Amp procedure](#the-amp-procedure) below, which the skill holds as written there. It is Dragonfly's `sync-automations` steps 1 to 7, its Rules and its Unattended run section, generalised. The two changes that matter are these. The saved-prompt check is the whole stub marker line, with the factory name, because two factories in one Amp project can each have an `intake` automation. And Dragonfly's Slack-approval rule is dropped, because how a run notifies anyone is `run.md`'s business.

### The Amp procedure

The skill's Amp section is these steps. `<factory>` is `name` in `.factory/factory.yaml`, `<repo>` is the `owner/name` of the repository's `origin`, and `<trunk>` is the branch the person names, or else the remote's default branch (`git symbolic-ref --short refs/remotes/origin/HEAD`, without `origin/`). The skill passes the same value to `plan amp` as `--branch`, so the checkout and the stubs name one trunk.

1. **Read the desired set.** Put the checkout on the trunk first, so a stale branch cannot install an old prompt or clear a live schedule. In a clean checkout (`git status --porcelain --untracked-files=all` prints nothing), run `git fetch origin && git switch --detach origin/<trunk>`. In a checkout with changes, leave it alone: run `git fetch origin && git worktree add --detach <tmp> origin/<trunk>`, run every command below in `<tmp>`, and remove it with `git worktree remove <tmp>` at the end. Then run `metafab automations plan amp --branch <trunk> --json` and read its `entries`. If it fails, stop and report its errors, changing nothing. Without `AMP_USER_EMAIL` it prints one line saying so, and that line is the whole report.
2. **Read what is installed.** `list_schedules` returns every schedule and event trigger in the account, across all its projects, so a title alone proves nothing. A thread can hold several schedules, so every schedule tool call in this procedure passes the schedule's `schedule_id` together with its holding `thread`, and never relies on a thread's "only schedule". Take each schedule's ID from its `list_schedules` entry, or, when the entry does not carry one, from `get_schedule` on the holding thread, which lists a thread's schedules when it holds several. An installed entry is **managed** (the only kind this procedure updates, clears or archives) when all five hold:
   1. its title starts with `automation: `;
   2. it is a recurring schedule, not an event trigger;
   3. its holding thread belongs to the Amp project for `<repo>`, read from the thread;
   4. its saved prompt, read with `get_schedule` and its `schedule_id`, has as its first line exactly `` Run the factory automation `<name>` from the `<factory>` factory. ``, where `<name>` is the name in its title;
   5. its holding thread's title is exactly the schedule's title, and its first message, read with `read_thread` from its current context, is exactly ``This thread holds the `automation: <name>` schedule of the `<factory>` factory for metafab automations sync. Do nothing and end.`` (the **holding marker**). It names the factory, so two factories that share a project and its parent thread never take each other's holding threads, even after a schedule is gone

   An entry titled `automation: ` that fails any of 2 to 5 is reported as `left alone: <title>` and read no further. A schedule with any other title is a person's own: it is never read further, compared or changed. For each managed schedule, read its prompt, recurrence, label, whether it is paused, and its run mode. When two managed schedules carry the same title (two syncs overlapped), keep the oldest and give up the others: clear each one by its `schedule_id` and retire its holding thread (step 6). They are reported as cleared.
3. **Put the holding threads under one parent.** `create_thread` makes a thread a child of the thread that called it, so without this step every holding thread would sit under whichever run made it.
   1. *Find it.* Search with `find_thread` for `"Factory automations" author:me archived:false repo:<repo>`, and keep the threads titled exactly `Factory automations`. The oldest is the parent. A younger one whose first message is the parent prompt in item 3 (only overlapping syncs make one) is archived once item 4 has moved its children out, and reported as cleared. Any other is a person's own and is left alone.
   2. *Adopt one when there is none.* For each kept managed holding thread, read the thread it was started from (`origin.sourceThreadID` in `find_thread`) and list that thread's children with `find_thread` and `parent:<id>`. A source thread that is the account's own, unarchived, in this project, not itself a holding thread, and whose children include every kept managed holding thread is adopted: retitle it `Factory automations` with `update_thread` and leave it where it is. At most one can qualify. A person who keeps the holding threads under some other thread retitles it `Factory automations` before the sync, and item 1 finds it.
   3. *Create one when there is still none.* Create a thread in the project titled `Factory automations`, whose only message is `This thread holds the factory automation holding threads for metafab automations sync. Do nothing and end.`, then make it top level with `update_thread` and `parent_thread: null`.
   4. *Move the strays.* List the parent's children with `find_thread` and `parent:<parent id>`, and move each kept managed holding thread that is not among them under the parent with `update_thread` and `parent_thread: <parent id>`. A kept holding thread is a managed one that step 2 does not give up and step 6 does not clear. Nothing else moves.
4. **Create the missing ones.** For each entry with no managed schedule, first look for an **empty holding thread** for it: any thread `find_thread` returns for `"automation: <name>" author:me archived:false repo:<repo>`, wherever it sits, that is titled exactly `automation: <name>`, whose first message is the holding marker for that name and this factory, and that holds no schedule (`get_schedule` returns null). A sync interrupted after creating the thread, before or after moving it under the parent, leaves one, and `list_schedules` never shows it. Reuse the oldest such thread and move it under the parent when it is not there already. When there is none, create a thread in the project titled `automation: <name>`, whose only message is the holding marker, written exactly, because the next sync reads it back as proof, and move it under the parent with `update_thread`. Then set its schedule with `set_schedule` on that thread, taking `title`, `prompt`, `schedule`, `schedule_label` and `run_mode` from the entry. The thread exists only to hold the schedule, and each firing starts a fresh child thread of its own. Every other empty holding thread with this factory's holding marker, found by `find_thread` for `"automation: " author:me archived:false repo:<repo>`, is retired (step 6): one for a name with no entry, or a younger one for a name whose thread was reused.
5. **Update the ones that differ.** Compare each managed schedule with its entry by title, and update it with `update_schedule`, its `schedule_id` and its holding `thread`, passing only the values that differ: prompt (trailing whitespace trimmed on both sides, because Amp trims what it stores), label, the `TZID` of `DTSTART`, and the whole `RRULE`. Never compare the date or time in `DTSTART`: it only says which firing comes first, and it moves on its own as the clock passes (`0 7,20 * * *` planned at 19:59 Sydney gives 20:00, and at 20:01 gives 07:00 the next day, with the same `RRULE`). A schedule that is paused (`enabled: true` resumes it), or whose run mode is not `fresh`, also differs. Anything equal is left alone.
6. **Clear the ones that are gone.** For each managed schedule with no entry (the automation was deleted, is now `enabled: false`, or now names another owner), clear it with `clear_schedule`, its `schedule_id` and its holding `thread`. Then **retire** the holding thread:
   - When it still holds another schedule (`get_schedule` on the thread is not null), leave it unarchived and report `kept: <thread> holds another schedule`.
   - Its children are the runs its schedule started. List them with `find_thread` and `parent:<thread>`, and check each unarchived one with `get_thread_status`. When one is still working, leave the holding thread unarchived this time and report `kept: <thread> has a run in progress`. It is now an empty holding thread, so a later sync finds it in step 4 and retires it then. The sync never stops a run and never passes `stop_running_turn`.
   - Otherwise archive each unarchived child, whose work is over because the automation no longer runs from this account, and then archive the holding thread, each with `update_thread` and `archived: true`. Archiving keeps every thread readable. This is the order `update_thread` supports for a thread with children. `keep_child_threads` is not used, because it applies only to the current thread.
7. **Report the diff, and nothing else.** One line each for `created`, `updated`, `cleared`, `moved` and `kept` that has anything in it, naming the automations (`moved` names holding threads). One line `parent: adopted <thread>` or `parent: created <thread>` when step 3 did either. One line naming the schedules that were already right, so a person sees the whole set whenever something changed. One `left alone: <title>` line per entry step 2 left alone. And the single line `no changes` when every schedule already matched, every holding thread was already under the parent, and nothing was left alone.

The skill's Rules, as Dragonfly states them:

- **Only managed schedules are this procedure's to change.** Every other schedule and event trigger in the account belongs to whoever made it, including an `automation: ` one from another project or another factory. It is never updated, cleared, archived or adopted.
- **A schedule belongs to the account that holds it, and every run of it acts as that person.** So a sync installs only the automations its account owns or that are `"*"`, never installs into another account, and never picks an owner. Moving an automation to another owner is a merged change to `owner`: the old owner's next sync clears it and the new owner's installs it. A factory's own sync automation is the exception: once it names someone else, the old owner's firing stops at the owner check before it can clear anything, so the old owner runs the sync by hand once. The same holds when the sync automation itself is turned off.
- **One parent thread per account and project** (step 3). The sync retitles only a thread it adopts as that parent, and moves only managed holding threads.
- **A second run in a row changes nothing.** Every step compares before it writes.
- **The files decide; the account is only read.** Nobody edits the account by hand to add or remove a run.

**Unattended runs.** Amp lets a run read, set, update or clear a schedule on another thread only when the current request asks for it, and a firing's saved prompt is the whole of what it is asked. So the skill says: when an automation's body asks for this sync, that body is the owner's standing, explicit request to manage the `automation: <name>` schedules on their holding threads, to retire a holding thread whose schedule it clears or that holds none, together with the finished runs under it, to find, adopt or create the `Factory automations` parent, to move holding threads under it and to archive a younger duplicate parent, and nothing else. The skill also tells the author of such an automation to write that request into its body. An unattended run asks nothing and messages nobody beyond what `run.md` says. A hand run carries the same request from the person who asked for it.

`metafab` (the existing built-in skill) gets one line in its maintenance section: "To register automations in a harness, load `metafab-automations`."

### Build and check (`src/core/build/plan.ts`, `skill.ts`, `src/core/check/drift.ts`)

`BUILTIN_SKILL_NAMES` in `plan.ts` becomes `["metafab", "metafab-automations"]` always, whatever the factory holds. Adoption (`src/core/adopt.ts`) already refuses to adopt an unowned destination with a name in that list, so an unowned `metafab-automations` directory is never moved into `.factory/`. `builtInSkills(factory, config)`, which decides what is installed, returns `["metafab"]`, plus `"metafab-automations"` when `factory.automations?.list.length` is greater than 0. It returns nothing when `metafab-skill` is `false`. Each one compiles from its own `resources/<name>-skill/` directory with the generated comment and CLI version. When a factory's last automation is deleted, the next `build` removes the skill's owned output, as for any removed skill. The outdated-skill check in `drift.ts` covers both skills. The skill text has no directives, so it is the same for every selection.

### Failure, repeat runs and Windows

- `sync orca` is idempotent. A second run plans nothing, and a run after a partial failure finishes the rest.
- `plan amp` is read-only.
- `execFile("orca", …)` on Windows finds `orca.exe` or `orca.cmd` only through `PATH` resolution, which `execFile` does not do for `.cmd`. Orca's CLI on Windows is out of scope for this plan. The runner reports `ENOENT` as above, and tests that start the fake binary are skipped on Windows. The planning tests run everywhere through the injected `OrcaRunner`.
