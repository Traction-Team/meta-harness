# Plan 2.020: Metafab automations sync registers a factory's automations in Orca and Amp

After Plan 2.019 a factory declares automations and Metafab can print each one's stub, but nothing registers them in a harness. This plan registers them in two harnesses. `metafab automations sync orca` makes this machine's Orca automations match the files, through the `orca` CLI. Amp's schedules can be changed only by an agent's tools inside an Amp thread, so `metafab automations plan amp --json` prints the desired set. A new built-in skill, `metafab-automations`, holds Dragonfly's proven `sync-automations` procedure, generalised, so an Amp agent can apply that set. Both paths share one desired set and one definition of a managed registration, so a person can register the same automations in either harness or both.

- [Building: Built-in `metafab` skill](../specs/building.md#built-in-metafab-skill)

It is owned, versioned and checked like `metafab`."

## Decisions

Agreed with the person on 2026-11-26:

| Topic | Choice | Reason |
| --- | --- | --- |
| Orca | Metafab runs the `orca` CLI with `execFile` and an argument list | Orca has a full `automations list/create/edit/remove --json` CLI |
| Amp | Metafab prints the desired set, and an agent applies it with Amp's tools by following a built-in skill | Amp has no schedule CLI; `set_schedule` and the thread tools exist only inside a thread |
| Where the Amp procedure lives | A built-in `metafab-automations` skill shipped with the CLI, not a fab workflow | It is tied to Metafab's output format and its marker, and every factory with automations needs it |
| Daily sync | Not built in. A factory adds its own `sync-automations` automation whose body runs the sync (fab-basic follow-up) | Dragonfly does it this way, and Metafab never schedules anything itself |

Proposed in this plan, for approval:

| Topic | Choice | Reason |
| --- | --- | --- |
| A disabled automation in Orca | `edit --disabled`, keeping run history; removed only when deleted or re-owned | Orca's `remove` deletes run history, which a person may still want |
| Orca agent | `--agent`, or the agent all managed registrations already share; otherwise exit 2 | The agent is a personal choice, and the CLI never guesses missing input |
| Skill installed only when needed | `metafab-automations` is installed only when the factory has at least one automation | A factory without automations does not need the text |

## Design

### Desired set (`src/core/automations/desired.ts`)

```ts
export type Target = "orca" | "amp";
export interface DesiredEntry { name: string; title: string; cron: string; tz: string; checkout: "worktree" | "main"; stub: string }
export async function desiredSet(factory: Factory, target: Target, account: string, trunk: string): Promise<DesiredEntry[]>;
export function isManaged(entry: { title: string; prompt: string }, factoryName: string): string | undefined;   // the automation name, or undefined
```

`desiredSet` takes the enabled automations that have a `schedule` trigger and an `owner` of `"*"` or `account` (compared without letter case), in name order. Their stubs come from `renderStub`. Any automation error stops it with the problems and exit 1, before the target is touched. `isManaged` checks that the title is `automation: <name>` and that the prompt's first line is the marker for that name and `factoryName`.

### Orca (`src/core/automations/orca.ts`)

```ts
export interface OrcaRunner { (args: string[]): Promise<{ exitCode: number; stdout: string; stderr: string }> }
export function createOrcaRunner(): OrcaRunner;   // execFile("orca", [...args, "--environment", "local", "--json"]), windowsHide, no shell
export async function planOrcaSync(input: { desired: DesiredEntry[]; installed: OrcaAutomation[]; repoRoot: string; factory: Factory; agent?: string }): Promise<OrcaChange[] | NeedsInput>;
export async function applyOrcaSync(changes: OrcaChange[], run: OrcaRunner): Promise<OrcaSyncResult>;
```

0. **Local only.** Every call passes `--environment local`, so `ORCA_ENVIRONMENT` or `ORCA_PAIRING_CODE` in the caller's environment cannot send the sync to a paired remote Orca. The spec's account and main checkout are this machine's. The runner also removes `ORCA_PAIRING_CODE` from the child's environment. If the first step finds that `local` does not pin it as documented, the runner removes both variables instead.
1. **First step of the build:** confirm the CLI's current shape with `orca automations create --help` and `orca agent-context --json`. Check the `--workspace` selector for the main checkout (expected `path:<root>`), the field that holds the run context path (seen as `runContext.path`), and whether `rrule` holds the cron as given (seen as `"0 9 * * 1,4"`). Write down anything different in `automations.md` in this pull request.
2. **Read:** `orca automations list --json`, then `result.automations`. The **main checkout** is the first `worktree ` line of `git -c core.quotePath=false worktree list --porcelain`, as Plan 1.028 decided, as a real path. The parent of `--git-common-dir` is wrong for `--separate-git-dir` and for submodules. So a sync run from a linked worktree still names the main checkout, and the factory directory inside it is the same relative path. When that line is missing, or names a bare repository or a directory that does not hold `.factory/` at that relative path (a bare repository, a submodule's linked worktree), sync exits 1 with `This repository has no main checkout for Orca to run in` and the fix `Run the sync from a normal clone`, changing nothing. Installed entries that belong to this repository have a `runContext.path` equal to the main checkout (case-insensitive on Windows and macOS, as `isInside` compares). Each such entry that passes `isManaged` is managed. Any other entry titled `automation: ` is reported in `leftAlone`.
3. **Plan:** keep the oldest managed entry of each title (`createdAt`) and remove the rest. For each desired entry:
   - With no managed entry, `create`: `--name <title> --trigger <cron> --timezone <tz> --prompt <stub> --provider <agent> --enabled --fresh-session`. For `worktree`, add `--repo path:<root> --base-branch origin/<trunk> --setup run`. For `main`, add `--workspace path:<main checkout>`. Here `<root>` is also the main checkout.
   - When the managed entry differs in prompt (trailing whitespace trimmed), cron (fields joined by one space), `timezone`, `agentId`, `enabled`, workspace mode, base branch, the workspace for `main` (the path part of `workspaceId`, after `::`, compared with the main checkout as above; live Orca data shows `runContext.path` can name the root while `workspaceId` names another checkout), setup policy (for `worktree`, which must be `run`) or session reuse (which must be off), `edit <id>` with only the flags that differ. A changed setup policy gets `--setup run`, and session reuse gets `--fresh-session`. The first step names the fields that hold the setup policy and session reuse; `launchSetup` and `reuseSession` are expected. A change between `worktree` and `main` is a `remove` plus a `create`, because the CLI does not move an automation between workspace modes.
   - A managed entry with no desired entry is `edit <id> --disabled` when its automation exists, is disabled and is owned by this account or `"*"`. Otherwise it is `remove <id>`. An entry that is already disabled is unchanged.
4. **Agent:** resolved before anything is planned. It is `--agent`, or else the single `agentId` all managed entries share. When the desired set is not empty and neither gives one (there are no managed entries, or they use different agents), sync returns `NeedsInput` with `required: ["agent"]` (exit 2) and changes nothing. Only when the desired set is empty is no agent needed, because sync then only disables or removes.
5. **Apply:** run the changes in plan order. Stop at the first failing call and exit 1 with Orca's stderr and the fix `Start Orca, then run the sync again`. The result lists what was done before the failure. `orca` missing (`ENOENT`) is exit 1 with `The orca command was not found` and the fix `Install Orca, or run the sync on a machine that has it`.
6. **Output:** the lines `+ automation: <name>`, `~ automation: <name> (cron, prompt)`, `- automation: <name>` and `off automation: <name>`, one line `left alone: <title>` for each foreign entry, and `Orca automations are up to date.` when nothing changed. `--json` adds `created`, `updated`, `disabled`, `removed`, `unchanged` and `leftAlone`. `--dry-run` prints the same and calls no command that writes.

The account is `account("orca")`. With none, exit 1 and the fix `Set git config user.email`. The trunk is `--branch` or `defaultTrunk`. With neither, exit 1 and the fix `Pass --branch <trunk>`.

### Amp schedules (`src/core/automations/amp-schedule.ts`)

`ampSchedule(cron, tz, now)` ports Dragonfly's function of the same name to TypeScript, with `plainNumbers`, `dayCodes`, `zoneClock`, `instantOfWallClock`, `firstFiring` and `daysLabel`. Two fixes to the port:

- Dragonfly's `firstFiring` compares whole minutes, so at 09:00:30 it accepts 09:00:00, which is before now. Here each candidate is kept only when its instant is at or after `now.getTime()`.
- A wall-clock time that a fall-back change repeats has two instants. `instantsOfWallClock(wallClock, tz)` returns every instant whose zone clock reads that time: it tries the offsets a day before and a day after, and keeps those that read back exactly. For each candidate day, `firstFiring` collects every instant of every allowed time on that day and takes the smallest one at or after now. It does not take the first in wall-clock order. So for Sydney `0,30 2 * * *` at the first 02:15 of a fall-back night, the first 02:30 wins over the second 02:00.

The `DTSTART` stamp is a wall-clock time with `TZID`, so both instants give the same stamp text. The rule matters only for deciding whether today's time is still ahead.

`--json` gives the standard result object with `account` (the email) and `entries` (the array of entry objects above). The skill reads `.entries`. It returns `{ schedule, label }` or `{ reason }`. `plan amp` builds `{ name, title, schedule, schedule_label, run_mode: "fresh", prompt }` per desired entry, with `prompt` being the stub with trailing whitespace trimmed. One entry that cannot be expressed refuses the whole plan with exit 1, naming the automation and the reason. `plan amp` without `AMP_USER_EMAIL` exits 1 with `The Amp account is unknown: AMP_USER_EMAIL is not set, so this is not an Amp thread`.

`plan orca` prints the desired set and the changes `sync orca --dry-run` would make. The two share `planOrcaSync`.

### The `metafab-automations` skill (`resources/metafab-automations-skill/SKILL.md`)

It has the frontmatter `name: metafab-automations` and a harness-neutral description: "Registers this factory's automations in Orca or Amp so their schedules match .factory/automations/. Use when asked to sync automations, after a change under .factory/automations/ merges, or when an automation's body says to sync." It has two sections:

- **Orca.** Run `metafab automations sync orca --dry-run`, show the changes, then run it without `--dry-run`. Pass `--agent` the first time. Report the output lines.
- **Amp.** Dragonfly's `sync-automations` steps 1 to 7 and its Rules, generalised. The name `develop` becomes the stub's trunk. `amp --json` becomes `metafab automations plan amp --json`, and the steps read its `entries` array. The holding-thread marker becomes the spec's text. The project check reads "the Amp project for this repository". The saved-prompt check is the whole stub marker line, `Run the factory automation \`<name>\` from the \`<factory>\` factory.`, with the name in the title and the factory from `factory.yaml`. Dragonfly's check of the words and name alone is not enough here, because two factories in one Amp project can each have an `intake` automation. A schedule whose marker names another factory is reported as left alone. It keeps finding, adopting or creating the `Factory automations` parent thread, moving stray holding threads, keeping the oldest duplicate, comparing only `TZID` and `RRULE`, clearing and archiving managed schedules with no entry, the report format, and the rule that an unattended run's authority comes from the automation body that asks for the sync.

`metafab` (the existing built-in skill) gets one line in its maintenance section: "To register automations in a harness, load `metafab-automations`."

### Build and check (`src/core/build/plan.ts`, `skill.ts`, `src/core/check/drift.ts`)

`BUILTIN_SKILL_NAMES` in `plan.ts` becomes `["metafab", "metafab-automations"]` always, whatever the factory holds. Adoption (`src/core/adopt.ts`) already refuses to adopt an unowned destination with a name in that list, so an unowned `metafab-automations` directory is never moved into `.factory/`. `builtInSkills(factory, config)`, which decides what is installed, returns `["metafab"]`, plus `"metafab-automations"` when `factory.automations?.list.length` is greater than 0. It returns nothing when `metafab-skill` is `false`. Each one compiles from its own `resources/<name>-skill/` directory with the generated comment and CLI version. When a factory's last automation is deleted, the next `build` removes the skill's owned output, as for any removed skill. The outdated-skill check in `drift.ts` covers both skills. The skill text has no directives, so it is the same for every selection.

### Failure, repeat runs and Windows

- `sync orca` is idempotent. A second run plans nothing, and a run after a partial failure finishes the rest.
- `plan amp` is read-only.
- `execFile("orca", …)` on Windows finds `orca.exe` or `orca.cmd` only through `PATH` resolution, which `execFile` does not do for `.cmd`. Orca's CLI on Windows is out of scope for this plan. The runner reports `ENOENT` as above, and tests that start the fake binary are skipped on Windows. The planning tests run everywhere through the injected `OrcaRunner`.

## Done when

- On a Mac running Orca, in a format 2 factory with one scheduled automation, `metafab automations sync orca --agent opencode` creates an Orca automation that, run now, opens a worktree on the trunk and starts OpenCode on the stub. A second sync prints `up to date`.
- In an Amp thread of the project, "sync the automations" loads `metafab-automations`, which creates the holding thread and schedule under `Factory automations`. A second run reports `no changes`.
