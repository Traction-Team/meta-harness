# Plan 2.021: One module decides which factory formats metafab reads and what each needs

Format 2 is checked by hand in about twenty places: `format === 2` in discovery, the loader, `create`, build rendering, the automations commands, and `1 | 2` literal types and `value !== 1 && value !== 2` in the npm and fab source checks, with the message "Use format 1 or 2" written out twice. Adding a format means finding all of them. This refactor puts the known formats and the minimum format of each feature in one module, so Plan 2.022 adds format 3 by changing one constant and one table entry. Behaviour does not change: every message, exit code and test stays the same.

## Specs

- [Factory format](../specs/factory-format.md): formats 1 and 2, rule 7
- [Sharing: fab validation](../specs/sharing.md): unknown factory format versions

This plan changes no spec.

## Decisions

| Topic | Choice | Reason |
| --- | --- | --- |
| Shape of the helper | A list of known formats plus a table of features with their minimum format, and `supportsFeature(format, feature)` | The person asked for "a function for checking format above a requirement, reused", so a new format costs one constant |
| Behaviour | None changes, including message text | One hat at a time: the format 3 behaviour comes in Plan 2.022 |

## Design

New `src/core/factory/format.ts`:

```ts
export const FACTORY_FORMATS = [1, 2] as const;
export type FactoryFormat = (typeof FACTORY_FORMATS)[number];
export const LATEST_FORMAT: FactoryFormat;               // the last entry
export function isFactoryFormat(value: unknown): value is FactoryFormat;

/** The first format that has each feature. */
export const FORMAT_FEATURES = { env: 2, skills: 2, directives: 2, automations: 2 } as const;
export type FormatFeature = keyof typeof FORMAT_FEATURES;
export function supportsFeature(format: FactoryFormat | undefined, feature: FormatFeature): boolean; // undefined reads as 1
export function formatListText(): string;                // "1 or 2"; "1, 2 or 3" later
```

Each call site uses it:

- `knownFormat` in `validate.ts` and `fabFormat` in `sources/validate.ts` use `isFactoryFormat`. `checkNpmFormat` in `sources/npm.ts` too. Their fixes build `Use format ${formatListText()}, or upgrade @seasb/metafab`, which prints today's text.
- The `1 | 2` types in `factory/types.ts`, `sources/types.ts`, `publish/package-json.ts`, `env/declarations.ts`, `factory-yaml.ts`, `discovery.ts` and `create.ts` become `FactoryFormat`.
- `format === 2` / `format !== 2` / `format === 1` checks become `supportsFeature(format, "<feature>")`: `automations` in `discovery.ts`, `load.ts`, `create.ts`, `automations/load.ts` and the three `automations-*` commands; `env` and `skills` in `factory-yaml.ts`, `env/declarations.ts` and `env/validate.ts`; `directives` in `build/plan.ts` (lines 294 and 321) and `env/validate.ts`.
- `supportsFeature(undefined, …)` is for callers that already default a missing format to 1 (discovery, `load.ts`, `create.ts`). `parseEnvField` and `parseSkillsField` today report "needs format: 2" only when the format is exactly 1, never when it is missing or invalid, because rule 7 already reports those. They keep that: `format !== undefined && !supportsFeature(format, "env")` (and `"skills"`). So a `factory.yaml` with no `format` plus `env: {}` and `skills: {}` still reports only the missing format, and `format: 99` reports only rule 7.
- The "needs format: 2" problems stay word for word: `'"env" needs format: 2'` in `env/declarations.ts` and `'"skills" needs format: 2'` in `factory-yaml.ts` keep their wording and take the number from `FORMAT_FEATURES`. `needsFormatTwo()` in `automations/problems.ts` is renamed `needsFormat("automations")` with the same output.
- The rule 7 message in `rule7FactoryYaml`, `"format" must be 1 or 2`, is built from `formatListText()`. Its fix (`Set format: 2 to use env and skills, or format: 1`) stays as written; Plan 2.022 rewrites it for format 3.
- The `.factory/automations/ needs format: 2` warning in `load.ts` and the error in `automations/problems.ts` take the number from `FORMAT_FEATURES.automations`.

`format.ts` imports nothing from the rest of `src/`, so every module can import it without a cycle.

**Failure, second run, Windows.** Unchanged: no file, path or exit code changes.

## Tests

- New `test/core/factory/format.test.ts`: `isFactoryFormat` accepts 1 and 2 and refuses 0, 3, `"2"` and `2.5`; `supportsFeature` is false for every feature at 1 and true at 2; `supportsFeature(undefined, "env")` is false (the signature is `supportsFeature(format, feature)` throughout); `formatListText()` is `1 or 2`. A wrong table entry or an off-by-one comparison fails it.
- In `test/core/factory/validate.test.ts`: a `factory.yaml` with no `format` and `env: {}` plus `skills: {}` reports only `factory.yaml is missing "format"`; `format: 99` with the same fields reports only rule 7; `format: 1` with them reports both "needs format: 2" errors. Add these if no existing test pins them; they catch a `supportsFeature(undefined, …)` that reads a missing format as 1.
- Every existing test passes unchanged. That is the behaviour proof for the refactor.
