# Plan 1.014: Adoption and `init` polish

Fix six follow-ups from the last cold review of PR #10 (Plan 1.006). None of them loses data. Adoption refuses some skills that `build` would accept, two problems use the wrong wording, and `init` reports some read failures with the wrong cause or leaves files behind when it fails. After this merges, adoption accepts exactly what `build` accepts, `init` names the real cause of a read failure, and an unreadable `metafab.yaml` or `factory.yaml` stops `init` before it writes anything. Other failures in the closing build can still leave the new factory files behind, as today.

## Specs

- [CLI: Adopt existing skills](../specs/cli.md#adopt-existing-skills)
- [CLI: Set up a factory](../specs/cli.md#set-up-a-factory)
- [Building: Compiled skills](../specs/building.md#compiled-skills), and the 2026-10-25 symlink decision in the roadmap
- [Building: Repeatability](../specs/building.md#repeatability): an unreadable path is `Cannot read <path>`, exit 1

## Decisions

| Topic | Choice | Reason |
| --- | --- | --- |
| Which symlinks adoption accepts | A link whose target, resolved from the skill's new place in `.factory/skills/<name>/`, is inside `.factory/` | This is exactly the rule `build` applies to source skills (decision 2026-10-25). Adoption must not refuse a skill that would build after the move |
| Who judges links during adoption | `treeProblems` alone; `compileSkill` gets `linkRoots` so it accepts the same links | The user has not moved anything yet, so build's "points outside .factory/" about a file in `.claude/skills/` is confusing. One gate means one wording |
| How `init` recognises an unreadable `metafab.yaml` | `load.ts` exports `unreadableConfigCode(config)`, backed by a module-private `WeakMap`; `init` stops matching the problem text | Rewording the message today silently disables the guard; a `WeakMap` keeps `types.ts` out of `owns` |

## Design

### 1. Symlinks into `.factory/` (`src/core/adopt.ts`, `treeProblems`)

Today `treeProblems` resolves each link from its destination (`.factory/skills/<name>/<relative>`) and requires the target to be inside the destination skill directory. Change the bound to the factory directory (`<root>/.factory`). A link that resolves inside the skill being moved still passes. A link that resolves anywhere else, including another destination such as `.agents/skills/`, is still refused with exit 5. The message becomes `Symlink <path> points outside .factory/ after the move`, with the fix `Point it inside .factory/, or remove the symlink`.

`.claude/skills/<name>`, `.agents/skills/<name>` and `.factory/skills/<name>` have the same depth, so a relative link keeps its meaning after the move. Keep computing the target from the destination path, because the code depends on that.

### 2. Wording of compiled-skill problems (`checkSkillTree`)

`checkSkillTree` also calls `compileSkill` with `factoryDir` set to the candidate skill directory. `compileSkill` resolves each link from where it is now, under `.claude/skills/` or `.agents/skills/`, and refuses one outside `factoryDir` with build's wording ("points outside .factory/"). Passing `<root>/.factory` instead would refuse every link that stays inside the skill, so neither directory alone is right.

Make `treeProblems` the only gate on where a link points, because it resolves from the destination and words the problem for adoption. Let `compileSkill` accept what `treeProblems` accepts:

- `CompileSkillOptions` (`src/core/build/skill.ts`) gains `linkRoots?: string[]`. These are extra absolute directories a link may resolve into, beside `factoryDir`. `build` never passes it, so build's behaviour does not change.
- `checkSkillTree` passes `factoryDir: <candidate skill dir>` and, when `<root>/.factory` exists, `linkRoots: [<root>/.factory]`. A link into `.factory/` is then accepted by both gates. A link anywhere else is refused by `treeProblems` with adoption wording before `compileSkill` runs.
- Other `compileSkill` problems (a broken link, an unreadable file) pass through, with `file` set to the candidate path, as today.

Dot directories inside a skill are not installed, so links in them are not judged, as today.

### 3. Built-in skill names (`src/core/build/plan.ts`, `src/core/adopt.ts`)

`plan.ts` exports `BUILTIN_SKILL_NAMES` (today `["metafab"]`) next to `BUILTIN_SKILL_DIR`, and `compileBuiltinSkill` uses it. `adopt.ts` imports it and drops its own copy.

### 4. Real read errors from `loadConfig` (`src/core/config/load.ts`, `src/core/init/run.ts`)

`loadConfig` reports any read failure other than `ENOENT` as `Cannot read .factory/metafab.yaml`. Keep that for every error from `readFile` that carries a string `code` (`EACCES`, `EPERM`, `EISDIR`, `EIO`, `ENOTDIR`, `ELOOP`, `EMFILE` and the rest), as [Repeatability](../specs/building.md#repeatability) requires. Rethrow only an error without a string `code`, so an unexpected error reaches the CLI's bug path (`renderBug` in `src/cli.ts`, which prints the stack and exits 1) instead of looking like a permissions problem.

The intake note's real complaint is in `init`. `init` maps the problem to `Cannot read file ... / Check its permissions or restore the file` whatever the cause. Keep that fix line for `EACCES` and `EPERM`, and use `Restore the file, then run metafab init again` for every other code. Export:

```ts
/** The error code when `config` came from a file that could not be read; undefined otherwise. */
export function unreadableConfigCode(config: Config): string | undefined
```

It reads a module-private `WeakMap<Config, string>` that `unreadableConfig(code)` fills. It does not match message text, and `src/core/config/types.ts` stays unchanged. `init`'s `unreadableConfig` helper is replaced by this call.

### 5. Unreadable `.factory/factory.yaml` stops `init` early (`src/core/init/run.ts`)

Today `runInit` loads the factory after it writes `.factory/AGENTS.md` and `.gitattributes`, so an unreadable `factory.yaml` fails the build and leaves those files behind. Before `ensureFactoryFiles`, when `.factory/factory.yaml` exists, read it once. On a read error, throw `unreadableFactory(".factory/factory.yaml", "Cannot read .factory/factory.yaml", "Check its permissions or restore the file")`, with exit 1 and no writes. A file that is readable but invalid is not refused here; the closing build reports it, as today.

## Tests

- Adopt: `.claude/skills/release/notes.md -> ../../../.factory/shared/notes.md` is moved, and a following `build` installs `notes.md` with the target's content
- Adopt: a link to `../../../.agents/skills/other/x.md` is still refused with exit 5, with the new message, and nothing changes
- Adopt: a link that stays inside the skill is still accepted (regression)
- Adopt with `.factory/` present: a link that stays inside the skill and a link into `.factory/shared/` are both accepted in the same skill, and the move and the following `build` succeed
- Adopt with no `.factory/` yet: a link that stays inside the skill is accepted. This is the existing "accepts a symlink that stays inside the moved skill" test, which must still pass
- `compileSkill` with `linkRoots`: a link into a listed root is copied; without `linkRoots` the same link is refused, as today
- Problems are injected with `vi.mock("node:fs/promises", ...)`, because `loadConfig` has no seam. Use real files where they reach the code: EISDIR from a directory named `metafab.yaml`, and EACCES from chmod 000
- `adopt.ts` has no hard-coded `"metafab"` list (a unit test against the exported constant is enough)
- `loadConfig` with an injected `EIO` returns the `Cannot read` problem and `unreadableConfigCode` gives `EIO`; an injected `ENOTDIR` is also unreadable; an injected error without a `code` throws
- `init` with an `EIO` on `metafab.yaml` says `Restore the file, then run metafab init again`, not "Check its permissions"
- `init` with an unreadable `metafab.yaml`: exit 1, `Cannot read file .factory/metafab.yaml`, nothing written (regression, still passes after the predicate change)
- `init` with an unreadable `factory.yaml` (chmod 000; skipped on Windows and when running as root): exit 1, no `.factory/AGENTS.md`, no `.gitattributes`
