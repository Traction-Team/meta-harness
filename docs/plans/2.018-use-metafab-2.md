# Plan 2.018: fab-basic and this repository use metafab 2.0.0

Plan 2.015 pinned the prerelease while 2.0.0 did not exist: fab-basic 0.2.0 tells its importers to run `npx --yes @seasb/metafab@next`, its CI builds with `@next`, and this repository's devDependency is exactly `2.0.0-next.1`. Once Plan 2.017 has published 2.0.0 under `latest`, this plan moves all three to the stable release, as Plan 2.015's decisions said: fab-basic 0.2.1 goes back to plain `npx --yes @seasb/metafab`, and this repository depends on `^2.0.0` and updates to fab-basic 0.2.1.

## Specs

- [Sharing: Updating](../specs/sharing.md)
- [Building: Keeping installed skills current](../specs/building.md#keeping-installed-skills-current)

This plan changes no spec.

## Decisions

| Topic | Choice | Reason |
| --- | --- | --- |
| fab-basic's `metafab` default | `npx --yes @seasb/metafab`, no tag or version | Plan 2.015's decision: back to the plain package when 2.0.0 ships. 2.0.0's unknown-field and unknown-format fixes name the upgrade if a later fab needs a newer CLI |
| fab-basic version | 0.2.1, a patch | Only the CLI command in templates, docs and CI changes; the factory's behaviour and format do not |
| This repository's devDependency | `^2.0.0` | Plan 1.025's caret range: the hooks follow patch and minor fixes |

## Design

**Part A, in `github:Traction-Team/fab-basic`, before this repository's pull request.** On a branch with a pull request there:

- Replace `npx --yes @seasb/metafab@next` with `npx --yes @seasb/metafab` in `.factory/templates/setup/factory.md`, `.factory/templates/setup/orca.yaml`, the `orca.yaml` requirement's description in `.factory/factory.yaml`, `.factory/docs/process.md`, fab-basic's own `docs/factory.md` (its `metafab` setting, which its workflows and scripts run), `README.md` and `.github/workflows/ci.yml`.
- Reword README's version paragraph ("Run it through the `next` dist-tag until 2.0.0 ships") to say 0.2.x needs Metafab 2.0.0 or later, which `npx --yes @seasb/metafab` installs.
- Before tagging, `git grep -n '@seasb/metafab@next'` must print only `CHANGELOG.md`'s 0.2.0 entries, which stay as history. The 0.2.1 entry names the `next` dist-tag in words, not the `@seasb/metafab@next` command.
- Add a `CHANGELOG.md` entry for 0.2.1 that says so, and that importers who already created `docs/factory.md` or `orca.yaml` from the 0.2.0 templates can change `@next` there by hand, because `update` never rewrites a file a template created.
- CI green on all four jobs, merge, tag `v0.2.1` on `main`. A release is the tag alone; nothing is published to npm.

**Part B, this repository's pull request.**

0. `npm view @seasb/metafab version` must print `2.0.0` (or a later 2.x). Until it does, this plan stays `draft`, so `next.mjs` never offers it, and with `stacking` on never chains it onto 2.017's branch.
1. `npm install --save-dev @seasb/metafab@^2.0.0`, so `package.json` reads `^2.0.0` and the lockfile resolves the newest stable 2.x.
2. `node dist/cli.js update`: the recorded range `^0.2.0` selects 0.2.1. The review summary lists only the changed lines above. `node dist/cli.js build`, then `node dist/cli.js diff` must print no local edits.
3. `docs/factory.md` note: the devDependency is `^2.0.0` and the `2.0.0-next.1` pin is gone. The `metafab` setting stays `node dist/cli.js`.

**Failure.** If 2.0.0 is not on npm, step 1 fails and nothing changes: stop. If fab-basic's CI fails on the plain package, the release is wrong: stop and report it, do not tag. If `update` shows conflicts in `.factory/`, a local edit slipped in after 2.015: resolve toward upstream and record the edit in fab-basic.

**Second run.** `update` on 0.2.1 again reports nothing to do; `build` reports `Up to date.`
