# Plan 2.023: Root `AGENTS.md` shows the factory layout and a table of its workflows

After [Plan 2.022](2.022-workflow-files.md) a workflow file is not installed as a skill, so no harness lists it. Agents learn it exists from root `AGENTS.md`, which every agent reads. This plan adds a generated **Workflows** section to the factory block: a short tree of what `.factory/` holds, one sentence on how to read a workflow file, and a table with each workflow's name, the file to read and when to use it. It lists every workflow, including those that are skills. Until now the spec said the block never lists workflows, and fab-basic wrote its own table in `.factory/AGENTS.md`. A new `agents-md` map in `metafab.yaml` turns the section off.

## Specs

- [Building: Root `AGENTS.md`](../specs/building.md#root-agentsmd)
- [Configuration: Top-level keys](../specs/configuration.md#top-level-keys) and [Validation](../specs/configuration.md#validation)

This plan changes both; see Design.

## Decisions

Agreed with the person on 2026-11-28:

| Topic | Choice | Reason |
| --- | --- | --- |
| What the section holds | The `.factory/` layout as a text tree, then a table of name, file and description | "Explain the fab structure, maybe with one of those text diagrams, and then a short table with name / path / when to use" |
| Flow diagram | None. The numbered Pipeline list already gives the order and the stops | The person: the pipeline in `factory.yaml` already covers it |
| Which workflows | Every workflow, including skill workflows, whatever the format | The person agreed that the section appears in every factory's block, with a setting to turn it off |
| Setting | `agents-md: { workflows: false }` in `metafab.yaml`; default `true` | The person: a nested `agents-md` map, because more `AGENTS.md` settings are likely |
| A workflow that is also a skill | Its row gives its file like any other; the intro says a workflow that is also a skill can be loaded as that skill | One table shape for every workflow |

## Design

**The section.** `renderAgentsBlockBody(factory, standing, options)` in `build/agents.ts` writes it after the rendered `.factory/AGENTS.md` and before `## Pipeline`, when `options.workflows` is true and `factory.workflows` is not empty:

````markdown
## Workflows

This repository's process lives in `.factory/`:

```text
.factory/
  AGENTS.md      standing instructions, above
  factory.yaml   the pipeline, below
  workflows/     how work moves: read the one that matches the request
  skills/        reusable knowledge, installed as agent skills
  partials/      text that other files import
  templates/     document templates
  scripts/       scripts the workflows run
  automations/   work that runs on its own
  docs/
```

When a request matches a workflow, read its file and follow it. A workflow that is also installed as a skill can be loaded as that skill.

Workflow files are read as written, so apply their directives yourself:

- Your environment is one value of each variable below. Work out the one value for this run from the labels. If no label settles it, run `metafab env`; if that still leaves more than one value, ask the person which applies before you follow the workflow. Never pick a case at random.
  - `harness`: `opencode` (In OpenCode (OPENCODE=1 is set)), `claude` (In Claude Code (CLAUDECODE=1 is set)), `amp` (In Amp (AMP_THREAD_ID is set))
  - `workspace`: `orca` (With Orca worktrees), `orb` (In Amp orbs (workers start with create_thread)), `worktree` (With plain git worktrees)
- `<!-- factory:import <path> -->`: read that file, with `<path>` relative to the file the line is in, and apply these rules inside it too.
- `<!-- factory:when <condition> -->` ... `endwhen`: keep the text only when the condition holds for your environment.
- `<!-- factory:switch env.<name> -->`: keep the one `case` that lists your value, or `default` when no `case` lists it; skip the rest.
````

The variable lines are generated from `env` in `factory.yaml`, in declaration order, each value with its label in brackets; a value with no label is written by name only. The labels are how an agent tells its value, so fab-basic's already name the environment variable that identifies each harness. A variable's `default` is noted after its values (`default: worktree`). The whole "apply their directives" list appears only when `supportsFeature(format, "directives")`; the variable lines only when `env` declares a variable. A `case` that lists several values, nested blocks and nested imports need no extra wording: the rules apply at every level, as the [Switch](../specs/environments.md#switch) and [Import](../specs/environments.md#import) sections define them for `build`. Then the table:

````markdown
| Workflow | File | When to use it |
| --- | --- | --- |
| `file-work` | `.factory/workflows/file-work.md` | A bug, idea, feedback or follow-up... |
````

- **Tree.** `Factory.topLevel` (new, filled by `loadFactory`) is the sorted list of non-dot entries directly in `.factory/`, each with whether it is a directory. The tree shows `AGENTS.md` and `factory.yaml` when they exist, then directories: the known ones in the order above with their fixed comment (`automations/` only in format 2 and later), then any other directory, by name, with no comment. Files other than those two, such as `metafab.yaml` or a `README.md`, are not shown. Comments are padded to one column.
- **Directive sentence.** Only when `supportsFeature(format, "directives")`. A format 1 factory has no directives.
- **Rows.** Pipeline workflows in pipeline order, then the rest by name. The File column is `Workflow.file` in backticks. The description is `Workflow.description`, with `|` written `\|`. A skill workflow with no description is already a rule 1 error, so the build never reaches it.
- **Same for everyone.** The section depends only on the factory, not the environment selection, like the rest of the block.

**Setting.** `metafab.yaml` gains:

```yaml
agents-md:
  workflows: false   # default true
```

`Config.agentsMd: { workflows: boolean }`. `TOP_LEVEL_KEYS` gains `agents-md`. Validation: `agents-md` must be a map (rule 3); its only key is `workflows`, and an unknown key is an error that suggests the closest known key (rule 2); `workflows` must be a boolean. An empty map or `agents-md:` with no value means the defaults. `build` passes `config.agentsMd.workflows` to `renderAgentsBlock`. `check` compares against the same output, so turning the setting on or off makes the committed block stale until the next `build`.

**Line limit.** The existing 300-line warning counts the new section.

**Existing factories.** Every factory with workflows gets the section on its first build with this version, so `check` and the CI recipe's `git diff --exit-code -- AGENTS.md` report a stale block until that build's `AGENTS.md` is committed. Hooks rebuild it locally. Plan 2.024's release notes say so.

**This repository.** The regenerated `AGENTS.md` block gains the section, listing the nine fab-basic workflows by their `SKILL.md` files. fab-basic's hand-written "Factory workflows" table stays until [Plan 2.025](2.025-use-workflow-files.md) removes it upstream, so for a while the block has both.

**Specs.** `building.md`, Root `AGENTS.md`: the example gains the section; rule 5 becomes "It writes a Workflows section listing every workflow with its file and description, unless `agents-md.workflows` is `false`", and the closing paragraph about the pipeline being the only added content changes to match. `configuration.md`: the example and the top-level table gain `agents-md`, and a short `agents-md` section lists `workflows`. `environments.md` gains "Reading a workflow file in place": an agent reading a workflow file applies the same rules `build` applies when it renders (imports relative to the containing file, recursively; a `when` keeps its text when its condition holds; a `switch` keeps the `case` that lists the value, else `default`), for the one value of each variable that applies to its own run, which it works out from the labels the generated block lists. When the labels and `metafab env` still leave several values, it asks the person; unlike `build`, it does not keep every matching branch, because it acts rather than displays.

**Failure.** A bad `agents-md` value is a configuration error: `check` exits 1 and `build` refuses as for any config error. No partial writes: block writing is unchanged.

**Second run.** An unchanged factory and setting give the same block; `build` reports `Up to date.`

**Windows.** Paths in the File column use `/`.

## Tests

- **Rendering** (`test/core/build/agents.test.ts`): extend `EXPECTED_BLOCK` for `mark4-like`, whose six pipeline workflows are skills. Add a standalone workflow whose name sorts before `build-slice` (such as `audit/SKILL.md`), so the rows must follow pipeline order and then name order; an implementation that sorts all rows by name, or lists them in discovery order, fails. A format 3 fixture with `a.md`, `b/workflow.md`, `c/SKILL.md` and a description holding `|` checks the File column (`b/workflow.md`, not the folder), the escaping and the directive sentence. A format 1 fixture has no directive list. A format 3 fixture declaring `harness` (labels on two values, none on the third, a `default`) gets one variable line in declaration order with the labels in brackets, the unlabelled value by name and the default noted; a format 3 fixture with no `env` gets the directive list without variable lines. A factory with an unknown top-level directory lists it last with no comment; a factory with `metafab.yaml` and `README.md` lists neither.
- **Setting** (`test/core/config`): `agents-md: { workflows: false }` parses; `agents-md: true`, `agents-md: { workflow: false }` (suggests `workflows`) and `agents-md: { workflows: "no" }` are errors with line and fix.
- **Build and check** (`test/core/build`, `test/core/check`, `test/cli`): with `workflows: false` the block has no Workflows section and still has the Pipeline. A block written before this change is stale for `check`. A factory with no workflows gets no section.
