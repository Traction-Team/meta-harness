# Plan 2.011: A factory declares env variables and each developer selects values in Git config

A team whose members use different agent harnesses and workspace tools today writes every variant into every workflow, or writes one and lets the others guess. [Environments](../specs/environments.md) fixes that in five plans. This first one introduces `format: 2`, lets `factory.yaml` declare `env` variables and their values, and resolves each developer's **selection** from `--env`, `FACTORY_ENV_<VAR>`, Git config and the declared defaults. `metafab env` shows the selection and where each value came from, and `metafab env set` and `env unset` write it to repository or global Git config and rebuild. `build` and `check` accept `--env` and carry the resolved selection into the build planner, but nothing renders differently yet: Plan 2.012 adds the directives that use it. This is the first version 2 plan; the store plans (2.001 onwards) add `documents` and scorers to the same format 2.

## Decisions

Agreed with the person:

| Topic | Choice | Reason |
| --- | --- | --- |
| Names | `env` in `factory.yaml`, `factory.env.<var>` in Git config, `FACTORY_ENV_<VAR>` in the process; no "metafab" and no "dimensions" | The format is open; another tool can implement it |
| Several values per variable | A selection holds a list of values for each variable | One developer uses several harnesses in one checkout |
| Where a selection lives | Git config, by scope, below `--env` and `FACTORY_ENV_*` | Personal, never committed; `--global` covers every repository; worktrees share `.git/config` |
| `harness` and `agents` | `env` controls content only; `agents` still chooses install destinations | Two separate questions: what to say, and where to write it |
| Format | `format: 2`, introduced here and shared with the store plans; this work comes after the v1 release and before the store | One format bump; a 1.x CLI refuses a format 2 factory with a clear rule 7 error |

Proposed in this plan, for approval:

| Topic | Choice | Reason |
| --- | --- | --- |
| `env set` and `env unset` rebuild | Both run `build` after writing Git config, and report its changes | The installed skills match the new selection without a second command; the spec says so |
| Reading Git config | One call, `git config -z --show-scope --get-regexp ^factory\.env\.`, from the factory root, parsed as NUL-terminated records | One process for every variable; `--show-scope` gives the priority order Git itself uses; `-z` means a value with a newline cannot be misread as another key |
| Other Git scopes | Lines in any scope other than `worktree`, `local`, `global` and `system`, such as `command` from `git -c` or `GIT_CONFIG_COUNT`, are ignored silently | The spec's order is exactly worktree, local, global, system; a selection never comes from how one Git process was started |
| Git older than 2.26 | `--show-scope` is refused: one warning, and source 3 gives nothing | `--show-scope` arrived in Git 2.26 (2020); no silent misreading of scopes |
| `--env harness=` (no value) | A warning, `--env harness= names no value`, and the next source applies | The spec's rule: the first source with a declared value wins; an empty option is likely a script with an unset shell variable |
| Same variable twice in `--env` | Error, exit 1 | The spec says the option repeats once per variable; a second value list for one variable is ambiguous |
| `env set` value | Written as the given values, trimmed and deduplicated, joined with `,`, in the given order | Readable with `git config --get`; order does not change the selection |
| `env set harness=` | Error, exit 1, fix `Run metafab env unset harness` | An empty key would be ignored by every read; unset says what was meant |
| `env unset` of an undeclared variable | Allowed, with no warning, when the name is a valid variable name | Cleans up a stale global key that another factory declared |
| Planner signature | `planBuild(factory, config, cliVersion, options?: PlanBuildOptions)`; `options.selection` is a resolved selection; when absent, `planBuild` resolves one from the process environment and Git config | `import`, `update`, `init` and `setup` keep their calls and still honour the developer's selection; only `build` and `check` take `--env` |
| `build --json` | Adds `env` when the factory declares variables | Scripts can see what a build was for; nothing changes for format 1 factories |
| Problem location for selection warnings | `.factory/factory.yaml`, on the variable's line, with the source in the message | Every problem needs a file and a line; the declaration is what the warning is about |

## Design

### Types (`src/core/env/types.ts`, new; `src/core/factory/types.ts`)

```ts
export interface EnvValue {
  name: string;
  /** The declared label, or `When <variable> is <value>`. */
  label: string;
  line: number;
}
export interface EnvVariable {
  name: string;
  description?: string;
  values: EnvValue[];          // declaration order, never empty after validation
  default?: string[];          // declaration order of the names given
  line: number;                // the variable's key line in factory.yaml
}
/** Variable name → selected value names, in declaration order. Every declared variable has an entry. */
export type EnvSelection = ReadonlyMap<string, readonly string[]>;
export type SelectionSource = "option" | "environment" | "git" | "default" | "all";
export type GitConfigScope = "worktree" | "local" | "global" | "system";
export interface ResolvedVariable {
  variable: string;
  values: string[];
  source: SelectionSource;
  scope?: GitConfigScope;      // for "git"
  from?: string;               // for "environment": FACTORY_ENV_<VAR>
}
export interface ResolvedSelection {
  variables: ResolvedVariable[];
  selection: EnvSelection;
  warnings: Problem[];
}
```

`FactoryYaml.format` becomes `1 | 2`, and `FactoryYaml` gains `env: EnvVariable[]` (`[]` when absent).

### Parsing and rule 14 (`src/core/env/declarations.ts`, new; `src/core/factory/factory-yaml.ts`; `validate.ts`)

- `isFormatOne` becomes `knownFormat(field): 1 | 2 | undefined`, keeping today's rule that the node is a plain YAML integer (`YAML_INTEGER_PATTERN`), now with the value 1 or 2. `format: "2"` and `format: 2.0` are not formats. Rule 7's message becomes `"format" must be 1 or 2`, fix `Set format: 2 to use env, or format: 1`. A missing `format` keeps `Add format: 1`.
- `KNOWN_FACTORY_FIELDS` gains `"env"`.
- `parseEnvField(fieldNode, parsed, file, problems): EnvVariable[]` in `declarations.ts`, shaped like `parsePipelineEntry`. All problems are errors on the key's or value's line:
  - `env` with `format: 1`: `"env" needs format: 2`, fix `Set format: 2`, on the `env` line. The variables are still parsed so their own errors show too.
  - `env:` with nothing after it (null) or `{}`: no variables, no problem (spec rule 8).
  - `env` not a mapping: `"env" must be a mapping of variable names`, fix `Write each variable as <name>: { values: [...] }`.
  - A variable name that is not a string, breaks rule 5, or starts with a digit: `Variable name "<n>" must start with a letter and use lowercase letters, digits and single hyphens`, fix `Use a name like "<slugify(n), with a leading v when it starts with a digit>"`.
  - A variable that is not a mapping: `Variable "<n>" must be a mapping with values`.
  - Unknown key: `Unknown key "<k>" in variable "<n>"`, fix from `didYouMean(k, ["values", "description", "default"])`.
  - Missing `values`: `Variable "<n>" is missing "values"`.
  - `values` an empty list or mapping, or neither: `"values" of "<n>" must be a non-empty list or mapping of value names`.
  - A value name that breaks rule 5 (a number such as `1` in YAML is not a string): `Value "<v>" of "<n>" must use lowercase letters, digits and single hyphens`.
  - A repeated value in a list: `Value "<v>" of "<n>" repeats`. (Repeated mapping keys are already a YAML duplicate-key error.)
  - A value entry that is neither null nor a mapping, an unknown key in it, or a `label` that is empty, not a string, or not single-line: `Value "<v>" of "<n>" must be null or { label: <text> }` / `Unknown key "<k>" in value "<v>"` / `"label" of value "<v>" must be a non-empty, single-line string`.
  - `default` not a value name or a non-empty list of value names: `"default" of "<n>" must be a value name or a non-empty list of value names`; a name not in `values`: `Default "<d>" of "<n>" is not one of its values`, fix from `didYouMean`. A repeated default name is deduplicated silently.
  - `description` empty, not a string, or not single-line: `"description" of "<n>" must be a non-empty, single-line string`.
- `FactoryYaml` is still built when `env` has errors (with the valid variables only), as `pipeline` is today, so other rules still run; the errors keep `build` from running.
- Aliases in `env` resolve through `resolveNode`, and count toward the existing alias limit.

### Selection (`src/core/env/select.ts`, `src/core/env/git-config.ts`, new)

```ts
export interface EnvConfigEntry { scope: GitConfigScope; variable: string; value: string }
export type EnvConfigReader = (root: string) => Promise<{ entries: EnvConfigEntry[]; warnings: Problem[] }>;

/** git config -z --show-scope --get-regexp ^factory\.env\., cwd = root, through `run` (runGit by default; tests inject a fake). */
export function createEnvConfigReader(run: typeof runGit = runGit): EnvConfigReader;
export const readEnvConfig: EnvConfigReader;   // createEnvConfigReader()

export function envVariableName(variable: string): string;   // FACTORY_ENV_ + upper case, "-" → "_"
export function splitValues(text: string): string[];          // comma split, trim, drop empty, dedupe

export interface ResolveOptions {
  root: string;
  options?: readonly string[];               // raw --env arguments
  processEnv?: NodeJS.ProcessEnv;            // default process.env
  readConfig?: EnvConfigReader;              // default readEnvConfig
}
/** Throws MetafabError (exit 1) for a bad --env; everything else is a warning. */
export async function resolveSelection(variables: readonly EnvVariable[], options: ResolveOptions): Promise<ResolvedSelection>;
```

`readEnvConfig` reads every scope in one call, with `-z`. Stdout is split on NUL only, never on newlines, into alternating records: a scope record, `<scope>\0`, then an entry record, `<key>\n<value>\0`. The first newline in the entry record ends the key and everything after it, newlines included, is the value. An entry record with no newline is a key with no value (`[factory "env"]` with a bare `harness` line) and gives no values. Verified with Git 2.50: `git config factory.env.harness amp`, then `--add` of `x<LF>y`, then a bare `workspace` key, gives exactly `local\0factory.env.harness\namp\0local\0factory.env.harness\nx\ny\0local\0factory.env.workspace\0`. An odd number of records, or output that does not end in NUL, is treated like any other unreadable output: one warning and no entries. The variable is the whole key after `factory.env.`, and Git has already lowercased it; a key with a further `.`, such as `factory.env.other.harness` (subsection `env.other`), names no variable and is skipped silently. Exit code 1 with no output means no keys: no entries. When `runGit` throws `ENOENT` (Git not installed), the result is empty with no warning (spec rule 5). Outside a repository Git still reads global and system config, so those entries count (spec rule 5, as amended). An `error: unknown option 'show-scope'` (Git before 2.26) gives one warning, `Git 2.26 or later is needed to read factory.env.* from Git config`, and no entries. Any other non-zero exit (a corrupt or unreadable config file) gives exactly one warning, `Cannot read factory.env.* from Git config: <Git's first stderr line>`, and no entries, so selection falls through to the default or every value; `readEnvConfig` never throws for a Git failure. A record in any scope other than `worktree`, `local`, `global` or `system` (such as `command`, from `git -c` or `GIT_CONFIG_COUNT`) is skipped silently.

`resolveSelection`, for each declared variable in declaration order, takes the first source that yields at least one declared value:

1. `--env`. Each argument must be `<variable>=<values>`: no `=` is an error, `--env needs <variable>=<values>: "<arg>"`; an undeclared variable is an error, `--env names unknown variable "<v>"`, fix `Declared variables: <list>` or `This factory declares no environment variables`, with a did-you-mean first when one is close; the same variable twice is an error, `--env names "<v>" twice`. All three exit 1 and are collected before throwing, so one run reports every bad argument.
2. `processEnv[envVariableName(name)]`.
3. Git config entries for the variable, from the highest-priority scope that has any: `worktree`, `local`, `global`, `system`. All entries of that scope are split and combined in order.
4. `default`.
5. Every value.

In sources 1 to 3, each value that the variable does not declare gives a warning, `Ignored "<value>" from <source>: harness does not declare it` (with `<source>` one of `--env harness=...`, `FACTORY_ENV_HARNESS`, `factory.env.harness in global Git config`), fix `Declared values: opencode, claude, amp`, and is dropped. When no declared value is left, the next source applies. Git config keys and `FACTORY_ENV_*` variables for undeclared variables are never read, so they cannot warn (spec rule 2). The selected values are returned in declaration order, so `claude,opencode` and `opencode,claude` give the same selection.

A factory with no variables (format 1, or `env: {}`) resolves to an empty selection without running Git. `--env` on such a factory is the unknown-variable error.

### Planner and check

```ts
export interface PlanBuildOptions { selection?: ResolvedSelection }
export async function planBuild(factory, config, cliVersion, options?: PlanBuildOptions): Promise<BuildPlan>;
```

`BuildPlan` gains `selection: ResolvedSelection`. When `options.selection` is absent and the factory declares variables, `planBuild` calls `resolveSelection(env, { root })`; the warnings join `plan.warnings`. When `factory.factoryYaml` is undefined (a broken `factory.yaml`), the selection is empty. Nothing else in `planBuild` reads the selection in this plan.

`runCheck(root, cliVersion, options?: { env?: readonly string[] })` resolves the selection after loading and passes it to `planBuild`. A bad `--env` throws before any problem is collected; `check` then exits 1 with only that error, as for a usage error.

### Commands (`src/commands/build.ts`, `check.ts`, `env.ts`; `src/cli.ts`; `src/help.ts`)

- `build` and `check` declare `env: { type: "string", multiple: true }`. `build` loads, stops on load errors as today (before reading `--env`), then resolves and plans. The body of `buildCommand.run` moves into an exported `runBuild(cwd, { env, json })` that `env set` and `env unset` reuse.
- `env` (`metafab env [--env <variable>=<values>]...`): finds and loads the factory, and exits 1 with the problems when any problem on `.factory/factory.yaml` is an error (other factory problems do not block it: it reads only `factory.yaml`). Then it resolves the selection, with `--env` as a preview, and reports it. Text, one line per variable, columns padded:

  ```text
  harness    opencode, claude   Git config (global)
  workspace  worktree           default in factory.yaml
  ```

  Source words: `--env`, `FACTORY_ENV_HARNESS`, `Git config (<scope>)`, `default in factory.yaml`, `every value (nothing selected)`. With no variables: `This factory declares no environment variables.` JSON: `variables` as the spec edit above says. Warnings go in `problems`. `env` never writes.
- `env set <variable>=<values> [--global]`: one positional; missing or malformed is an error naming the usage. The variable must be declared, and every value declared (refused, exit 1, with the declared values as the fix; spec). Without `--global` it first runs `git rev-parse --git-dir`; outside a repository it exits 1, `metafab env set needs a Git repository for repository config`, fix `Use --global, or set FACTORY_ENV_HARNESS`. When `git` is not installed it exits 1, `Git is not installed`, with the same fix minus `--global`. Then `git config [--global] --replace-all factory.env.<variable> <values>` through `runGit` (an argument list, never a shell; the value is one argument, so no quoting is involved). A non-zero exit (a locked or unwritable config file) exits 1 with Git's first stderr line, and nothing is built. Then `runBuild`. The result has `variable`, `values`, `scope` (`local` or `global`), and `runBuild`'s `changed`, `hooks`, `exitCode` and `problems`. When the build fails (exit 1 or 5), the Git config change stays, since it is valid on its own: the result is `ok: false` with the build's exit code and problems, plus one warning, `factory.env.<variable> changed, but the installed output was not rebuilt`, fix `Fix the problems above, then run metafab build`.
- `env unset <variable> [--global]`: `git config [--global] --unset-all factory.env.<variable>`. Git's exit 5 (the key is not set) is not an error: the summary says `factory.env.<variable> was not set in <repository|global> config` and the build still runs. Other errors as for `set`.
- Both warn when the value they wrote does not decide the selection: `FACTORY_ENV_<VAR> is set and overrides Git config`, or `factory.env.<variable> is also set in <scope> config, which takes priority` (for example a repository value after `set --global`, or a `worktree` value after `set`).
- `src/cli.ts` adds `envCommand`, `envSetCommand`, `envUnsetCommand` to `COMMANDS`. The token after `env` selects `env set` or `env unset` when it is exactly `set` or `unset`; otherwise `env` runs and the token is a positional, which `env` refuses with `Unknown env subcommand "<x>"` and a did-you-mean over `set` and `unset`. Unlike `pipeline`, `env` alone is a command. (Plan 2.003 turns the `pipeline` special case into a `GROUPS` list; `env` keeps this rule there.) `src/help.ts` gets the usage, arguments and option descriptions for the three commands and for `--env` on `build` and `check`, and `metafab env --help` lists `env set` and `env unset` under the usage.

### Format 2 fabs (`src/core/sources/validate.ts`, `types.ts`, `npm.ts`; `src/core/publish/package-json.ts`)

`detectFormat` accepts 1 and 2 from `package.json` and from `factory.yaml`, and `validateFab` returns the format it found (`ValidatedFab.format: 1 | 2`). `invalidFormat`'s fix becomes `Use format 1 or 2, or upgrade @seasb/metafab`; `checkNpmFormat` accepts 1 and 2 with the same fix. `FabPackageJson.metafab.format` becomes `1 | 2`; `buildPackageJson` already copies `factory.factoryYaml?.format`, and a test pins `2`. `loadFactory` then validates the fab, `env` included, so a fab with a bad `env` is refused with exit 4.

### Edge cases

- **CRLF and BOM** in `factory.yaml` are handled by the existing YAML reader; line numbers are unchanged.
- **Non-ASCII** values in Git config or `FACTORY_ENV_*` (`ämp`) are undeclared values: a warning, never a crash. Git output is read as UTF-8.
- **Case.** `Amp` is not `amp`: a warning with did-you-mean. Git lowercases variable names in keys, and declared names are lowercase, so `factory.env.Harness` reads as `harness`.
- **Windows.** `process.env` is case-insensitive there, so `factory_env_harness` also counts; that is the platform's behaviour and is documented in the test. Git config paths need no handling: Git reads them.
- **No terminal, CI.** Nothing prompts. A CI checkout with no config and no `FACTORY_ENV_*` selects every value, so CI's `build` then `check` agree.
- **Second run.** `env set` with the same values runs `--replace-all` again (no change) and the build reports `Up to date.`; `env unset` of an absent key is not an error.
- **Monorepo.** Two factories in one repository share `factory.env.*` keys; each reads only the variables it declares.
- **Hooks.** A hook runs `metafab build` with no `--env`, so it uses Git config and the process environment.

## Open questions
