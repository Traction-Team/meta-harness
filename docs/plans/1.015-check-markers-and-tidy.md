# Plan 1.015: `check` conflict markers and internals

`check` must fail while any file under `.factory/` has a conflict marker ([Sharing: Merge rules](../specs/sharing.md#merge-rules)). Two cases pass silently today: a marker after a UTF-8 byte order mark (BOM), and a marker in a text file that is not UTF-8. Plan 1.010 makes conflict markers a normal part of `update`, so these gaps should close first. This plan also removes three duplications from PR #9 that would let `check` and `build` drift apart. After it merges, `check` finds every marker whatever the encoding, walks `.factory/` once, and reports stale installs in every destination correctly.

## Specs

- [Sharing: Merge rules](../specs/sharing.md#merge-rules)
- [Building: Ownership](../specs/building.md#ownership)
- [Building: Built-in `metafab` skill](../specs/building.md#built-in-metafab-skill): `check` detects an outdated built-in skill
- [Building: Repeatability](../specs/building.md#repeatability): one `Cannot read <path>` per unreadable path

## Decisions

| Topic | Choice | Reason |
| --- | --- | --- |
| Binary detection | Keep the NUL probe on the first 8 KiB as the only test. A file that fails UTF-8 decoding is text | The marker prefixes are ASCII, so a lenient decode finds them in any ASCII-compatible encoding. UTF-16 files contain NUL bytes and stay binary |
| BOM | Strip one leading U+FEFF before splitting into lines | `<<<<<<< ` on line 1 after a BOM is a real marker |
| Where `cliVersion()` lives | `src/util/version.ts`, used by `build` and `check`. `src/core/init/run.ts` keeps its copy until Plan 1.016, which owns that file | Keeps this plan's `owns` clear of Plan 1.014 |

## Design

### Markers (`src/core/check/markers.ts`)

- Replace the fatal decoder with `new TextDecoder("utf-8", { fatal: false, ignoreBOM: false })`. With `ignoreBOM: false` the decoder removes a leading BOM. Invalid bytes become U+FFFD and do not affect the ASCII marker prefixes.
- `readTextFile` returns `binary` only when the NUL probe finds a NUL.
- One walk: export `scanFactoryFiles(root): Promise<Problem[]>`. It calls `walkFactoryFiles` once and runs both scanners over the same file list. Walk read problems are reported once. `scanConflictMarkers` and `scanUpstreamFiles` become internal helpers that take the walk result. Update `src/core/check/index.ts` to call and re-export the single entry point instead of the two old ones. Problem order stays the same: walk read problems and markers first, then `.upstream` files. `test/core/check/markers.test.ts` imports the old two functions today. Rewrite it to use `scanFactoryFiles`, keeping every existing case.

### Destinations (`src/core/check/drift.ts`)

`SKILL_DIRECTORIES` becomes `destinations([...TARGETS]).map((d) => d.directory)`, so a new target with a new directory is covered without editing `check`. Today this gives the same two directories, so the change guards a future target and does not alter behaviour. Export `SKILL_DIRECTORIES`, and test that it equals `destinations([...TARGETS]).map((d) => d.directory)`.

### `cliVersion()` (`src/util/version.ts`)

```ts
export function cliVersion(): string
```

It reads the package's own `package.json` through `createRequire` with the specifier `../../package.json`, which is right from both `src/util/` and `dist/util/`. It falls back to `"0.0.0"` as today. The unit test covers only `src/`, so also check that `node dist/cli.js build` writes the real version into the built-in skill's comment. `src/commands/build.ts` and `src/commands/check.ts` import it and drop their copies.

## Tests

- A file starting with a BOM and then `<<<<<<< HEAD` is reported at line 1
- `café\n<<<<<<< ours\n` saved as ISO-8859-1 is reported at line 2
- A file with a NUL in its first 8 KiB is still skipped as binary
- A UTF-16LE file with a BOM is skipped as binary (it has NUL bytes)
- An unreadable directory under `.factory/` (chmod 000; skipped on Windows and as root) gives exactly one `Cannot read` problem, and a `.upstream` file beside it in a readable directory is still reported
- A stale owned skill in `.agents/skills/` while only `claude` is selected reports "installed for an agent tool that is no longer configured", and the same holds the other way round. This is a regression guard; it passes before the change too
- `cliVersion()` equals the `version` in `package.json`
- Every existing case in `test/core/check` still passes. `markers.test.ts` is rewritten to call `scanFactoryFiles`, with the same expectations
