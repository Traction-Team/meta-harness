# Plan 1.021: Harden fab sources and accept `git+file://`

`metafab publish` can write to a local bare repository (`publish.git: file:///…/fab.git`), but `metafab import` cannot read one back: `git+file:///…` falls through to the npm name parser and fails with an npm error. This plan makes `git+file:///<absolute path>` a Git source with tags, ranges, `update` and `diff`, exactly like `git+https://`, and gives every other unsupported URL scheme a clear error that lists the supported forms. It also closes the fab-source gaps the Plan 1.008 reviews left (moved here from Plan 1.012): the Git mirror and the cache no longer leave temporary directories behind or delete each other's entries when two commands run at once, a cache Metafab cannot write gives exit 3 instead of a stack trace, an oversize npm package is refused before it is downloaded, and `extractTarball` flattens when asked to strip a prefix too. After it merges, a person can try publish, import and update on one machine with no remote, and the source layer behaves the same under concurrency, a full disk and an interrupted run.

From intake: *import cannot read a local Git repository that publish can write*, Sebastian, end-to-end trial of publish, import and update in a scratch repository, 12 Nov 2026. Every fact from that note is carried below.

From Plan 1.012, Hardening: the five "remaining fab source gaps found in the Plan 1.008 reviews (PR #6)" and "Confirm `npm pack --ignore-scripts` runs no scripts on npm 9 and 10, or set an `engines` minimum". The intake note, the moved 1.012 steps and owns, and the roadmap line are handled at planning time, not by this pull request.

- The "Other Git repository" row's example becomes `` `git+ssh://git@example.com/fab-acme.git`, `git+https://example.com/fab-acme.git` or `git+file:///srv/fabs/fab-acme.git` ``.
- After the paragraph that starts "Metafab also reads `ssh://` URLs", add:

  > `git+file:///<absolute path>` names a Git repository on this machine or on a mounted share, such as the bare fab repository `publish.git: file:///…` writes. It works exactly like `git+https://`: version tags, ranges, refs, `update` and `diff`. The path must be absolute: three slashes (`git+file:///srv/fabs/fab-acme.git`), `localhost` (`git+file://localhost/srv/fabs/fab-acme.git`), or on Windows a drive after two or three slashes (`git+file:///C:/fabs/fab-acme.git` or `git+file://C:\fabs\fab-acme.git`). Encode a `#` in the path as `%23`, because `#` starts the ref. The recorded `source` is the URL as written, so it names a path on this machine. Metafab reads only committed content: uncommitted edits in a working tree are not part of the fab. A source with `file:` and no `git+` is a local path: it reads `.factory/` from a working tree and never sees tags.
  >
  > Any other URL scheme, such as `http://`, `git://`, `git+http://` or `ftp://`, is refused with exit code 1 and a message that lists the supported forms. A local path that is a bare Git repository is refused with exit code 3 and a message that names its `git+file://` form.

- After the paragraph "Metafab fetches Git sources with Git…", add:

  > Metafab downloads an npm fab with `npm pack <name>@<version> --ignore-scripts`. In npm 9.6.4, 10.9.2 and 11, the versions checked, `npm pack` runs lifecycle scripts only for a local directory, never for a registry package, and `--ignore-scripts` turns those off as well. A test pins this on the npm that CI runs. Before the download, Metafab reads the package's reported size and file count from the registry (`dist.unpackedSize` and `dist.fileCount`) and refuses a package that reports more than the [fab limits](#importing-a-fab) with exit code 4. A package that reports less than it holds is still refused after the download. The recorded version that `update` downloads as its base, and that `diff` compares with, skips the reported-size check, because it was accepted once; the checks after the download still apply.
  >
  > Downloads are cached in `~/.metafab/cache/` (`METAFAB_CACHE` overrides it). Commands that run at the same time can share the cache: each download is written to a temporary entry next to its final place and then renamed into place, so one command never removes or reads another's partial entry. A temporary entry an interrupted command leaves behind is removed by a later command after 24 hours. A cache Metafab cannot write, for example because of its permissions or a full disk, stops the command with exit code 3 and names the cache path, before the repository changes.

## Decisions

Agreed with the person on 2026-11-12:

| Topic | Choice | Reason |
| --- | --- | --- |
| Local Git sources | Accept `git+file:///path/repo.git` as a Git source with tags and versions exactly like `git+https://` | A versioned fab in a local or network-share repository could not be imported, and publish, import and update could not be tried without a remote. The trial had to rewrite a `git+https://` source with `GIT_CONFIG_*` `url.<file-url>.insteadOf` |
| Other URL schemes | Any other unsupported URL scheme gets a clear error that lists the supported forms, not the npm package-name error | `Invalid source "git+file:///…": name can only contain URL-friendly characters` told the person nothing |

Made in this plan:

| Topic | Choice | Reason |
| --- | --- | --- |
| `git+file://` path forms | Accept an empty host (`git+file:///abs`), `localhost`, and a Windows drive right after `//` or `///` (`git+file://C:\fabs\x.git`, `git+file:///C:/fabs/x.git`). Refuse any other host and any relative form (`git+file:../x.git`) | Git accepts exactly these (checked with Git 2.50: `file://localhost/…` and `%20` both work). A relative path would make the recorded source depend on the current directory, and `update` re-parses it later from another one |
| What Git is given | `file://` plus the text after `git+file://`, unchanged (scheme lower-cased, as `parseGitUrl` does). `source` is the input as typed | Git decodes `%20` and accepts a raw space itself; re-serialising through `new URL()` would change the recorded source and the mirror key (the reason `stripSourceCredentials` cuts text instead of re-serialising) |
| `git://`, `http://`, `git+http://` | Not added; refused with the supported-forms error, with a hint (`use https://`, `use git+https://`, `use git+https:// or git+ssh://`) | Unauthenticated, unencrypted transports. The spec never listed them |
| A path source that is a bare repository | Refused (exit 3, as a path with no `.factory/` is today) with a message naming the `git+file://` URL to use | The trial's first attempt was a plain `file:///…/fab.git`; the old message only said `.factory` does not exist |
| `publish.git` with `git+` | Strip the prefix before Git sees it (`gitTransportUrl`). Today `check` accepts `git+https://` but `git clone` fails: `git: 'remote-git+https' is not a git command` (checked with Git 2.50) | `check` and `publish` must agree, and people will paste the import form |
| Import line in a generated README | `importSourceForGitUrl(publish.git)`: `https://` → `git+https://`, `file://` → `git+file://`; every other form unchanged | Today a fab published to `https://github.com/x/fab.git` gets a README telling people to `import https://…`, which `import` reads as an HTTPS tarball |
| Cache entries | `getOrCreate` builds into `<target>.tmp-<uuid>`, validates it, then renames it into place. It never deletes a target it did not create, except a complete entry that fails validation | Today a failed `create` runs `rm(target)`, so two concurrent imports can delete each other's entry, and a failing `rm` replaces the original error |
| Git mirror | Every clone, first or replacement, goes to `<mirror>.tmp-<uuid>` and is renamed into place. Removing the old backup is best effort | An interrupted first clone left a partial mirror at the real path; a failed `rm` of the backup threw after the swap had succeeded |
| Stale temporary entries | Siblings named `<name>.tmp-*` or `<name>.old-*` older than 24 hours are removed, best effort, before each create | A concurrent command's in-progress clone must not be deleted; 24 hours is far longer than any clone and only costs disk |
| Cache write failures | Every filesystem call that writes the cache in the Git and npm fetch paths is wrapped: one `fetch-failed` problem, exit 3, naming the path | `mkdir` and `rename` threw EACCES/ENOSPC as internal bugs (exit 1, stack trace) |
| npm size cap | Check `dist.unpackedSize` against `MAX_FAB_TOTAL_SIZE` and `dist.fileCount` against `MAX_FAB_ENTRIES` from `npm view` before `npm pack`; keep the check after `npm pack`; when `npm pack` fails and its staging tarball is already over the cap, report the size error | npm 9 and 10 (`libnpmpack`) hold the whole tarball in memory and write it with one `writeFile`, after writing it to npm's own cache, so a check while it writes cannot stop it. Registry metadata is the only early signal. A registry that understates it is still caught after the download, as today |
| npm scripts and `engines` | No `engines.npm`. `engines.node` stays `>=20` | Read on 12 Nov: `workspaces/libnpmpack/lib/index.js` in npm v9.6.4 (the npm Node 20.0 ships) and v10.9.2 runs `prepack`/`postpack` only when `spec.type === 'directory' && !opts.ignoreScripts`; a registry `name@version` spec is type `version`, and `pacote.tarball` for a registry spec runs no scripts. npm 11 was checked in Plan 1.008. `engines.npm` only warns anyway. A test pins it on the npm the CI matrix runs (Node 20 and 22 ship npm 10) |
| Long cache keys | `fabKey` keeps keys up to 120 characters as today; a longer key becomes its first 80 characters, `-`, and the first 32 hex characters of the SHA-256 of the whole key (all 120+ characters, not the part after the first 80) | A `git+file://` source carries a whole local path into the fab directory name. The key is `FAB_FETCH_FORMAT` (25 characters: `git-verbatim-` and 12 hex), `-`, the source, `-` and the 40-character commit, so 67 characters plus the source: a source over 188 characters passes the 255-byte name limit (`ENAMETOOLONG`), and on Windows the cache path nears 260 characters sooner. Existing short keys are unchanged, so existing caches still hit |
| `extractTarball` with both options | `singleTopDirectory` is given the extra `strip` only, not the prefix segments again | It strips the prefix, then strips its segments a second time, so it looks one level too deep and never flattens. No caller passes both today, so this is latent |

## Design

### Parsing (`src/core/sources/parse.ts`)

Today (`parse.ts:202`) any `file:` prefix is a path source, and `:221`-`:222` accept only `git+ssh://` and `git+https://`; `git+file://` falls through to `splitNpm` and its npm name error.

- New `parseGitFileUrl(input: string): SourceSpec`, called when `/^git\+file:/i` matches, before the `file:` branch (which matches only `file:`, so the order is for clarity). It splits the ref with `splitRef`, takes `rest = base.slice("git+file:".length)`, and:
  - `rest` must start with `//`. Otherwise `invalidSource(input, "a Git file URL must be absolute, such as git+file:///srv/fabs/fab.git")`.
  - After `//`, accept: `/` (an absolute POSIX path or `/C:/…`), `localhost/` (case-insensitive), or `DRIVE_PATH` (`C:\` or `C:/`). Anything else is a host: `invalidSource(input, "a Git file URL cannot name a host; use git+file:///<absolute path>")`. `git+file:///` with nothing after is `"the Git file URL has no path"`.
  - Returns `{ kind: "git", url: "file:" + rest, source: base, ref? }`.
- New `unsupportedScheme(input, scheme)`: after every known form and before `splitNpm`, a value matching `/^([A-Za-z][A-Za-z0-9+.-]*):/` is refused. The scheme is lower-cased before it picks a hint, so `HTTP://` gets the `http` hint; the message quotes it lower-cased. An npm name never contains `:`, and `isScpGit` and `isPathLike` have already claimed `git@host:path` and `C:\…`/`C:/…`. The message is `Invalid source "<redacted input>": unsupported URL scheme "<scheme>:". Supported sources: an npm name, github:owner/repo, git+https://, git+ssh://, ssh://, git@host:path, git+file:///<path>, an https:// tarball, or a local path`, followed by a hint for `http` (`Use https:// for a tarball or git+https:// for a Git repository`), `git` and `git+http` (`Use git+https:// or git+ssh://`). A one-letter scheme (`C:fab`) gets `a Windows path needs a slash after the drive, such as C:\fabs\acme` instead. Code `invalid-source`, exit 1, as every parse error. Unlike `invalidSource`, this error carries one problem `{ level: "error", file: "<redacted input>", message, fix }` so the CLI prints a fix line: `Use git+https://, git+ssh://, git+file://, ssh://, user@host:path or github:owner/repo for a Git repository, an https:// URL for a tarball, an npm name, or a local path` (the one-letter case: `Write the path as C:\fabs\acme or C:/fabs/acme`).
- New exports used by publish:

  ```ts
  /** The URL to hand to Git: `git+https://`, `git+ssh://` and `git+file://` lose `git+`. */
  export function gitTransportUrl(url: string): string;
  /** The source `import` accepts for a URL Git accepts: `https://` and `file://` gain `git+`. */
  export function importSourceForGitUrl(url: string): string;
  ```

  Both change only the scheme text and keep the rest byte for byte. `gitTransportUrl` also lower-cases the scheme, as `parseGitUrl` does, because Git compares it case-sensitively: `GIT+HTTPS://Example.com/Fab.git` becomes `https://Example.com/Fab.git`. A URL with no `git+` prefix is returned with only its scheme lower-cased; an scp URL is returned unchanged.
- `src/core/config/source.ts` needs no change: `classifySource` calls `parseSource`, and its fallback already treats `git+` as Git. A test pins `classifySource("git+file:///srv/fab.git") === "git"`.

### Git fetch, update and diff (`src/core/sources/git.ts`)

Nothing in `resolveGit`, `selectRef` or `fetchGit` depends on the transport. `update` (`src/core/update/fetch.ts:38`, `select.ts:60`, `run.ts:1108`) and `diff` re-parse the recorded `source`, so once `parseSource` reads `git+file://`, version resolution, `--to`, base download and `diff` work unchanged. The round-trip test proves it. Git's own rules still apply and pass through as `fetch-failed`, exit 3, with Git's message: a missing path (`does not appear to be a git repository`), `protocol.file.allow=never`, `safe.directory` refusing a repository another user owns. `git clone --mirror` of a `file://` URL copies objects (no hard links), so the mirror never shares files with the source.

Mirror handling:

- `cloneMirror(url, mirror, options)` clones into `<mirror>.tmp-<uuid>`, rewrites `origin`, then `installMirror(temporary, mirror)`: `rename(temporary, mirror)`. If the rename fails because `mirror` now exists (`EEXIST`, `ENOTEMPTY`, or on Windows `EPERM`/`EBUSY` with `mirror` present), another command won the race: remove the temporary clone (best effort) and use `mirror` when `isUsableMirror`, else throw `fetch-failed`. Any other failure removes the temporary clone and throws `cacheWriteError(mirror, error)`.
- `replaceMirror` clones the same way, renames `mirror` to `<mirror>.old-<uuid>`, renames the clone into place, and on success removes the backup with `.catch(() => undefined)`: a failed removal never fails a swap that worked. If the first rename fails, the clone is removed and `cacheWriteError` is thrown; if the second fails, the backup is renamed back (best effort) and `cacheWriteError` is thrown.
- `ensureMirror` first calls `sweepStale(path.dirname(mirror), path.basename(mirror))`.
- `exportFactory` takes the staging directory `getOrCreate` gives it (below) instead of `rm`/`mkdir` on `fabDir`; it no longer calls `mkdir` itself. The staging directory is created by `extractTarball`'s own `mkdir(destination, { recursive: true })` (`extract.ts:576`). `mkdtemp` for the archive, `mkdir(<cache>/git)` and every rename are wrapped with `cacheWriteError` (or `fetchError` for the system temp directory, naming it).
- `ExtractTarballOptions` gains `writeError?: (target: string, error: unknown) => MetafabError`. When it is set, `extractTarball` passes a failure of its `mkdir(destination)` to it, and also an extraction failure whose `code` is `EACCES`, `EPERM`, `ENOSPC`, `EROFS` or `EDQUOT` (tested by a new exported `isCacheWriteFailure(error)`), instead of `tarballError` (exit 4). Without it, behaviour is unchanged, so `fetchHttps` and path sources still report as today. `exportFactory` and `fetchNpm` pass `(target, error) => cacheWriteError(target, layout.root, error)`, so a full or read-only cache during extraction is exit 3, not "Cannot extract" exit 4.

### Cache (`src/core/sources/cache.ts`)

```ts
export interface GetOrCreateOptions<T> {
  validate: (dir: string) => Promise<T>;
  create: (staging: string) => Promise<void>;
}
/** Removes `<name>.tmp-*` and `<name>.old-*` siblings older than 24 hours. Best effort. */
export async function sweepStale(parent: string, name: string, now?: number): Promise<void>;
/** One `fetch-failed` problem naming the path, exit 3. */
export function cacheWriteError(target: string, root: string, error: unknown): MetafabError;
```

`getOrCreate(target, options)`:

1. If `target` exists, `validate(target)`. On success return it. On failure the entry is complete but wrong (renames are atomic, so it is never partial): remove it, best effort, and carry on.
2. `sweepStale`, then `staging = <target>.tmp-<uuid>`; `create(staging)`, then `validate(staging)`. On failure remove `staging` (best effort, `.catch(() => undefined)`) and rethrow the original error.
3. `rename(staging, target)`. When it fails because `target` now exists (`EEXIST`, `ENOTEMPTY`, or `EPERM`/`EBUSY` with `target` present), another command won: remove `staging`, then `validate(target)` and return it. For a file target (`npmTarball`), POSIX `rename` replaces the file, which is safe because both have passed the integrity check. Any other rename failure removes `staging` and throws `cacheWriteError(target, error)`.

`validate` must accept the directory it is given: the closures in `fetchGit` and `fetchNpm` move from the captured `fabDir` to their argument. `validate` still returns the final path, not the staging path, so callers keep using `layout.fabFactoryDir(key)`.

`cacheWriteError` message: `Cannot write the Metafab cache: <code>: <path>`; problem `{ level: "error", file: toPosixPath(<path>), message, fix: "Free disk space or make <root> writable, or set METAFAB_CACHE to a writable directory, then run the command again" }`; code `fetch-failed`; exit 3. `root` is the cache root: every caller has `layout.root` from `cacheLayout` (`fetchGit`, `resolveGit` through `ensureMirror`, `fetchNpm`, `fetchNpmTarball`), and passes it down to `cloneMirror`, `replaceMirror`, `exportFactory` and `downloadTarball`. `getOrCreate` gains a `root` field in its options for the same reason. In the calls above, `cacheWriteError(x, error)` is shorthand for `cacheWriteError(x, layout.root, error)`. The repository is unchanged: `import` and `update` fetch before their first write.

`fabKey` caps long keys as in Decisions. `keySegment` is unchanged.

### npm (`src/core/sources/npm.ts`)

- `readManifest` also returns `unpackedSize?: number` and `fileCount?: number` from `dist` when they are non-negative integers; `ResolvedNpm` carries them.
- `ResolveNpmOptions` gains `recorded?: boolean`. When it is true, `resolveNpm` leaves `unpackedSize` and `fileCount` off the result, so `downloadTarball` skips the pre-check. `resolveRecorded` in `src/core/update/fetch.ts` passes `recorded: true` for an npm upstream, so `update`'s base download and `diff` skip it: the recorded version was accepted once, and a registry that later reports a larger size must not make the base look gone. The size check after `npm pack` and the extraction limits still apply. `update`'s new-version resolution does not pass it and is checked as `import` is.
- `downloadTarball` checks them first: over `options.maxTotalSize ?? MAX_FAB_TOTAL_SIZE` gives `Cannot download npm package "<name>@<version>": it unpacks to <n> bytes, more than the <limit>-byte fab limit`; over `MAX_FAB_ENTRIES` gives `... it has <n> files, more than the <limit>-file fab limit`. Both are `invalid-fab`, exit 4, before `npm pack` runs. `NpmOptions` gains `maxTotalSize?: number` as a test seam, like `maxTarballSize`.
- When `npm pack` fails and a `.tgz` in the staging directory is already over `maxBytes`, throw `tarballTooLarge` instead of the npm error.
- `mkdir(path.dirname(target))` and the `copyFile` into the cache use `cacheWriteError`; the copy goes to the staging path `getOrCreate` gives.
- The test `does not run install scripts from a package` grows: the `fab-scripts` fixture also declares `preinstall`, `postinstall`, `prepare`, `prepack` and `postpack`, each writing a marker into a directory whose absolute path the test passes in an environment variable, and the test asserts the directory stays empty.

### `extractTarball` (`src/core/sources/extract.ts`)

At `extract.ts:553`, call `singleTopDirectory(entries, prefix, options.strip ?? 0)`, since `singleTopDirectory` strips the prefix itself (`prefixedPath`) and `strip` already counts the prefix segments (`extract.ts:548`).

### Path sources (`src/core/sources/path.ts`)

`locateFactoryDir`: when `.factory` is missing and `specPath` holds a `HEAD` file and `objects/` and `refs/` directories, the message becomes `Cannot read local fab "<path>": it is a bare Git repository. Import it as git+<pathToFileURL(specPath).href>`. Still `fetch-failed`, exit 3.

### Publish

- `gitUrl` in `src/core/publish/git-target.ts` returns `gitTransportUrl(publish.git)`. Every Git call (`clone`, `ls-remote`, `push`) uses it; messages keep using `stripSourceCredentials` of that URL.
- `publishSource` in `src/core/publish/readme.ts` returns `importSourceForGitUrl(stripSourceCredentials(publish.git))` when there is no npm name.
- `GIT_URL` in `src/core/config/validate.ts` gains `(?:git\+)?file:\/\/`; the fix line becomes `Use git@host:path, ssh://, git+ssh://, https://, git+https://, file:// or git+file://.`

### Edge cases

- **Windows**: `git+file:///C:/…` and `git+file://C:\…` both parse; Git for Windows accepts the `file://` text it is given. The round-trip test builds its source with `pathToFileURL`. Renames that lose a race report `EPERM` on Windows, which `getOrCreate` and `installMirror` treat as a lost race only when the target exists. The `fabKey` cap keeps the cache path short.
- **CRLF**: no change; Git fetches stay byte-exact (Plan 1.018).
- **No terminal, `--json`**: nothing here prompts; `GIT_TERMINAL_PROMPT=0` already applies. Errors appear in the JSON `problems` as today.
- **A second run**: the mirror and fab entry are reused; `update` fetches into the existing mirror.
- **An interrupted run**: no cache path is ever partial, because every entry and mirror is renamed into place; temporary siblings are swept after 24 hours. `import` and `update` have not written to the repository before the fetch finishes.
- **No Git**: `execFile("git")` fails with `ENOENT`, reported as today as `fetch-failed`, exit 3, with the spawn message.
- **No network**: a `git+file://` source needs none.
