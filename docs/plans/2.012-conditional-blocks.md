# Plan 2.012: When and switch blocks and conditional skills compile for the selected environment

After Plan 2.011 a factory can declare `env` variables and every build knows the developer's selection, but the output is the same for everyone. This plan makes it differ. In a format 2 factory, `<!-- factory:when ... -->` and `<!-- factory:switch ... -->` blocks in any skill's Markdown and in `.factory/AGENTS.md` are rendered: a developer on one harness gets that harness's text and nothing else, and a developer on two gets both, each after a label line. `skills:` in `factory.yaml` installs a whole skill only where its condition can be true. `metafab check` validates every directive, every condition and every switch over every branch, whatever the local selection is, so every selection compiles. The root `AGENTS.md` block is rendered for every value, so it stays identical for everyone. Imports arrive in Plan 2.013.

## Decisions

Agreed with the person:

| Topic | Choice | Reason |
| --- | --- | --- |
| Keywords | `when`/`endwhen`, `switch`/`case`/`default`/`endswitch` | Plain words; not "include", which reads like file inclusion |
| Partially matching blocks | Kept, after a label line | A developer who uses two harnesses needs both texts and to know which is which |
| One file with a `switch`, exhaustive | Not per-harness files; a switch without `default` must name every value | Variants stay side by side; adding a value lists every switch to update |
| Directives in `.factory/AGENTS.md` | Allowed; rendered for every value | The committed root block must be identical for everyone |
| Frontmatter | No directives in frontmatter; skill descriptions stay harness-neutral | A skill's name and description are its discovery metadata and must not vary |
| `check` and selections | No compile of every selection; static validation of every branch | Rules 1 to 4 and 6 cover every branch, so every selection compiles |

Proposed in this plan, for approval:

| Topic | Choice | Reason |
| --- | --- | --- |
| Where validation runs | `environmentProblems(factory)` from `loadFactory` | `build`, `check`, fab validation on `import` and `update`, and publish's staged validation all reject a broken directive, as Plan 1.023's rule 13 does |
| Which files are rendered | Files whose extension, lowercased, is `.md` | `NOTES.MD` behaves like `notes.md` on every file system |
| Fence detection | A line whose first non-blank characters are three or more backticks or tildes opens a fence at any indentation; it closes on a line of the same character, at least as long, with nothing else but blanks | Safer than CommonMark's three-space limit: a directive in a fence inside a list item is never live. An unclosed fence runs to the end of the file, as in CommonMark |
| A directive-looking line that is not a whole directive | A line whose first non-blank text is `<!-- factory:` but that does not match the directive form (no `-->`, text after it) is an error | It would otherwise leak into installed output as a broken comment |
| Label line indentation | The label line takes the leading whitespace of the opening directive line | A labelled block inside a list item stays inside the item |
| Scenario count | Scenarios range only over the variables named in the block's own condition and its enclosing conditions; a block whose variables span more than 1024 combinations of declared values is an error (spec amended) | Other variables cannot change the result, and the bound keeps rendering and the all-values root block cheap however many variables a factory declares |
| `map` | Unchanged in this plan | See Open questions |

## Design

### Directive scanner and parser (`src/core/env/directives.ts`, new)

```ts
export type Node =
  | { kind: "text"; line: number; text: string }
  | { kind: "when"; line: number; indent: string; condition: Condition; children: Node[]; endLine: number }
  | { kind: "switch"; line: number; indent: string; variable: string; branches: Branch[]; endLine: number };
export interface Branch { kind: "case" | "default"; line: number; indent: string; values: string[]; children: Node[] }
export interface MarkdownDocument {
  file: string;                 // repository-relative, for problems
  nodes: Node[];
  problems: Problem[];
  /** Variables any condition or switch in the document names. */
  variables: ReadonlySet<string>;
}
export interface ParseOptions {
  file: string;
  /** Line number of the first line of `text` in the source file (the body of SKILL.md starts after its frontmatter). */
  firstLine: number;
  variables: readonly EnvVariable[];
}
export function parseMarkdown(text: string, options: ParseOptions): MarkdownDocument;
/** Lines that are directives, outside fences: for format 1's warning and the frontmatter rule. */
export function directiveLines(text: string, firstLine?: number): number[];
```

Text arrives LF-normalised (`toLF` already runs in `addFile` and `loadFactory`). A BOM on the first line is kept in the output, as today, and ignored when matching.

A directive line matches `^[ \t]*<!--[ \t]*factory:([A-Za-z0-9_-]*)(?:[ \t]+(.*?))?[ \t]*-->[ \t]*$`. A line whose first non-blank text is `<!-- factory:` (any spacing after `<!--`) and that does not match is `A factory: directive must be one whole line: <!-- factory:<name> <arguments> -->`. Lines inside a fence are never directives.

Errors, each on its line, with file and fix:

| Case | Message | Fix |
| --- | --- | --- |
| Unknown name | `Unknown directive "factory:<n>"` | did-you-mean over the seven names, else `Use when, endwhen, switch, case, default, endswitch or import` |
| `start` or `end` | `factory:<n> marks the generated block in the root AGENTS.md and cannot appear in source` | `Remove the line` |
| `import` (until Plan 2.013) | `factory:import is not supported yet` | `Copy the text in for now` |
| `when` with no condition | `factory:when needs a condition` | `Write <!-- factory:when env.<variable> == <value> -->` |
| Bad condition | `Cannot read condition "<c>": <reason>` | `Write env.<variable> == <value>, != <value> or in [<values>], joined with and, or, not and parentheses` |
| Unknown variable or value | `Condition names unknown variable "<v>"` / `Condition names unknown value "<x>" of <v>` | did-you-mean, else the declared names |
| Arguments on `endwhen`, `default`, `endswitch` | `factory:<n> takes no arguments` | `Remove "<args>"` |
| `switch` argument | `factory:switch needs env.<variable>` | |
| `endwhen` / `endswitch` with nothing open | `factory:<n> has no matching factory:<opener>` | `Remove the line` |
| `endwhen` closing a switch, or `endswitch` closing a when | `factory:<n> cannot close the factory:<other> on line <l>` | `Close the inner block first` |
| Open at end of file | `factory:<n> on line <l> is never closed in this file` (on line `l`) | `Add <!-- factory:end<n> --> in the same file` |
| `case` or `default` not directly in a switch | `factory:<n> must be directly inside a factory:switch` | |
| Text between `switch` and first `case` | `Only blank lines may come between factory:switch and its first case` | `Move the text into a case` |
| `case` with no values, or a bad value name | `factory:case needs one or more value names separated by spaces` | |
| Value not declared | `factory:case names unknown value "<x>" of <v>` | did-you-mean |
| Value in two cases | `Value "<x>" already has a case on line <l>` | `Remove it from one case` |
| `case` after `default`, or a second `default` | `factory:default must be the last branch of its switch` | |
| Variables of a block and its enclosing conditions span more than 1024 combinations of declared values (for a switch branch, the switch's variable counts) | `Condition spans too many combinations: <n> over <variables>; the limit is 1024` (on the directive line) | `Split the condition, or nest fewer conditions` |
| Switch without `default` missing values | `factory:switch over env.<v> has no case for <x>, <y>` (on the switch line) | `Add a case for each, or a factory:default` |
| Unclosed fence followed by directive lines | warning: `The code fence on line <l> is never closed, so the directive lines after it are text` | `Close the fence` |

One problem per line; after an error the parser keeps going, treating the bad line as text, so one run reports every problem in a file.

### Conditions (`src/core/env/condition.ts`, new)

```ts
export type Condition =
  | { kind: "test"; variable: string; values: string[]; negate: boolean }   // == is in [v]; != is not in [v]
  | { kind: "not"; operand: Condition }
  | { kind: "and" | "or"; operands: Condition[] };
export function parseCondition(text: string): { condition: Condition } | { error: string };
export function conditionProblems(condition: Condition, variables: readonly EnvVariable[]): string[];
export function evaluate(condition: Condition, scenario: ReadonlyMap<string, string>): boolean;
export function conditionVariables(condition: Condition): Set<string>;
```

The tokenizer follows the spec's Conditions section as amended: it reads `(`, `)`, `[`, `]`, `,`, `==`, `!=` as tokens whether or not whitespace surrounds them, and a word (`and`, `or`, `not`, `in`, a name, `env.<name>`) ends at whitespace or at one of those symbols, so `env.h==amp`, `not(env.h in[a,b])` and `env.h == amp` read the same, and `env.h==ampand` is one name, `ampand`; names and `env.<name>` follow the name rules, and `and`, `or`, `not`, `in` are keywords only where the grammar expects one, so a value may be named `in`. Precedence is `not` over `and` over `or`. Errors: an empty condition, a trailing operator, `in []`, a trailing comma, an unclosed `(` or `[`, `=` instead of `==`, `env.` with no name, and leftover tokens, each as `<reason> at "<token>"`.

### Scenarios and labels (`src/core/env/scenarios.ts`, new)

```ts
export type Scenario = ReadonlyMap<string, string>;
export const MAX_COMBINATIONS = 1024;
export function scenarios(selection: EnvSelection, variables: Iterable<string>): Scenario[];   // product, declaration order
/** Product of the declared value counts of `variables`: the all-values case, independent of the selection. */
export function combinations(variables: Iterable<string>, declared: readonly EnvVariable[]): number;
export type Applies = { kind: "all" } | { kind: "none" } | { kind: "some"; label: string };
/** `enclosing` are the conditions of the blocks around this one, outermost first. */
export function classify(condition: Condition, enclosing: readonly Condition[], selection: EnvSelection, variables: readonly EnvVariable[]): Applies;
export function allValues(variables: readonly EnvVariable[]): EnvSelection;
```

`classify` enumerates `scenarios(selection, V)`, where `V` is the variables that `condition` and every condition in `enclosing` name, keeps the scenarios in which every enclosing condition is true (the context), and then those in which `condition` is also true: `none` when none is, `all` when every context scenario is, else `some`. No other variable is enumerated, so the work per block is at most `MAX_COMBINATIONS` scenarios: the parser reports the error in the table above when `combinations(V, env)` exceeds it, so the bound holds for every selection, including the all-values root block, and a document with that error is never rendered. The label follows the spec's Rendering section exactly, including the amended rule for variables with every value and an `or` across variables: variables in `env` order, values in `values` order, ` or ` within a variable, `, and ` between variables. Each value contributes its `EnvValue.label`.

### Rendering (`src/core/env/render.ts`, new)

```ts
export interface RenderContext { variables: readonly EnvVariable[]; selection: EnvSelection }
export function renderDocument(document: MarkdownDocument, context: RenderContext): string;
```

Rendering walks the tree with the list of enclosing conditions. A `when` is classified with `classify(condition, enclosing, ...)`; `none` drops it, `all` renders its children with the condition added to `enclosing`, `some` renders its children first, the same way, and writes `<indent>**<label>:**` before them only when that rendered text is not empty; a block whose children all drop out (or that had none) writes nothing at all. The same rule applies to each labelled `case` and `default`. A switch classifies each branch as `env.<v> in [<case values>]`, and `default` as `not (env.<v> in [<every case value>])`, each with the switch's enclosing conditions, in source order; a branch's children have the branch condition added. Directive lines and the blank lines between `switch` and its first `case` are removed. Text lines are written unchanged: no renumbering, no reflow, no blank-line collapsing. The trailing newline of the input is kept.

### Conditional skills (`src/core/factory/factory-yaml.ts`, `src/core/env/declarations.ts`)

`KNOWN_FACTORY_FIELDS` gains `"skills"`; `FactoryYaml` gains `skills: SkillCondition[]`, `{ name: string; condition?: Condition; line: number }`. `parseSkillsField` reports, on the key's line: `"skills" needs format: 2` (fix `Set format: 2`); `"skills" must be a mapping of skill names`; an entry that is not a mapping, `Skill entry "<n>" must be { when: <condition> }`; an unknown key, `Unknown key "<k>" in skill entry "<n>"` with did-you-mean over `when`; a missing or empty `when`; a condition error or undeclared name as for directives. `environmentProblems` adds the checks that need the skills: `skills names unknown skill "<n>"` with did-you-mean over `factory.skills`, and `"<n>" is in the pipeline, so it cannot have a skills entry`, fix `Remove the entry: the pipeline names installed workflows for everyone`.

### Validation (`src/core/env/validate.ts`, new; `src/core/factory/load.ts`)

`export async function environmentProblems(factory: Factory): Promise<Problem[]>`, called at the end of `loadFactory`:

- For each skill, `collectSkillFiles` (below) lists its files as `build` would; each `.md` file is read, decoded with `textContent`, normalised with `toLF`, and checked. A file that is not UTF-8 is skipped: `build` copies it unchanged. `SKILL.md` is parsed below its frontmatter with `firstLine` set to the line after the closing `---`. `.factory/AGENTS.md` is parsed from `factory.agentsMd`.
- Format 2: every `parseMarkdown` problem, the conditional-skill checks above, and rule 6: any line of `directiveLines(frontmatter)` in `SKILL.md`'s frontmatter, or in the frontmatter of any other rendered `.md` file that starts with `---`, is `Directives are not allowed in frontmatter`, fix `Move the directive below the closing ---; name and description stay the same in every environment`.
- Format 1: one warning per file whose `directiveLines` is not empty, on its first directive line: `<file> has factory: directives, which need format: 2`, fix `Set format: 2 in .factory/factory.yaml, or remove the directives`.
- No `factory.yaml`: the factory is format 1 for this rule.

Read errors are reported once by the existing walker problems and `dedupeReadErrors`.

### Build (`src/core/build/skill.ts`, `plan.ts`, `agents.ts`)

- `skill.ts`: the directory walk moves into `export async function collectSkillFiles(source: SkillSource, options: CompileSkillOptions): Promise<{ files: { relative: string; target: string; mode: number }[]; problems: Problem[] }>`, with the symlink containment, loop and read rules unchanged; `compileSkill` reads those files. `CompileSkillOptions` gains `render?: (file: { relative: string; text: string; firstLine: number }) => string` and `appliesOnly?: string`. In `addFile`, a text file with a `.md` extension goes through `render`; for `SKILL.md`, only the body after the frontmatter does, and `insertComment` then adds the comment and, when `appliesOnly` is set, the line `**Applies only <label>.**` right after it. The built-in `metafab` skill and adoption never pass `render`, so their directives (in fenced examples) are copied.
- `plan.ts`: for a format 2 factory, `compileFactorySkills` builds a renderer over `factory.factoryYaml.env` and `plan.selection.selection`. For each skill with a `skills` condition, `classify(condition, [], selection, env)` decides (a `skills` condition over more than 1024 combinations is the same error, on its `factory.yaml` line): `none` skips the skill, so `scanDestination` removes its owned directory as for a deleted skill; `some` passes `appliesOnly`. The standing instructions are rendered once with `allValues(env)` and passed to `renderAgentsBlockBody(factory, standing)` and `agentsBlockLineCount(factory, standing)`; the line limit counts the rendered block.
- Format 1: no renderer and no `skills`, so output is byte for byte what it is today.

### Check

`runCheck` needs no new step: the validation arrives in `factory.problems`, and drift (rule 7) compares installed output with `planBuild`'s output for the selection. Selection warnings come after drift, as plan warnings do today.

### Edge cases

- **Nesting.** A `when` in a `case` is classified in the case's scenarios; a switch in a `when` likewise.
- **One selected value.** A switch over a variable with one selected value keeps exactly one branch, unlabelled.
- **Empty block.** A partial-match `when`, `case` or `default` whose rendered children are empty (no lines, or only inner blocks that are removed) writes no label line.
- **Directive in a list item, indented.** Recognised; the label line keeps the indentation.
- **CRLF.** Normalised before parsing; output is LF, as all output is.
- **Windows paths.** Problem files are POSIX; nothing here touches paths beyond the existing walk.
- **Large files and many variables.** One pass per file; each block enumerates at most 1024 scenarios, whatever the number of declared variables.
- **Second run.** Same input and selection give the same bytes, so `build` reports `Up to date.`
- **Changing the selection.** `env set` (2.011) rebuilds; a skill whose condition turns false is removed, one that turns true is created.

## Open questions

2. Should `check` warn about a `default` that no value can reach (every value has a case)? Proposal: yes, as a warning, `factory:default is never used: every value of <v> has a case`; it costs one comparison and catches dead text. Add it here if the person agrees.
