# Plan 1.026: Every error names a fix, every JSON result has problems, and problem files use `/`

Plan 1.022's contract sweep and error review found four ways the CLI breaks its own output contract. Some errors have no `problems`, so the person sees what went wrong and no next step. Many problems have `level: "error"` and no `fix`. Five results leave out `problems`. On Windows, `import` of a path source reports problem files with backslashes. This pull request fixes every site in one change, and changes the types so that the compiler refuses a new site of each kind. After it merges, every failed command (exit 1, 3, 4 or 5) shows at least one `  fix: ` line, every `--json` result has `problems`, and no problem `file` has a `\` on any platform. It ships in 2.0 and builds on `main` after Plan 2.011 merges.

## Specs

- [CLI: JSON output](../specs/cli.md#json-output): `problems` is in every result, the problem shape, `fix` on every error, `/` in `file`
- [CLI: Command behaviour](../specs/cli.md#command-behaviour): rules 4 to 6, which the contract sweep tests
- [CLI: Exit codes](../specs/cli.md#exit-codes): no exit code changes
- [Sharing: Fab validation](../specs/sharing.md) ("Fab validation rejects"), [Steps](../specs/sharing.md#steps) and the publish retry sentence ("fix the failure and run `metafab publish` again"): the sources of the fix wording below

Spec edit this pull request makes. In `cli.md`, [JSON output](../specs/cli.md#json-output), the first paragraph:

> With `--json`, a command writes one JSON object to standard output. Human-readable messages go to standard error. Every result contains `ok`, `command`, `exitCode` (the process exit code) and `problems`. A result for missing input (exit 2) contains `required` instead of `problems`.

becomes:

> With `--json`, a command writes one JSON object to standard output. Human-readable messages go to standard error. Every result contains `ok`, `command`, `exitCode` (the process exit code) and `problems`, including a successful result with nothing to report, where `problems` is empty, and `metafab --version --json`, which adds `version`. A result for missing input (exit 2) contains `required` instead of `problems`.
>
> Each problem has `level` (`error` or `warning`), `file`, `message`, and `line` when it is known. Every error also has `fix`: the next step the person can take. A warning has `fix` when there is one. `file` uses `/` separators on every platform, also when it starts with a local path the person typed; the message may repeat that path as typed. A failed command (exit 1, 3, 4 or 5) reports at least one error, so without `--json` standard error shows at least one `fix:` line.

No other spec text changes. No exit code, message or `code` changes; the only output changes are the added `problems` and `fix` values and the `/` in problem files.

## Design

### The types (`src/errors.ts`, `src/output.ts`, `src/util/yaml.ts`, `src/input.ts`)

```ts
interface ProblemBase { file: string; line?: number; message: string }
export interface ErrorProblem extends ProblemBase { level: "error"; fix: string }
export interface WarningProblem extends ProblemBase { level: "warning"; fix?: string }
export type Problem = ErrorProblem | WarningProblem;

export interface MetafabErrorOptions {
  exitCode?: ExitCode;
  code?: string;
  problems: Problem[];        // required
  details?: unknown;
  cause?: unknown;
}
// constructor(message: string, options: MetafabErrorOptions): no default
```

- `MetafabError.problems` stays declared as `readonly problems?: Problem[]`, so `error.problems ?? []` in callers still compiles. Declaring it required is optional cleanup and is not needed.
- `CommandResult.problems` in `src/output.ts` becomes `problems: Problem[]`.
- `YamlProblem.fix` in `src/util/yaml.ts` becomes `fix: string`. Every producer (`parseYaml`, `aliasProblems`, `expansionProblem`, `parseFrontmatter`) already sets it. This one change clears `factoryAliasProblems` and `parseFactoryYaml` in `src/core/factory/factory-yaml.ts` and `loadSkill` in `src/core/factory/discovery.ts` with no edit. Those files are not in `owns`.
- `NeedsInput` in `src/input.ts` passes `problems: []`.
- Tests are not type-checked (`tsconfig.json` includes only `src/`), so test objects without `fix` still run.

A trial of these four type changes on `main` (with the edit helpers' `fix` made required, as below) gave 59 compiler errors, plus 16 more in `config/validate.ts` once `Report` was overloaded, plus the 5 command results. That list is the work. After 2.011 merges, the builder runs `npm run typecheck` first and fixes any new site it reports in `src/core/env/**` or `src/commands/env.ts` the same way.

### Problem files on Windows (`src/core/sources/problems.ts`, new)

```ts
/** A problem file that starts with a source label: redacted, `/`-separated on every platform, no trailing `/`. */
export function sourceProblemFile(label: string, relativePath?: string): string {
  const base = redact(label).replace(/\\/g, "/").replace(/\/+$/, "");
  return relativePath === undefined || relativePath === "" ? base : `${base}/${relativePath.replace(/^\.\//, "")}`;
}
```

It replaces:

- `prefixedFile` in `src/core/sources/validate.ts`. Every `loadFactory` problem from a fab, and `invalidFormat` and the missing `.factory` problem. This is the CI failure in the note.

`redact` runs first, so a credential in a label is never written to `file`. On POSIX a label with a literal `\` in a directory name also gets `/`. Rule 4 forbids `\` in `file`, so that is the contract. The summary (`Invalid fab from D:\a\…`) is unchanged.

### Failure, second run, Windows, CRLF

- **Failure.** Every site keeps its exit code, its message, its `code` and its timing. Each one throws before it writes, as it does today, so a failed `import`, `update` or `publish` leaves the repository as it was. The person now also sees `<file>: error: <message>` and `  fix: <fix>` on stderr, and the same problem in `--json`. For the 17 errors that had no problems, stderr now repeats the message as a problem line under the stdout summary, as `unreadableFactory` already does.
- **Second run.** Nothing here writes state. Problems are built fresh on each run, so a second run gives the same output. `updateWriteFailed` keeps its two cases: restored (the new fix: fix the cause and run `update` again) and not restored (the existing Git fix).
- **Windows.** `sourceProblemFile` is the whole Windows change. The contract case "import: an invalid fab exits 4" now asserts rule 4 on `windows-latest` too. The `create workflows\\x` case also asserts `problems`. CI runs `windows-latest` only on ready pull requests and `main` (Plan 1.022), so the Windows result is known once the pull request is marked ready.
- **CRLF.** No change touches line endings. The YAML fixes reuse `parseYaml` and the `yaml` parser, which already handle CRLF. The fix texts are single-line constants.
