# Plan 1.022: Verify agent tools, Windows and the CI recipe

Metafab installs files for agent tools but never runs them. Nothing yet proves that Claude Code, Codex, opencode, Cursor and Copilot read what `build` writes, that the hooks run under Git for Windows, or that the spec's CI recipe works outside this repository. This plan proves those things before the 1.0 release. It runs the spec's CI recipe against the `mark4-like` fixture in a test, on LF and CRLF checkouts, on all three operating systems. It adds a CI job that installs the packed CLI and proves which resolution path each hook used. It sweeps every command for the `--json`, no-prompt and fix-line rules. It records agent tool checks in a new `docs/verification.md`, and it answers the duplicate-skills open question in the spec. It fixes one-line defects in the CLI's command layer and the result shape of internal errors. Every other finding becomes an intake note. After it merges, `docs/verification.md` holds a dated, versioned result for each tool and operating system, and the release plan (1.012) can rely on it.

This plan takes over these steps from [Plan 1.012](1.012-release.md): the four Hardening bullets "Run the spec's CI recipe (`build`, `git diff --exit-code`, `check`) in our own CI against the `mark4-like` fixture", "Windows pass: paths, CRLF checkouts, executable bits, long paths", "Review every error message for a fix line and a correct exit code" and "Confirm every command supports `--json` and never prompts without a terminal", and the whole "Agent tool verification" section.

From intake: *check by hand that Metafab's git hooks run under Git for Windows*, Plan 1.016 (Design: hookScript), PR #17, 8 Nov 2026. The note was deleted when this plan was written; its facts are carried over in full in [Git hooks under Git for Windows](#git-hooks-under-git-for-windows).

## Design

### `docs/verification.md` (new)

One file and one structure, so the release plan can read off what was checked, where and when.

```markdown
# Verification record

Metafab installs files for agent tools but never runs them (README: Deferred features, "Runtime verification of agent behaviour").
This file records the checks a person or agent made against real tools and operating systems before a release.
Add a row when you check something again. Do not edit an old row; add a new one with the new date.

Result is one of: `pass`, `fail`, `partial`, `pending`, `not run`. Every `fail` or `partial` links the intake note filed for it. `pending` means a person still has to run the check; `not run` gives the reason.

```

Columns:

- **Tool**: for example `Claude Code`. **Version**: the exact output of `claude --version`, `codex --version`, `opencode --version`, Cursor's *About* version, or the VS Code and GitHub Copilot Chat extension versions. **OS**: name and version, such as `macOS 15.1` or `Windows 11 24H2`.
- **Date**: ISO `YYYY-MM-DD`.
- **Steps**: the step ids from this plan (for example `A1`, `D1–D4`), so a row stays short and the steps live in one place.
- **Where** (CI): the workflow run URL and job name.
- **Verdict** in the review tables: `ok`, `fixed in this PR` (with the commit), or `filed` (with the intake link).

The headings are anchors other files link to (`verification.md#agent-tools`). The builder keeps them stable.

`build-plan` writes `pending` rows for A4, A5 and W4. `finish-plan` adds the person's rows below them; it does not edit the `pending` rows.

`docs/verification.md` is under `docs/`, so later rows can be added straight to `main` as a docs-only change (AGENTS.md, "Publishing docs changes").

### The scratch repository

Each manual check uses a new repository outside this checkout, built from this branch's CLI:

```sh
npm run build
npm pack --pack-destination "$TMPDIR"                    # seasb-metafab-<version>.tgz
mkdir "$TMPDIR/mh-verify" && cd "$TMPDIR/mh-verify"
git init && npm init -y
npm install --save-dev "$TMPDIR/seasb-metafab-<version>.tgz"
cp -R <checkout>/test/fixtures/build/mark4-like/source/.factory .
cp <checkout>/test/fixtures/build/mark4-like/source/CLAUDE.md .
printf 'agents: all\ngit-hooks: true\n' > .factory/metafab.yaml
npx metafab build
git add -A && git commit -m "scratch factory"
```

`agents: all` selects `claude` and every `.agents/skills/` target, so every tool sees both directories, which is the duplicate case. A second repository with `agents: [claude]` and a third with `agents: [codex]` are the controls.

On Windows, the same steps run in PowerShell with `$env:TEMP` and `Copy-Item -Recurse`. The agent tool then opens a second clone made with `git clone -c core.autocrlf=true`, so it reads a CRLF checkout.

### Spec CI recipe against `mark4-like` (`test/cli/ci-recipe.test.ts`, new)

The recipe from [Repeatability](../specs/building.md#repeatability), with `npx @seasb/metafab` replaced by in-process `runCli`. The `describe` block sets `{ timeout: 60_000 }`, because each case clones and builds several times, which is slow on Windows runners.

Setup, in `beforeEach`: `env = await isolateGitConfig()`, with `let env: Awaited<ReturnType<typeof isolateGitConfig>>` declared in the `describe` block. In `afterEach`: `env.restore()`, then `await rm(env.dir, { recursive: true, force: true })`, then remove every other temporary directory the test made (team repositories and clones, through their `cleanup()`).

1. Two **team repositories**, each made with `makeRepo({}, { git: true, prefix: "metafab recipe é-" })`. The space and `é` in the path cover W3 on every operating system. Into each, copy `test/fixtures/build/mark4-like/source/`, renaming `gitignore.txt` to `.gitignore` (the fixture stores it under another name so this repository's Git does not read it). Add `.factory/skills/git-conventions/run.sh` with a `#!/bin/sh` line.
   - **team-eol** also commits a `.gitattributes` with the three `eol=lf` lines from [Line endings](../specs/building.md#line-endings).
   - **team-plain** commits no `.gitattributes`.
2. In each, `runCli(["build"])`, then `git add -A`, `git update-index --chmod=+x .factory/skills/git-conventions/run.sh` (so the bit exists in the index on Windows too), and a commit with `-c user.name=test -c user.email=test@example.invalid -c core.autocrlf=false`.
3. Clone with `git clone --quiet` from the local path (no network), with `-c core.longpaths=true` always, in three variants:
   - **LF**: from team-plain, `-c core.autocrlf=false`.
   - **CRLF with eol lines**: from team-eol, `-c core.autocrlf=true`. Root `AGENTS.md` and `CLAUDE.md` arrive as CRLF, and `.factory/AGENTS.md` stays LF. The test reads the bytes of all three and asserts each.
   - **CRLF without eol lines**: from team-plain, `-c core.autocrlf=true`. Every text file arrives as CRLF. The test asserts it for `.factory/AGENTS.md` and `AGENTS.md`.

   Git converts on checkout on every operating system when `core.autocrlf=true`, so the CRLF variants run on Linux and macOS as well as Windows.
4. In each clone, the recipe: `runCli(["build"])` exits 0; `git diff --exit-code -- AGENTS.md CLAUDE.md .gitignore .gitattributes` exits 0; `runCli(["check", "--json"])` exits 0 with no error problems.
5. A second `runCli(["build", "--json"])` reports no changed paths (the `changed` list in its result is empty).

Failure cases:

- **Stale committed block**: in team-plain, edit `.factory/AGENTS.md` and commit without building. In a fresh clone (LF and CRLF), `build` rewrites the block, and `git diff --exit-code` exits 1 and names `AGENTS.md`. This is the case the recipe exists for.
- **Stale installed skill**: in a clone, after `build`, edit `.claude/skills/git-conventions/SKILL.md`. `check --json` exits 1. Its problem's `file` uses `/` separators on every operating system (no `\`), and the problem has a `fix`.
- **Executable bit**: on Linux and macOS, the installed `.claude/skills/git-conventions/run.sh` has mode 0755 in the LF clone. On Windows the test asserts only that `check` exits 0, because the spec says only content is compared there.
- **Long paths**: a skill file under `.factory/skills/git-conventions/`, nested in directories of 40 characters each, so that its absolute installed path is at least 300 characters. In the team repository and in the LF clone, `build` and `check` exit 0, and the installed copy's bytes equal the source. Git for Windows needs `core.longpaths=true` to check out such a path. That is Git's limit, not Metafab's, which is why every clone passes it, and `docs/verification.md` records it. If Node or Metafab fails here on Windows, the case becomes `test.fails` with an intake note (see Decisions).

### Contract sweep (`test/cli/contract.test.ts`, new)

Every command in `COMMANDS` (`src/cli.ts:27`) has at least one case. A guard test fails if `COMMANDS` has a name with no case, so a new command cannot skip the sweep.

Every case runs `runCli([...args, "--json"], { cwd, tty: false, stdin })`. `stdin` is a `Readable` whose `read()` records that it was called and pushes nothing. The case asserts:

1. `stdout` is exactly one JSON object: it parses, and nothing follows it except a final newline.
2. It has `ok` (boolean), `command` (string) and `exitCode` (number). `exitCode` equals the returned process code, and the code is 0 to 5.
3. It has `problems` (an array, possibly empty). Only when `exitCode` is 2 does it have `required` instead: a non-empty array, each item with `name` and `description`, and `flag` when a flag exists.
4. Every problem with `level: "error"` has a non-empty `fix`, and its `file` has no `\`.
5. The `stdin` stream was never read.
6. The same arguments without `--json` give the same exit code and no stack trace on stderr (no line starting with `    at `). The internal-bug case is exempt: its human run must print the stack (see that case).
7. For every case whose exit code is 1, 3, 4 or 5, the human run's stderr contains at least one line starting with `  fix: ` (the form `formatProblem` in `src/output.ts` prints). Exit 2 is exempt, because its `Required values:` list names the flags. A case that prints no fix line is a finding. Today that is every `MetafabError` thrown without `problems`. Such a case stays as `test.fails`, with the intake note that covers it (one note may cover several sites), under the rule in Decisions.

Cases (the fixtures are copied into a temporary directory; none needs the network):

| Command | Cases |
| --- | --- |
| `init` | empty directory outside Git (exit 0, `agents` set to all); an existing `.claude/skills/foo/SKILL.md` without `--adopt` (exit 2, `required` names `--adopt`) |
| `build` | no factory (exit 1, fix names `metafab init`); `mark4-like` (exit 0) |
| `create` | `create workflows/x` without `--description` (exit 2) |
| `pipeline add`, `pipeline remove` | an unknown workflow name (exit 1 with a fix) |
| `map` | `mark4-like` (exit 0); no factory (exit 1) |
| `check` | a stale installed skill (exit 1) |
| `import` | the path source `test/fixtures/fabs/valid-fab` (the exit code the spec gives for a non-interactive import); `test/fixtures/fabs/invalid-fab` (exit 4); a path that does not exist (exit 3) |
| `update`, `diff` | a factory with no `upstream` (the spec's exit code, with a fix) |
| `detach` | a factory with no `upstream`: exit 0 and `problems: []`. `detach` of nothing is a no-op, not an error ([Sharing](../specs/sharing.md): "After detachment, the factory has no upstream"), and `src/commands/detach.ts:20` already returns an empty list |
| `publish` | no `publish` key in `metafab.yaml` (exit 1 with a fix); `--dry-run` with a valid `publish` key and no network target |
| global | no command; an unknown command; `pipeline` with no subcommand |
| internal bug | a stub command that throws `new Error("boom")`, passed as `commands`, as `test/cli/cli.test.ts` does: exit 1, `command`, `problems` with the bug fix line, no stack in JSON. Human run: stderr has the stack (a line starting with `    at `) followed by the `  fix: ` line. That assertion replaces rule 6 for this case, and rule 7 applies |

Windows only (`test.skipIf(process.platform !== "win32")`): `import` with a `.\\fab`-style relative path source, and `create workflows\\x --description d`. Each either works like its `/` form or gives a usage error with a fix. The result is recorded.

Where the spec fixes the exit code for a case (cli.md and sharing.md), the case asserts it. Where it does not, the case asserts only the contract, and the code goes in the review table.

### `.github/workflows/ci.yml`: the `hooks` job (new)

`verify` and `factory` are unchanged. `verify` now also runs the new tests on every operating system.

```yaml
hooks:
  strategy:
    fail-fast: false
    matrix:
      os: [ubuntu-latest, macos-latest, windows-latest]
  runs-on: ${{ matrix.os }}
  defaults:
    run:
      shell: bash          # Git Bash on Windows: the same sh family that runs the hooks
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with:
        node-version: 20
    - run: npm ci && npm run build && npm pack --pack-destination "$RUNNER_TEMP"
    - name: Stub npx
      run: <writes $RUNNER_TEMP/stub/npx and adds it to GITHUB_PATH>
    - name: Project dependency
      run: <D1 to D4>
    - name: Global install
      run: <G1 to G3>
```

This job makes no claim about line endings, so it does not set `core.autocrlf`.

**Stub `npx`**: write `$RUNNER_TEMP/stub/npx` as `#!/bin/sh` + `echo "npx stub reached" >&2` + `exit 1`, make it executable, and prepend its directory to `PATH` through `$GITHUB_PATH`. The hooks inherit `PATH` from `git`, so a hook that falls through to the `npx` line fails fast with a known message and never reaches the network. Every hook output below is captured with `2> hook.log`, and every commit uses `git -c user.name=ci -c user.email=ci@example.invalid`.

**Project dependency** (no global `metafab`; the step first asserts `! command -v metafab`):

- **D1**: in `$RUNNER_TEMP/dep`, run `git init`, `npm init -y` and `npm install --save-dev "$RUNNER_TEMP"/seasb-metafab-*.tgz`. Write `.factory/metafab.yaml` with `agents: [claude]` and `git-hooks: true`, plus one workflow. Run `./node_modules/.bin/metafab build` and commit. The step calls the shim directly, not `npx metafab`, because the stub `npx` is first on `PATH` and would fail. It is also the exact path the hook checks with `[ -x node_modules/.bin/metafab ]`, so D1 proves that shim runs before D2 relies on it. `node_modules/` is in `.gitignore`.
- **D2**: delete `.claude/skills/`, then `git switch -c b1`. Assert that `.claude/skills/metafab/SKILL.md` exists, and that `hook.log` contains neither `metafab: build failed` nor `npx stub reached`. Only `node_modules/.bin/metafab` could have built it. This proves `[ -x node_modules/.bin/metafab ]` is true for npm's extensionless `sh` shim, which is the intake question, and that Git for Windows' `sh` runs the hook.
- **D3**: `git worktree add ../dep-wt -b b2`. Assert that `../dep-wt/.claude/skills/` does not exist, and that `hook.log` contains `npx stub reached` and `metafab: build failed`, and that the command exited 0. This proves the new spec sentence: a project dependency alone does not build a new worktree.
- **D4**: remove `node_modules/.bin/metafab` (and `metafab.cmd` / `metafab.ps1` on Windows), delete `.claude/skills/`, then `git switch -c b3`. Assert that nothing was rebuilt and that `hook.log` contains `npx stub reached`. This is the control showing that D2's build came from the local shim.

**Global install**, in `$RUNNER_TEMP/glob`, a repository with no `node_modules/`:

- **G1**: `npm install --global "$RUNNER_TEMP"/seasb-metafab-*.tgz`. Set up the same factory, run `metafab build` and commit.
- **G2**: `git worktree add ../glob-wt -b g2`. Assert that `../glob-wt/.claude/skills/metafab/SKILL.md` exists, and that `hook.log` contains neither failure line. This proves `command -v metafab` finds the global shim, and it is the intake note's exact repro.
- **G3**: `npm uninstall --global @seasb/metafab`, then `git worktree add ../glob-wt2 -b g3`. Assert that `../glob-wt2/.claude/skills/` does not exist and that `hook.log` contains `npx stub reached`. This is the control for G2.

The real `npx` fallback is not exercised: the pinned `@seasb/metafab@<version>` is not on npm until 1.0, and after 1.0 it needs the network. `docs/verification.md` records that it was not run, and why.

### Edge cases this plan must cover

- **No terminal**: the contract sweep runs every case with `tty: false` and a `stdin` that fails the case if it is read. The CI jobs have no terminal.
- **`--json`**: the contract sweep, including the internal-bug result.
- **A second run**: the recipe test runs `build` twice in each clone. For `init` and `build`, repeat safety is covered only by the existing tests.
- **An interrupted run**: tests clean up their temporary directories in `afterEach`. A manual session that stops partway leaves `pending` or `not run` rows, never invented results.
- **No Git**: the `init` and `build` contract cases run outside Git. The recipe needs Git and says so.
- **No network**: no test reaches it. Only the `hooks` job uses it, for `npm install` of the tarball's dependencies. The `npx` stub keeps the hooks off the network.
- **Windows and CRLF**: as above.

The only CLI behaviour this plan changes is the result shape of internal errors and of `MetafabError`s without problems, plus any one-line fixes. None of them writes to the repository, so a failure leaves it unchanged, as it does today.
