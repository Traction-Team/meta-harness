# Plan 1.011: `metafab publish`

Package `.factory/` as a fab and publish it to npm, a Git fab repository, or both.

## Specs

- [Sharing: Publishing](../specs/sharing.md#publishing)
- [Sharing: Fab layout](../specs/sharing.md#fab-layout)
- [Sharing: Version policy](../specs/sharing.md#version-policy)
- [Configuration: `publish`](../specs/configuration.md#publish)

## Design

### `publish [--dry-run] [--tag <tag>]`

1. Require a valid `publish` section (exit 1 with the config problems otherwise).
2. Run `check`. Stop on errors.
3. Stage the fab in a temporary directory:
   - Copy `.factory/`, keeping modes.
   - Exclude `metafab.yaml`, `.factory/README.md`, and every `publish.exclude` glob (`picomatch`, relative to `.factory/`, `dot: true`). A link with one of those names is left out too: `README.md` may point outside `.factory/` because it is read as the fab README.
   - Exclude the names `npm pack` always ignores (`.DS_Store`, `.npmrc`, `.gitignore`, `npm-debug.log`, `._*`, `.*.swp`, `*.orig`, `.git`, `CVS`, and the rest of npm's defaults), so the npm tarball and the Git fab carry identical files and the reported list is exact.
   - Fail when an excluded workflow is still in the pipeline.
   - Copy with the fab rules `import` applies: 1 MB per file, 64 MiB and 10 000 entries in total, and a link is copied as its target's content when the target stays inside `.factory/` (a broken or escaping link fails by name).
   - Validate the staged `.factory/` with `loadFactory` (an exclude can break a reference) and fail when it is empty. A staged fab that breaks the fab rules exits 4, as `import` reports it; the pipeline and exclude-config checks stay exit 1.
4. README at the fab root: `publish.readme`, else `.factory/README.md`, else generated from the staged factory (name, description, pipeline with stops, workflow and skill lists, and the `npx @seasb/metafab import <source>` command).
5. npm target: write `package.json` with `name`, `version`, `description` (falls back to `factory.yaml`), `keywords` (always includes `metafab`, deduplicated), `files: [".factory", "README.md"]`, `metafab: { format: 1 }`, `repository` from the CI environment when provenance is available, `license` when set.
6. Print the file list, total size, and targets.
7. Stop here with `--dry-run`.
8. Check the version is new on every target before publishing to any:
   - npm: `npm view <name>@<version> version --json`; a 404 means new.
   - Git: `git ls-remote --tags <url> refs/tags/v<version>`.
9. Publish to each target.

### npm target

`npm publish <stagingDir> --access <access> [--tag <tag>] [--provenance]`. Add `--provenance` when running in GitHub Actions with `ACTIONS_ID_TOKEN_REQUEST_URL` set, or in GitLab CI with `SIGSTORE_ID_TOKEN` set. Stream npm's output to stderr.

### Git target

1. Clone `publish.git` into a temporary directory. Use `publish.branch`, else the remote default branch, else `main` for an empty repository.
2. Skip the target when tag `v<version>` carries identical content; stop the publish when it carries different content. Compare with Git: check the tag out, copy the staged fab over it, and check that `git add -A` leaves nothing staged.
3. Protection: the branch head must carry an annotated tag created by an earlier `publish`. Tag messages are `metafab publish <version>`, which identifies them. An empty repository passes. Otherwise exit 5.
4. Remove every tracked file (`git rm -r -q .`), copy the staged fab in, `git add -A`.
5. Commit `Publish <version>` and create the annotated tag.
6. `git push --atomic origin <branch> v<version>`.

Run `git ls-remote` (step 8), `git clone` and `git push` through one publish helper that sets `GIT_TERMINAL_PROMPT=0` unless standard input is a terminal and `--json` is absent, as `import` does ([Plan 1.009](1.009-import.md#fetch-hygiene)), so an SSH key with a passphrase can prompt.

### Result

JSON: `{ ok, command: "publish", version, files: [...], size, targets: [{ target: "npm" | "git", status: "published" | "skipped" | "failed", detail }] }`.

## Tests

- Staged fab never contains `metafab.yaml` or `.factory/README.md`
- An excluded workflow that is still in the pipeline fails
- `--dry-run` publishes nothing and touches no target
- Publishing an existing version fails on either target before anything is published
- A hand commit on the fab repository branch makes the next publish exit 5
- The project repository's `git status` is unchanged after publish
- The published Git fab imports with the expected `version` and `commit`

## Open questions

1. Partial failure: npm succeeds and the Git push fails (or the reverse). (Carried from the [spec](../specs/README.md#open-questions).) **Decided:** publish Git first (its push is atomic and its preflight is strongest), then npm. A target that already has this exact version with identical content is skipped, so a re-run publishes only the rest; a target with different content stops the whole publish before anything is published. The Git comparison uses Git itself, so line endings and modes compare as Git stores them. [Sharing: Publishing](../specs/sharing.md#publishing) states the order, the skip, the refusal, and the recovery.
2. Should `publish` also accept `--provenance` / `--no-provenance` to override detection? **Decided:** no flags in v1. `publish` detects provenance from the CI environment, and the generated `package.json` names `repository` from the same environment when provenance is available.
