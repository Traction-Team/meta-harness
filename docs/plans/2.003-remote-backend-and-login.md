# Plan 2.003: Remote store backend over the protocol, with login and logout

This plan connects Metafab to remote stores: an HTTP client that implements the [Store protocol](../specs/store-protocol.md) as a `StoreBackend`, a credentials file, and `metafab store login` and `logout`. It adds an in-process test server that implements the protocol over the local backend, so the contract suite from Plan 2.002 runs against the remote client too, and `npm run test:contract`, which runs the same suite against any server URL; that is how Metastore Cloud, in its own repository, proves it conforms. It also turns `store` and `scorer` into command groups like `pipeline`, and registers every later command with its usage and help, each returning "not implemented" until its plan lands, so Plans 2.004 to 2.008 each own only their own command files. After it merges, a person can sign in to a store; nothing reads or writes documents yet.

Rule 2 becomes "Outside the repository, Metafab keeps only the download cache (`~/.metafab/cache/`), store credentials (`~/.metafab/credentials.json`) and local stores (`~/.metafab/store/`)."

**`cli.md`, Commands.** Add a section after "Share a factory":

> ### Keep documents and scores
>
> `metafab store <command>` keeps a factory's working documents and scores in a store, and `metafab scorer <command>` runs the factory's scorers. Both groups are specified in [Store](store.md). `metafab store --help` and `metafab scorer --help` list their commands.

**`cli.md`, Exit codes.** Add the row `| 6 | Metafab could not reach the store, the store refused its credentials, or it speaks another protocol version |`.

## Decisions

Proposed in this plan, for approval:

| Topic | Choice | Reason |
| --- | --- | --- |
| HTTP | Node's global `fetch` with `AbortSignal.timeout`; no dependency | Node 20 has it; the protocol is plain JSON |
| Timeouts | 30 s for reads; 300 s for `POST /v1/changes`, blob uploads and downloads | A large change or blob must not time out on a slow link |
| Exit code for an unreachable or refusing store | New code 6 | Agents need to tell "sign in or check the network" apart from a validation failure (1) or missing input (2) |
| Where later commands are registered | All of them now, in `src/commands/store/index.ts` and `src/commands/scorer/index.ts`, with stubs that exit 1 `not implemented yet`, as the [Store](../specs/store.md) status note allows until Plans 2.009 and 2.010 merge; no release ships in between | Each later plan then owns only its command files, so plans that do not share code can be built in parallel |
| Test server | `node:http` over `LocalBackend`, in `test/helpers/` | One semantics source for both runs; it refuses unknown request fields, as the protocol requires, so the client cannot drift |
| Credentials key | The URL's origin (scheme, host, port) | One token serves every store on a host, as Metastore Cloud tokens are per account |
| Credentials on Windows | Mode 0600 is applied where supported; on Windows the file relies on the user profile's permissions | Node cannot set Windows ACLs without a dependency |

## Design

### Exit 6 errors (`src/errors.ts`, `src/core/store/errors.ts`)

`ExitCode` gains `StoreUnavailable = 6`. `src/core/store/errors.ts` builds `MetafabError`s with that exit code and these `code`s, messages and fixes:

| `code` | When | Message | Fix |
| --- | --- | --- | --- |
| `store-unauthenticated` | 401, or no token | `Not signed in to <origin>` | `Run metafab store login` |
| `store-forbidden` | 403 | `<origin> refused this request for <identity or "this token">` | `Ask an owner of the store for access` |
| `store-unreachable` | network error or 5xx after retries | `Cannot reach <url>: <reason>` | `Check the network and the url in .factory/metafab.yaml` |
| `store-protocol` | 426, a `protocol` other than 1, or a response that breaks the protocol | `<url> speaks protocol <n>` / `<url> sent an unexpected response to <route>` | `Upgrade @seasb/metafab` / `Report it to the store's operator` |

URLs in messages never include a query string, and no message or `details` ever contains a token.

### Remote client (`src/core/store/remote/`)

`client.ts`: `class RemoteBackend implements StoreBackend`, constructed with `{ url, token, fetch?, sleep?, now? }` (the last three for tests). `id` is `remote:<url without trailing />`.

- `request(method, route, { query?, body?, idempotencyKey?, timeoutMs })` builds the URL by appending the route to the base URL's path (`<url without trailing />` + `/v1/...`), never with `new URL(route, base)`, which would drop the base path; it sends JSON with `Authorization: Bearer <token>` and, when given, `Idempotency-Key`. It parses the error body `{ error: { code, message, details } }` and maps status codes as the protocol's [Errors](../specs/store-protocol.md#errors) table says.
- Retries: `GET` up to three times after 1, 2 and 4 seconds, on a network error, 429 (waiting `Retry-After` seconds when it is given, at most 60) or 5xx. `POST /v1/changes` and `POST /v1/scores` retry the same way with the same body and `Idempotency-Key`, because both are idempotent. A blob `PUT` retries the same way.
- `info()`: `GET /v1/info`; `protocol !== 1` throws `store-protocol`. The result is cached for the client's life. Every other method calls it first, so a protocol mismatch is found before any write.
- `list()`: pages with `limit = limits.pageSize` until `next` is `null`.
- `get()` and `versions()`: 404 returns `undefined`.
- `putBlobs()`: `POST /v1/blobs/uploads` with every blob, then `PUT` each returned upload with only its `headers` and the bytes from `read()`, at most four at a time. The token is added only when the upload URL's origin equals the base URL's origin, so a signed object-storage URL never receives it. A non-2xx answer is `store-unreachable` naming the blob.
- `readBlob()`: `GET /v1/blobs/<sha256>`; `fetch` follows a 302. 404 returns `undefined`. The client checks the SHA-256 of the bytes and throws `store-protocol` on a mismatch.
- `apply()`: `POST /v1/changes`. 200 → `saved`; 409 with `conflict` or `archived` → those outcomes from `details`; 422 → `invalid`; 413 → `invalid` with one problem `The change is over the store's <details.limit> limit`.
- `recordScores()`, `listScores()` (pages until `limit` scores or `next` is `null`), `scoreNames()`.

`wire.ts`: small checks of each response shape (required fields and their JSON types) that throw `store-protocol` naming the route and the first bad field. No schema library.

`open.ts` also gains `backendIdFor(factory, config, env): Promise<string>` (asynchronous, because Plan 2.010's Git backend reads the remote URL from Git configuration), which returns the id `openBackend` would give (`local:<name>` or `remote:<url>`, with the same name and URL resolution) without opening anything or reading credentials, so `metafab check` (Plan 2.006) can find the right index offline. Plan 2.010 extends it for `git`.

`openBackend` for `remote` takes the URL from `env.METAFAB_STORE_URL ?? config.url`. A URL from the environment is checked with `storeUrlProblem` (Plan 2.002's configuration URL rule, exported from `src/core/config/validate.ts`) before any token lookup or request; a broken one is exit 1, `METAFAB_STORE_URL <phrase>`, fix `Correct or unset METAFAB_STORE_URL`. The token comes from `resolveToken`; a missing token throws `store-unauthenticated` only when a method is called, so commands that never call the backend, such as `status --offline` (Plan 2.004), still work. `openBackend` returns `{ backend, problems }`, where `problems` carries credential-file warnings into the command's result.

### Credentials (`src/core/store/credentials.ts`)

```ts
export interface CredentialsFile { schema: 1; tokens: Record<string, { token: string; identity: Identity; savedAt: string }> }
export function credentialsPath(home?: string): string;                // <home>/.metafab/credentials.json
export async function resolveToken(url: string, env: NodeJS.ProcessEnv, home?: string): Promise<{ token?: string; problems: Problem[] }>;
export async function saveToken(url: string, token: string, identity: Identity, home?: string): Promise<void>;
export async function removeToken(url: string, home?: string): Promise<boolean>;
```

`METAFAB_STORE_TOKEN` wins over the file. `saveToken` and `removeToken` read, change and write the file while holding `~/.metafab/credentials.lock` (`acquireLock` with `waitMs: 5000`), so two logins at once never drop each other's tokens. The file is written to a temporary file with mode 0600 and renamed; `chmod 0600` follows on macOS and Linux. A damaged file reads as empty: `resolveToken` returns a warning `Problem` (`file: "~/.metafab/credentials.json"`, message `The credentials file is damaged; it is ignored`, fix `Run metafab store login to replace it`), which the command adds to its result's `problems`, so it shows in text and in `--json`. The next `saveToken` replaces the file. Nothing prints as a side effect. Keys are `new URL(url).origin`.

### Commands (`src/commands/store/`, `src/commands/scorer/`, `src/cli.ts`, `src/help.ts`)

- `src/cli.ts`: the `pipeline` special case becomes a `GROUPS` list, `["pipeline", "store", "scorer"]`. A group name followed by a subcommand resolves `"<group> <subcommand>"`; a group name alone, or with an unknown subcommand, is the existing failure with a did-you-mean over the group's commands. `src/help.ts`'s group help (`renderGroupHelp`) takes any group.
- `src/commands/store/index.ts` exports `STORE_COMMANDS`, and `src/commands/scorer/index.ts` exports `SCORER_COMMANDS`; `COMMANDS` in `src/cli.ts` spreads both. One file per command, each a `CommandDefinition` with the usage, arguments and options of [Store](../specs/store.md) (`pull`, `status`, `push`, `diff`, `show`, `log`, `ls`, `mv`, `archive`, `restore`, `unpin`, `import`, `score`, `scores`, `login`, `logout`; `scorer list`, `prompt`, `record`). Every command except `login` and `logout` returns `notImplemented("store <name>")` from `src/commands/not-implemented.ts`. Plan 1.020's test that compares each usage with the spec's tables extends to the command tables in `docs/specs/store.md`.
- `store login [--url <url>] [--token-stdin]`:
  1. The URL is `--url`, else `METAFAB_STORE_URL`, else the factory's `store.url`. With `--url` or the variable, no factory is needed: `findFactory` runs only when neither is given, so `login --url` works in any directory. With a local backend and no `--url`: summary `The local backend needs no login`, exit 0. With no URL at all: exit 1, `No store URL`, fix `Pass --url, or add store.url to .factory/metafab.yaml`. A URL that breaks the configuration URL rule is exit 1 with that rule's message.
  2. `GET /v1/info` with no token. The protocol requires a 401 `unauthenticated` with `details.protocol` and, optionally, `details.tokenUrl`. A `details.protocol` other than 1 is exit 6 `store-protocol` before a token is asked for. `details.tokenUrl` is printed to standard error: `Create a token at <tokenUrl>`. A 200 to an unauthenticated request, or a 401 without `details.protocol`, is `store-protocol`. A network failure is exit 6.
  3. With `--token-stdin`, the token is standard input, trimmed; empty is exit 1, `No token on standard input`. Without it, in a terminal, `promptSecret("Token: ")` (new in `src/input.ts`: readline with output muted). Without a terminal and without the flag: `NeedsInput` with `{ name: "token", flag: "--token-stdin", description: "A store token. Create one at <tokenUrl>" }`, exit 2.
  4. `info()` with the token. 401 is exit 6, `The token was refused`. On success, `saveToken`, summary `Signed in to <origin> as <identity.name>`. JSON: `{ url, identity }`.
- `store logout [--url <url>]`: the same URL resolution; `removeToken`; summary `Signed out of <origin>`, or `Not signed in to <origin>` (exit 0 either way). It does not contact the server.

### Test server (`test/helpers/store-server/`)

`startStoreServer(options: { dir: string; tokens: Record<string, Identity>; tokenUrl?: string; pageSize?: number; limits?: Partial<Limits>; faults?: Fault[] }): Promise<{ url: string; requests: RecordedRequest[]; close(): Promise<void> }>` (`limits` goes to its `LocalBackend`, so later plans can test batching and limits) listens on `127.0.0.1:0`, serves the protocol below the base path `/acme/store` (so `url` is `http://127.0.0.1:<port>/acme/store`, and a client that drops the base path gets 404 on every route), and implements every route over a `LocalBackend` in `dir`: bearer check (401 with `details.protocol` and `details.tokenUrl`, also for `GET /v1/info`), pagination with opaque cursors (base64 of the last path or score position), request shapes checked as the protocol's [Errors](../specs/store-protocol.md#errors) table says (a body that is not JSON, a field of the wrong JSON type, or a bad query value such as `limit=abc` or an unknown `kind` is 400 `bad-request`; an unknown field is 422 `invalid`), blob uploads as `PUT /_blobs/<sha256>` URLs (hash and size checked) on a second listener with its own port, so uploads go to another origin as object storage would, and that listener records whether any request carried `Authorization`; blob downloads as a 302 to the same second listener, and `Idempotency-Key` passed to `apply`. `Fault` injects, per route and count: a 500, a 429 with `Retry-After`, a 426, a response body that breaks the protocol, a `protocol: 2` info, or "apply then drop the connection" (the change is saved and the socket destroyed before the response).

### Contract runs

`test/core/store/contract.test.ts` (from Plan 2.002) gains two runs of `describeBackendContract`: a `RemoteBackend` against `startStoreServer` with `pageSize: 2`; and, only when `METAFAB_CONTRACT_URL` and `METAFAB_CONTRACT_TOKEN` are set, a `RemoteBackend` against that URL. `package.json` gains `"test:contract": "vitest run test/core/store/contract.test.ts"`. `npm test` includes the file, and the external run is skipped without the variables, so no test reaches the network.

### Edge cases

- **Proxy, TLS.** `fetch` uses Node's defaults; `NODE_EXTRA_CA_CERTS` works. `http` is accepted only for loopback hosts by the configuration rule.
- **A redirect on a JSON route.** `fetch` follows it; the `Authorization` header is dropped on a cross-origin redirect by `fetch` itself, so a token never leaves the store's origin.
- **Clock skew.** The client sends no times except inside origins and scores; `recordedAt` and `savedAt` are the server's.
- **`--json`.** `login` writes the prompt and the token URL to standard error only, so standard output stays one JSON object.

## Tests

- Contract suite against the test server with `pageSize: 2`, so every list pages.
- Client: a GET retried after one 500 and after a 429 with `Retry-After: 1` (with an injected `sleep` that records the waits 1 and the server's value); four 500s exit 6 `store-unreachable`; "apply then drop" retried with the same key saves once and returns `saved`; 401 → `store-unauthenticated`; 403 → `store-forbidden`; 426 and `protocol: 2` → `store-protocol` before any write is sent (the server's `requests` shows no `POST`); a body missing `documents` → `store-protocol` naming the route; a blob whose bytes do not match its hash → `store-protocol`; 413 → `invalid` naming the limit; no recorded request, message or JSON result contains the token.
- Credentials: save, resolve and remove with an injected home; the environment variable wins; mode 0600 (skipped on Windows); a damaged file gives the warning in the command's `problems` (text and `--json`) and is replaced by the next login.
- Test server request shapes, one case per route family (documents, changes, blobs, scores): a body that is not JSON → 400; a wrong type (`baseVersion: "2"`) → 400; `limit=abc` → 400; an unknown field → 422. These run against the test server directly with `fetch`, so the server is held to the protocol as well as the client.
- Token scope: the second listener never receives `Authorization`, for uploads or for followed download redirects.
- `METAFAB_STORE_URL` with credentials, a query, or `http://` to a non-loopback host is exit 1 before any request (the test server's `requests` stays empty).
- `login --url` and `logout --url` in a directory with no factory work; two concurrent `saveToken` calls for different origins both survive;
- `login`: `--token-stdin` with a valid token saves it and prints `Signed in to … as …`; a refused token exits 6 and saves nothing; no terminal and no flag exits 2 with `required` naming `--token-stdin`; a terminal run with an injected input reads the token without echoing it to the injected output; the token URL goes to standard error; local backend prints `needs no login`; no URL exits 1. `logout` removes the entry and is exit 0 when there is none.
- CLI groups: `metafab store --help` and `metafab scorer --help` list their commands; `metafab store pul` suggests `pull`; `metafab store pull` exits 1 with `not implemented`; `metafab pipeline add` still works.
