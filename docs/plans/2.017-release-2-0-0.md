# Plan 2.017: Release metafab 2.0.0

`latest` on npm is still `1.0.0`, but fab-basic's newest tag, `v0.2.0`, is format 2. So the command the README gives a new user, `npx @seasb/metafab import github:Traction-Team/fab-basic`, installs 1.0.0, which refuses the fab with exit 4 (`Unknown factory format 2`). This plan releases what `main` holds today, environments (2.011 to 2.016) and the v1 fixes (1.026 to 1.029), as `2.0.0` under `latest`, so the plain command works again for format 1 and format 2 fabs. It also fixes the one error a 2.0.0 user would hit when a later Metafab adds a `factory.yaml` field, since a released version cannot be changed afterwards.

## Specs

- [CLI: Installation](../specs/cli.md#installation)
- [Factory format: YAML and frontmatter grammar](../specs/factory-format.md#yaml-and-frontmatter-grammar): "Unknown fields are errors", which rule 6 of [Validation](../specs/factory-format.md#validation) enforces

This plan changes both: the installation section says what a 1.x CLI does with a format 2 factory or fab and names the `next` channel, and the grammar paragraph says what the unknown-field fix names.

## Decisions

Agreed with the person on 2026-11-24:

| Topic | Choice | Reason |
| --- | --- | --- |
| What 2.0.0 contains | `main` as it is now: environments and the v1 fixes. The store (Milestone 5) ships later, as 2.1.0 | The plain install path is broken until a format 2 CLI is `latest`. `2.0.0-next.1` was checked to import format 1 fabs (fab-basic `#semver:^0.1.0`), so nothing that works on 1.0.0 stops working |
| Forward-compatible unknown fields | When `didYouMean` finds no close known field, the fix also says to upgrade `@seasb/metafab` | The store adds `documents` to format 2. A 2.0.0 CLI that reads such a fab would otherwise tell the person to remove the field. A likely typo keeps its did-you-mean fix alone |
| Checks in real OpenCode and Claude Code sessions | Not a release gate. They stay in [the intake note](../intake/2026-11-24-confirm-environments-in-real-sessions.md) | The six previews and the fresh Amp orb check passed in Plan 2.015 |
| Open intake bugs (Windows `git+file://localhost/C:/…` import, npm test timeouts, a flaky Git fixture, publish 2FA) | 2.0.x, not this release | None touches environments or the install path |
| The `next` dist-tag | Stays on `2.0.0-next.1` until the next prerelease | Only the release workflow can publish (trusted publishing), and it never runs `npm dist-tag add` (Plan 2.016's test) |

## Design

- **Version.** `package.json` and `package-lock.json` go to `2.0.0`. The release workflow from Plans 1.012 and 2.016 is unchanged: `dist-tag.mjs` prints `latest` for `2.0.0`, so the tag `v2.0.0` publishes under `latest` with provenance after `npm run verify`.
- **Unknown fields.** `rule6UnknownFactoryField` in `src/core/factory/validate.ts` keeps its message. Its fix is the did-you-mean suggestion when `didYouMean(key, KNOWN_FACTORY_FIELDS)` returns one. Otherwise it is `Remove the field or use a known name (format, name, description, pipeline, requires, env, skills), or upgrade @seasb/metafab if the factory was written for a newer version`. The same problem reaches `check`, `build` and `publish` of the repository's own factory (exit 1; `publish` runs `check` first, in `src/commands/publish.ts`) and `import` and `update` of a fab (exit 4), so all of them gain the hint. Unknown keys inside a `requires` or `skills` entry are not changed (see Out of scope).
- **README.** The install table and quick start stay on `npx @seasb/metafab`, which installs 2.0.0 once it is `latest`. Add after the quick start:
  - choosing what agents read: `npx @seasb/metafab env set harness=claude` (and `workspace=…`), with a link to the Environments spec, and that with nothing selected every variant is installed, labelled;
  - staying on 1.x: a format 2 fab needs Metafab 2; with 1.x, import a 1.x-compatible tag such as `github:Traction-Team/fab-basic#semver:^0.1.0`;
  - prereleases: `npx @seasb/metafab@next` installs the newest prerelease, which can be older than `latest` between prereleases (today `2.0.0-next.1`).
  Add the Environments spec to the documentation list. The quick start's `git add` line also stages `.claude/agents/`, which fab-basic 0.2.x's `requires` make `import --setup` create, and the update example's commit message names `0.2.x`, not `1.3.0`. `docs/specs/README.md` gets both fixes.
- **Specs index.** In `docs/specs/README.md`, Environments moves from "Version 2 (draft)" into the main specifications table, as released in 2.0.0. Store and Store protocol stay drafts, and that section's heading and sentence say they serve the 2.1 store plans. The intro ("Version 1 has four responsibilities") gets one sentence that version 2 adds environments.
- **CLI spec, Installation.** One paragraph: a factory with `format: 2` needs Metafab 2 or later. 1.x refuses a fab whose factory is format 2 with exit 4 at `import` and `update` (`Unknown factory format 2`), and fails `check`, `build` and `publish` of a repository whose own `.factory/factory.yaml` is format 2 with exit 1 (`"format" must be the integer 1`), because `publish` runs `check` first. Prereleases are published under the npm dist-tag `next` and never under `latest`.
- **Factory format spec, YAML and frontmatter grammar.** After "Unknown fields are errors", say that the fix is the closest known name when there is one, and otherwise says to remove the field or use a known name, or to upgrade Metafab. Rule 6's own wording does not change.
- **Failure.** The workflow's `verify` job fails before `npm publish`: nothing is published; fix on `main` and push the tag again after deleting it. A re-run after a successful publish fails on npm's duplicate version and changes nothing.
- **Windows.** No path handling changes.
