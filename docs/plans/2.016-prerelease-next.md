# Plan 2.016: Publish metafab 2.0.0-next.1 under the next dist-tag

Plan 2.015 needs a published CLI that reads format 2 before 2.0.0 ships: this repository's Git hooks run the `@seasb/metafab` devDependency, and fab-basic 0.2.0's importers run `npx @seasb/metafab@next`. Plan 1.012's release workflow runs `npm publish` with no `--tag`, so it cannot publish a prerelease safely: npm 11 refuses a prerelease version without `--tag`, and an older npm would move `latest` to it, so every `npx @seasb/metafab` user would get a 2.x prerelease. This plan makes the workflow publish any version with a `-` in it under the `next` dist-tag, and every other version under `latest`, and sets the version to `2.0.0-next.1`.

## Specs

- [CLI: Installation](../specs/cli.md#installation): the package and how people run it; a prerelease never becomes what `npx @seasb/metafab` installs

This plan changes no spec.

## Decisions

Agreed with the person on 2026-11-15: publish `@seasb/metafab@2.0.0-next.1` under `next` after 2.014 merges; fab-basic 0.2.0 and this repository pin it until 2.0.0 ships.

| Topic | Choice | Reason |
| --- | --- | --- |
| Which versions are prereleases | Any version whose semver has a prerelease part, that is, a `-` after `major.minor.patch` | Matches semver and npm; no list of identifiers to keep current |
| Tag for a prerelease | Always `next`, whatever the identifier (`next.1`, `rc.0`) | One channel to opt into; this plan needs only `next` |
| Tag for a stable version | `--tag latest`, written out | The workflow says what it does; a later change cannot drop the tag by accident |
| Where the rule lives | `.github/scripts/dist-tag.mjs`, a dependency-free script the workflow calls and the tests import | A YAML expression cannot be unit-tested |

## Design

- `.github/scripts/dist-tag.mjs` exports `distTag(version: string): "next" | "latest"` and, run as `node .github/scripts/dist-tag.mjs <version>`, prints the tag. It refuses a version that is not `major.minor.patch` with an optional `-<prerelease>` and `+<build>` (exit 1, message on stderr), so a malformed `package.json` version stops the release. A `+build` part alone does not make a prerelease.
- `.github/workflows/release.yml`, after the existing tag-equals-version check and `npm run verify`: a step `tag=$(node .github/scripts/dist-tag.mjs "$version")`, then `npm publish --tag "$tag"`. Nothing else changes: trusted publishing, provenance and the re-run behaviour are 1.012's.
- `package.json` and `package-lock.json` go to `2.0.0-next.1`.
- After merge: tag `v2.0.0-next.1` on `main`; the workflow publishes. A re-run fails on npm's duplicate version and changes nothing. A later `2.0.0-next.2` is a version bump and a tag, with no plan.
- `latest` stays on the newest 1.x, so `npx @seasb/metafab` and the `^1.0.0` devDependency from Plan 1.025 never resolve to the prerelease (a caret range does not match prereleases).
