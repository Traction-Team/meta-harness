# Plan 1.028: New worktree hooks find the project's metafab

With `git-hooks: true`, `git worktree add` runs the shared `post-checkout` hook in the new worktree, but that worktree has no `node_modules/`, so a project that depends on `@seasb/metafab` only as a devDependency gets no build: the hook falls to `PATH` and then `npx`, which needs the network and, in this repository, resolves the worktree's own unbuilt package. This plan adds one step to the hook's lookup: after the factory root's own `node_modules/.bin/metafab`, try the same path in the repository's main worktree, found with `git worktree list --porcelain`, before `PATH`. After it merges and a project upgrades, a plain `git worktree add` builds the new worktree's skills whenever the main checkout has run `npm install`. It ships in 2.0, not in a 1.0.x patch.

Kind is `feature`, not `bug`: the code matches [building.md, Git hooks](../specs/building.md#git-hooks), which says outright that "a project dependency alone does not build a new worktree". This changes that spec.

## Decisions

| Topic | Choice | Reason |
| --- | --- | --- |
| Where the new step goes | Second: after the factory root's `node_modules/.bin/metafab`, before `PATH` | The project's pinned copy beats a global one, as for the first step. Proposed in the intake note |
| How the hook finds the main worktree | The first `worktree ` line of `git -c core.quotePath=false worktree list --porcelain` | `<git-common-dir>/..` is wrong for `--separate-git-dir`, for a submodule (`.git/modules/<name>`) and for a bare repository. `worktree list` is Git's own answer and exists since Git 2.7. `core.quotePath=false` keeps a non-ASCII path unquoted |
| When the lookup runs | Lazily, inside the `elif` condition | A checkout in a worktree that has its own `node_modules` (the main checkout, the usual case) costs no extra process. Only the fallback path pays one `git` and one `sed` |
| Factory in a subdirectory | `<main>/<factoryRelDir>/node_modules/.bin/metafab`, the same relative path the first step uses | Keeps the two steps symmetric. A dependency hoisted to the repository root is an existing gap of step 1 too (Out of scope) |
| Main checkout's version differs from the worktree branch's devDependency | Run it anyway | The same is true today of a global `metafab` on `PATH`. The build is right for the factory as long as the CLI reads its format; if not, the hook prints its usual failure line and exits 0. Running `npm install` in the worktree switches later hooks to its own copy. Raised below as open question 1 |
| Bare repository with linked worktrees | No new lookup: the first entry is the bare directory, which has no `node_modules`, so the hook falls through to `PATH` | There is no main checkout to prefer, and picking another linked worktree is arbitrary. Open question 2 |
| Submodule | No special case. Inside the submodule's own worktree step 1 applies. In a linked worktree of a submodule, Git reports `.git/modules/<name>` as the main worktree, which has no `node_modules`, so it falls through | Checked with Git 2.50: harmless, and rare |
| Empty or failed `git worktree list` | `[ -n "$main" ]` guards the test | Otherwise `"$main/./node_modules/.bin/metafab"` would test `/node_modules/.bin/metafab` at the file system root |
| One lookup in two places | A private helper in `script.ts` builds the `if`/`elif`/`else` chain for a given `metafab` argument list; `hookScript` and `hookCommand` both use it | They must never drift (a test pins it), and Plan 2.009 calls "the same CLI lookup" for `store pull` |
| Hooks written by older versions | Rewritten by the first `build` with the new CLI, through the existing content comparison in `syncGitHooks` | No change to `sync.ts` is needed |
| A main-checkout CLI older or newer than the worktree branch's devDependency | Run it anyway, as `PATH` already does; no version check in `sh` | Agreed with the person on 2026-11-15 |
| A bare repository with only linked worktrees | No lookup beyond the first `worktree list` entry | Agreed with the person on 2026-11-15. Picking another linked worktree is arbitrary and costs a scan on every fallback |

## Design

### The new script

`hookScript("post-merge", ".", "2.0.0")` becomes exactly (the new line is the second branch):

```sh
#!/bin/sh
# metafab:start
# Generated by metafab build 2.0.0. Set git-hooks: false in .factory/metafab.yaml to remove.
cd "$(git rev-parse --show-toplevel)/." 2>/dev/null || exit 0
[ -d .factory ] || exit 0
if [ -x node_modules/.bin/metafab ]; then node_modules/.bin/metafab build
elif main=$(git -c core.quotePath=false worktree list --porcelain 2>/dev/null | sed -n '1s/^worktree //p') && [ -n "$main" ] && [ -x "$main/./node_modules/.bin/metafab" ]; then "$main/./node_modules/.bin/metafab" build
elif command -v metafab >/dev/null 2>&1; then metafab build
else npx --yes @seasb/metafab@2.0.0 build
fi || echo "metafab: build failed. Run metafab build." >&2
exit 0
# metafab:end
```

`./` is `<factoryRelDir>/`, quoted the same way as in the `cd` line, so `packages/my app` gives `"$main/packages/my app/node_modules/.bin/metafab"`. The shim runs with the current directory still set to the new worktree's factory root, so it builds the new worktree, not the main one. A prototype of this script, run as a real `post-checkout` with a fake shim, built `../wt 2` from `main é/node_modules/.bin/metafab`, and a later `git switch` in the main checkout still used step 1.

`hookCommand(".", "2.0.0")` keeps its single-line form with the same four steps:

```text
(cd "$(git rev-parse --show-toplevel)/." && if [ -x node_modules/.bin/metafab ]; then node_modules/.bin/metafab build; elif main=$(git -c core.quotePath=false worktree list --porcelain 2>/dev/null | sed -n '1s/^worktree //p') && [ -n "$main" ] && [ -x "$main/./node_modules/.bin/metafab" ]; then "$main/./node_modules/.bin/metafab" build; elif command -v metafab >/dev/null 2>&1; then metafab build; else npx --yes @seasb/metafab@2.0.0 build; fi) || true
```

Both come from one private function, `cliLookup(factoryRelDir, cliVersion, args)`, returning the four branch lines (`args` is `"build"` here). `hookScript` joins them with newlines, `hookCommand` with `; `.

### Upgrading

The hook text changes, so the first `build`, `init`, `import` or `update` with the new CLI rewrites all three owned hooks through the content comparison in `syncGitHooks` and prints `~ git hook post-checkout`, `~ git hook post-merge` and `~ git hook post-rewrite` (`hooks` with `action: "updated"` in `--json`). Until then the old hook stays, and since it runs the project's own copy, a project gets the fix once it installs the new version and builds once (`npm run factory` or any hook-triggered build). Hooks shared by worktrees on different Metafab versions are rewritten by whichever builds last, as today.

A line someone pasted by hand into a hook Metafab does not own, or under `core.hooksPath`, is not updated: `build` keeps printing the warning, now with the new line, and the person replaces it. The changelog entry says so.

In this repository, `npm run factory` runs `node dist/cli.js build` and writes the new hooks, but the next hook-triggered build runs the published `node_modules/.bin/metafab` (1.0.0), which writes the old ones back. The by-hand check in `proves` therefore waits for the devDependency to move to a 2.0 prerelease (Plans 2.016 and 2.015). The pull request's proof is the tests and the CI job.

### Failure, repeat runs, Windows

- Any failure in the new step (no `git`, `sed` missing, an unreadable main worktree) makes its condition false and the hook goes on to `PATH`; a failed build still prints the one line and exits 0, and the Git command never fails.
- Repeat runs: unchanged. A second `build` finds matching content and changes nothing.
- Windows: Git for Windows runs hooks with its `sh`, which has `sed`, prints `worktree C:/...` paths with forward slashes, and accepts them in `[ -x ]` and as a command. npm's extensionless `sh` shim beside `metafab.cmd` computes its base directory from `$0`, so it works when run by full path from another directory. Every path is quoted, so spaces are safe. The CI `hooks` job proves this on `windows-latest`. CRLF: the script is written LF as before.

## Tests

Command: `npx vitest run test/core/hooks`. Git is isolated as in Plan 1.016 (`isolateGitConfig`); the shell tests are skipped on Windows, where the CI job covers them.

- `script.test.ts`: the spec example equals `hookScript("post-merge", ".", "1.0.0")`; `hookCommand(".", "1.0.0")` equals the line above; the "same order and version" test lists four steps, in order, for both; `packages/my app` appears quoted in both the `cd` line and the main-worktree path; the snapshot is updated for all three hooks
- `end-to-end.test.ts`, all with a real `git worktree add` and a local fake package: the main checkout gets `node_modules/.bin/metafab` as a logging stub (the `LOGGING_STUB` pattern, writing `main:$PWD`), and `PATH` gets a second stub that logs `path:$PWD`:
  - The new worktree logs exactly `main:<new worktree>`; a later `git switch -c` in the main checkout logs `main:<main checkout>` through step 1
  - Container and worktree names with a space and `é` give the same result
  - With the main checkout's stub removed, the new worktree logs `path:<new worktree>`
  - With the new worktree's own `node_modules/.bin/metafab` present (created before a `git switch` in it), its own copy wins
  - A factory in `packages/app`: the stub at `<main>/packages/app/node_modules/.bin/metafab` runs; a stub only at `<main>/node_modules/.bin/metafab` does not
  - A bare repository with two linked worktrees: adding a third logs `path:`
  - A linked worktree of a submodule (added with `-c protocol.file.allow=always`): logs `path:`, and the Git command exits 0
  - A main-worktree stub that exits 1: the Git command exits 0 and stderr has `metafab: build failed. Run metafab build.`
  - Upgrade: hooks written from the old text (a fixture of the 1.0.0 `post-checkout`) are reported as three `updated` by `syncGitHooks`, and a second run reports none
- CI `hooks` job (Linux and Windows): `dep` becomes `"$tmp/dep space"`. D3 now asserts that `git worktree add ../dep-wt -b b2` builds `../dep-wt/.claude/skills/metafab/SKILL.md` with no `npx stub reached` and no failure line. D4 is unchanged. New D5, after D4 removed the shims: `git worktree add ../dep-wt2 -b b4` builds nothing and reaches the npx stub (D3's control). G1–G3 are unchanged: their repository has no `node_modules`
