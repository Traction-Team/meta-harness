# Plan 1.027: Narrow help detection, isolate the test build, and close the publish and source edge cases

The cold reviews of PR #22 (Plan 1.020) and PR #20 (Plan 1.021), and the build of Plan 1.024, left a set of small defects. None blocked 1.0, and they ship together in 2.0. After this pull request merges: `metafab init -help` is an unknown option, not a help request. The spawned-CLI tests compile their own copy of the CLI and never trust or race over a shared `dist/`. The publish summary prints a Windows-drive `publish.git` in full. `check` names the unsupported scheme of an `upstream.source` such as `ftp://…`, instead of asking for an npm version. `publish.git` values with a `#` either produce an `import` line that names the same repository or are refused by `check`. `git+file://localhost/` is refused as having no path. Cache write errors name the cache entry instead of a temporary directory that is already gone. Three small duplications are removed. And `import` lists the local factory files it kept that the fab does not have.

It closes these intake notes. Everything in them is carried below, so they can be deleted when this plan is ready:

- `docs/intake/2026-11-14-help-cluster-and-test-build.md`: items A1 to A3 and A6 below
- `docs/intake/2026-11-14-publish-label-drive-path.md`: item B1
- `docs/intake/2026-11-14-upstream-source-unsupported-scheme.md`: item B2
- `docs/intake/2026-11-15-publish-git-url-edge-cases.md`: items C1 to C7
- `docs/intake/2026-11-15-import-local-only-files.md`: item D1

Line numbers in those notes are from `main` before Plans 2.011 and 1.026. Both plans change these files, so the builder finds each site by its function name, as written below.

### Spec edits this plan makes

> Only `--help`, `-h` and a repeated `-h` such as `-hh` ask for help. Any other word after one dash is read as a group of short options. So `-help` and `-jh` are unknown options: the command exits with code 1 and writes nothing. When the letters after the single dash spell one of the command's long options, such as `-help` or `-dry-run`, the fix suggests the two-dash form (`--help`).

**`sharing.md`, [Steps](../specs/sharing.md#steps), step 5.** Replace the parenthesis "(`https://` and `file://` URLs gain `git+`, and a `#` in a `file://` path becomes `%23` so the path is not read as a ref)" with:

**`sharing.md`, [Git target](../specs/sharing.md#git-target), step 1.** After "Metafab removes `git+` before it hands the URL to Git.", add:

> In an `https://` URL, write a `#` in the path as `%23`. Git's HTTP transport drops everything after a literal `#`, so the push would go to a different repository. A `git@host:path` URL cannot hold a `#` at all, because an `import` source would read it as the ref and Git does not decode `%23` in that form. ## Design

### A. CLI and test build

**A1. `isHelpToken` (`src/cli.ts`).** It becomes `token === "--help" || /^-h+$/.test(token)`. `helpTarget` and its doc comment change to match ("`--help`, `-h` or `-hh`"). The comment above the `parsed.values.help === true` check says why it stays (see Decisions). Behaviour:

| Command line | Before | After |
| --- | --- | --- |
| `metafab init -help` | Help, exit 0 | `Unknown option '-help'`, exit 1, nothing written |
| `metafab init -jh`, `init -hx` | Help, exit 0 | `parseArgs` error for `-j` or `-x`, exit 1 |
| `metafab init -hh`, `check -hh` | Help, exit 0 | Unchanged |
| `metafab -help` | Global help, exit 0 | `Unknown command: -help`, fix `Did you mean --help?`, exit 1 |
| `metafab import --bogus -h` | Help | Unchanged: help still wins over an unknown option |

**A2. The `-<option>` hint.** Add a new helper `singleDashOption(token, names): string | undefined` in `src/cli.ts`. It returns `<word>` when `token` is `-<word>`, `<word>` is longer than one character, and `names` includes `<word>`. It is used in two places:

- In the `parseCommandArgs` catch in `main`. The rejected token is found by scanning `tokens.slice(consumed)` before `--`, rather than by parsing `parseArgs`'s message. The names are the command's options and `GLOBAL_OPTIONS`. The hint applies only when the first token that `parseArgs` would reject is itself the `-<word>` token: the scan stops at the first token that is not a known option, a known option's value or a positional argument, and gives the hint only if that token matches. Otherwise the original parse error is kept, so `publish --bogus -dry-run` still reports `--bogus` (cold re-review G2). When it matches, the message is `Unknown option '-<word>'`, and the fix is `Did you mean --<word>? Run metafab <command> --help to see its options`.
- In the unknown-command branch, when `first` matches `help`, `json` or `version`. The fix becomes `Did you mean --<word>?`.

Both are `failure(...)` results, exit 1, with one problem that carries a fix, as 1.026 requires. With `--json` they are one JSON object, as every failure is.

**A3. Test build (`test/cli/build.ts`).** The file is rewritten:

```ts
export const repoRoot: string;
/** A private compile of this checkout: `<root>/dist/cli.js`, with package.json and resources/ beside it. */
export interface BuiltCli { root: string; cliPath: string; cleanup(): Promise<void> }
/** Compiles once per test file (memoised in the module), into a directory no other file or run uses. */
export function buildCli(): Promise<BuiltCli>;
/** Compiles the repository's own dist/ with tsc, always. Only the release test calls it. */
export function buildDist(): Promise<void>;
```

`buildCli`:

1. Calls `sweepOld(parent)`, where `parent` is `<repo>/node_modules/.cache/metafab-cli`. It removes, best effort, any child directory older than 24 hours. These are left behind by a test run that was killed.
2. Runs `mkdtemp(path.join(parent, `${process.pid}-`))`.
3. Copies `package.json` and `resources/` into it (`cp`, recursive).
4. Runs `execFile(process.execPath, [tscPath, "--outDir", path.join(root, "dist")], { cwd: repoRoot, timeout: 120_000 })`. Then it sets mode `0o755` on `dist/cli.js`, as the `postbuild` script does.

When `tsc` fails, `buildCli` removes the directory and rethrows with `tsc`'s stdout, so the failing test shows the type error. `cleanup` runs `rm(root, { recursive: true, force: true, maxRetries: 5 })`. The retries are for Windows, where a spawned process that is closing can still hold a file. Callers run `cleanup` in `afterAll`.

`buildDist` runs `tsc` into `dist/` and sets mode `0o755` on `dist/cli.js`. It writes no marker and takes no lock. Deleted: `buildMarker`, `buildLock`, `ownerFile`, `isProcessAlive`, `lockIsStale`, `takeLock`, `takeOverStaleLock`, `newestInputMtime` and `buildIsCurrent`.

Callers:

- `test/cli/e2e.test.ts` uses `built.cliPath` and `built.root`. The test "package.json bin.metafab points at the built entry" checks `path.join(built.root, bin)`.
- `test/core/hooks/end-to-end.test.ts` writes its shim with `built.cliPath`.
- `test/release/package.test.ts` calls `buildDist()` in place of `buildCli()`.

Second run: every run compiles again in about 0.2 s per file, and the old directory is gone. Interrupted run: the directory is left behind and swept after 24 hours. It cannot affect another run, because nothing ever reuses it. Two vitest runs at once on one checkout: each spawning file has its own directory. Only the release test writes `dist/`, so two runs that both run it can still overlap there. That case is out of scope.

The flaky run: on 15 Nov, one `npx vitest run` straight after `npm run verify` failed one test (1272 passed). Nine further runs passed, including one straight after `npm run build`. The failing test was not recorded. The old helper is the likely cause, because `npm run verify` ends with `npm run build` rewriting the shared `dist/`, but this was not proven. After this change, no spawned-CLI test reads the shared `dist/`. The pull request records ten `npx vitest run` runs straight after `npm run verify`. If one fails, the builder records the test name and output, and files the failure with `file-work`, before the pull request is handed over.

**A6. `src/commands/not-implemented.ts`** is deleted. Nothing imports it. Run `grep -rn "not-implemented" src test` to confirm.

### B. Publish label and `upstream.source`

**B1. `targetLabel` (`src/commands/publish.ts`)** calls `sourceWithoutCredentials` (from `src/core/sources/index.ts`; export it there if it is missing) in place of `stripSourceCredentials`. With `publish.git: file://C:\Users\bob@corp\fab.git`, `metafab publish --dry-run` prints `Fab 1.0.0 for git (file://C:\Users\bob@corp\fab.git)`. Before the fix it printed `git (file://C@corp\fab.git)`. `https://user:token@host/fab.git` still prints `git (https://host/fab.git)`. `file://user:pw@localhost/srv/fab.git` prints `git (file://localhost/srv/fab.git)`. The dry run never runs Git, so the test runs on every platform.

**B2. `upstream.source` (`src/core/config/source.ts`, `src/core/config/validate.ts`).** Add a new export:

```ts
/** The error `import` would give for this source, or undefined when it parses. Never throws. */
export function sourceProblem(source: string, cwd: string): { message: string; fix: string } | undefined;
```

It calls `parseSource(source.trim(), { cwd })`. When that throws a `MetafabError`, it returns the message and fix of the error's first problem. 1.026 gives every `invalid-source` error a problem with a fix. If a problem is missing anyway, it returns the error's message and the fix `Write a source metafab import accepts; run metafab import --help`.

`validateUpstream` calls `sourceProblem` after the empty-source checks, with `repositoryRoot ?? process.cwd()`. When it returns a problem, `validateUpstream` reports it as an error on the `source` pair and returns without the version and commit rules. `classifySource` and `parseUpstream` do not change: they never throw.

Result: with `upstream.source: ftp://x/fab.tgz`, `metafab check` prints `Invalid source "ftp://x/fab.tgz": unsupported URL scheme "ftp:". Supported sources: …`, with `parseSource`'s fix line, and exits 1. Before the fix, it printed `"upstream" npm source requires "version"`.

### C. Source and publish edge cases (`src/core/sources/**`, `src/core/publish/**`, `src/core/config/validate.ts`)

**C1. `#` in `publish.git`.**

- `importSourceForGitUrl` (`parse.ts`) encodes `#` as `%23` in the text after `://` for every scheme it is given, not only `file`. Only `https` and `file` gain `git+`. `ssh://git@example.com/my#fab.git` becomes `ssh://git@example.com/my%23fab.git`. A `%23` that is already there is left alone. An scp URL is returned unchanged, as before.
- Rule 7 in `validatePublish` (`validate.ts`), before `isGitUrl`:
  - An `https://` or `git+https://` value whose text after `://` contains `#`. Message `"publish.git" has a # in an https:// URL.` Fix `Write the # as %23, such as https://example.com/my%23fab.git: Git over HTTPS drops everything after a #.`
  - A `git@host:path` value (as `isScpGit` reads it) that contains `#`. Message `"publish.git" has a # in a git@host:path URL, which an import source cannot name.` Fix `Use an ssh:// URL with # written as %23, such as ssh://git@example.com/~/my%23fab.git.`
- Both are errors. `metafab check` exits 1, and `metafab publish` stops at step 1 with the same problem and exit 1. Nothing is published.

**C2. `git+file://localhost/`.** Add a new export in `parse.ts`:

```ts
/** What follows `//` in a `file:` or `git+file:` URL: a path, no path, or a host. */
export function fileUrlAuthority(after: string): "path" | "empty" | "host";
```

The result is `"empty"` for `""`, for `/` repeated, and for `localhost` followed by nothing or by `/` repeated (`localhost/`, `localhost//`, `localhost///`), in any letter case (cold re-review G3). It is `"path"` for a value that starts with `/`, for `localhost/<something>`, and for `DRIVE_PATH`. Every other value is `"host"`. `parseGitFileUrl` uses it: `"empty"` gives `the Git file URL has no path`, and `"host"` gives today's host message.

**C4.** `fileUrlNamesHost` in `validate.ts` becomes `fileUrlAuthority(after) === "host"`, so the authority rule is written once. `git+file://localhost/` and `git+file://LOCALHOST` exit 1 with "no path". They used to name the filesystem root. The same `publish.git` value `file://localhost/` fails rule 7 with the general "not a Git URL" message, because its import line no longer parses.

**C3. Extraction errors name the entry.** The `writeError` callbacks that `fetchGit` (through `exportFactory`) and `fetchNpm` pass to `extractTarball` ignore the staging path they receive. They call `cacheWriteError(fabDir, layout.root, error)`, where `fabDir` is the final entry, so the problem names the same path as the tarball copy in `downloadTarball` (`target`). `exportFactory` gets a new parameter, `reportAs: string`, for this. The `cloneInto` mkdir already names the parent directory and is unchanged. Exit 3 and code `fetch-failed` do not change.

**C5. `isAbsentError`.** One `export function isAbsentError(error: unknown): boolean` (code `ENOENT` or `ENOTDIR`) goes in `src/util/fs.ts`. The private copies in `cache.ts`, `git.ts` and `publish/readme.ts` are deleted and import it instead.

**C6. Round trip with a literal `#`.** A new test in `git-file.test.ts`: `publish.git: file://` plus the bare repository's absolute path in `/`-form, inside a directory named `my#fab` (on Windows `file:///C:/…/my#fab/fab.git`). The path has no space, because `GIT_URL` refuses whitespace. The steps:

1. `publish` exits 0.
2. The generated README's import line contains `my%23fab`.
3. `metafab import <that line>` exits 0 and records it as `source`.
4. A second publish at `1.1.0`, then `update`, moves to `1.1.0`.

**C7. One validation per entry.** In `getOrCreate`:

1. Take `lstat(target, { bigint: true })` before the first `validate(target)`.
2. On failure, take `lstat(target, { bigint: true })` again. If the entry is gone, create it. If `dev`, `ino` and `ctimeNs` are the same `bigint` values as before and `ino !== 0n`, move the entry aside without validating it again. Otherwise validate it again, as today. When either `lstat` fails with `ENOENT` or `ENOTDIR`, the entry is absent: create it, as when it vanished before. Any other `lstat` error falls back to today's path (validate again, then move aside or create), so the change can only skip a validation, never add a failure (cold re-review G2). The comparison uses `bigint` stats for the reason Plan 1.019 did: NTFS file indexes can exceed `Number.MAX_SAFE_INTEGER`, so two entries could compare equal as numbers.

The `create` callbacks in `fetchGit` and `fetchNpm` stop calling `dropPayloadFiles`/`validateFab` and `validateExtractedFab` on the staging directory, because `getOrCreate`'s own `validate(staging)` does the same work. The concurrency tests from 1.021 must still pass unchanged.

Windows: `ino` from `lstat` comes from the NTFS file index and is stable. When it is 0 (some network filesystems), the check falls back to validating again. A unit test injects two `lstat` results whose `ino` values differ by one above `Number.MAX_SAFE_INTEGER` and asserts the entry is validated again. Two more inject a removal of the entry before the first and before the second `lstat`, and assert the entry is created with no error. The existing vanished-target test keeps its interleaving; if it relied on the number of `validate` calls, the builder asserts the outcome (the entry is recreated and valid) instead.

### D. Kept local files (`src/core/summary.ts`, `src/core/import/run.ts`)

- `SummaryGroupKey` gains `"kept"`. `HEADINGS.kept` is `Local files kept, not in the fab`. The order becomes code, session, setup, workflows, skills, other, kept, preserved, conflicts. `SummaryContext` gains `kept?: string[]` (`import` only). Each entry is `{ path }`, sorted, and drawn as a bare path, the same way `preserved` entries are.
- In `runImport`, after `copyFactoryTree` and the `after` snapshot: `kept` is every key of `after` that is not in the fab's file set and is not `metafab.yaml`. The fab's file set is the keys of `fabTree`, without `FAB_ROOT_EXCLUDES` at the root. A path at or under an adopted skill directory is also left out: each `plan.moves[].to`, made relative to `.factory/` with `/` separators. `kept` is computed from `after`, not `before`, so a local-only file that moved with a case realignment shows under its new spelling. A local `.factory/README.md` is listed, because the fab's README is never copied. That file is the case reported from Plan 1.024.
- `--json`: `review.groups` includes `{ key: "kept", heading, entries: [{ path }] }`. This is the same shape as every other group.
- A first import into a repository with no `.factory/` has an empty `kept` group, so the group is not shown. An import without `--force` that keeps local-only files shows them too.
