# Plan 2.010: A git backend keeps the store on a ref of this or another repository

A team that wants a shared store but no server can now keep it in Git. With `backend: git`, the store lives as commits on `refs/metafab/store` in the repository itself (the default), or on a branch of a separate repository. Access and credentials are Git's own, so there is no account and no `login`. Every change is one commit, pushed only if the ref has not moved; when another developer pushed first, the CLI fetches and applies the same change again, so work that does not overlap lands and an overlapping edit becomes an ordinary conflict. This is not documents on code branches: the ref is trunk-only, written only by the CLI, and never part of a pull request, so none of the Git ceremony the store removes comes back. It reuses the local backend's checks and file layout, so it behaves like every other backend and passes the same contract suite. After it merges, a team chooses between Metastore Cloud, its own server, a Git ref, and a local directory.

## Specs

- [Store: Backends](../specs/store.md#backends): [Git](../specs/store.md#git), and the shared rule that every backend gives the same results
- [Store: Configuration](../specs/store.md#configuration): the `remote`, `ref`, `repository` and `branch` keys, and rules 2, 4 and 5
- [Store: Limits](../specs/store.md#limits): the 50 MB blob limit for Git
- [Store: Credentials](../specs/store.md#credentials) and [Command behaviour](../specs/store.md#command-behaviour): exit code 6
- [Store: Security and privacy](../specs/store.md#security-and-privacy)

No spec edits: the spec already describes this behaviour, including the exception in [Command behaviour](../specs/store.md#command-behaviour) rule 4 that lets the Git backend commit and push its own store ref.

## Decisions

Proposed in this plan, for approval:

| Topic | Choice | Reason |
| --- | --- | --- |
| Default | A ref of this repository, `refs/metafab/store` at `origin` | Zero setup: the team already shares this repository and its permissions |
| Ref outside `refs/heads/` | Yes by default; `ref: refs/heads/<name>` allowed for teams that want to browse it | Code clones and fetches never download it, and it never appears as a branch or in a pull request |
| How a change lands | Applied with the local backend's code to a checkout of the fetched tip, committed with that tip as parent, pushed without force | A plain push of a child commit is refused if the ref moved, which is the lease the spec asks for, with no force |
| A lost race | Fetch, apply the same change to the new tip, push; up to five tries with growing, random waits; then exit 6 | The base-version checks run again, so only a real overlap becomes a conflict |
| Reads when the remote is unreachable | The cached state, with a warning in the result | Agents can still read plans offline; writes cannot be offline |
| Where the cache lives | `<cacheRoot()>/store/<key>/`, beside the fab download cache | One cache per store per machine, shared by every worktree on it; `METAFAB_CACHE` already redirects it for tests |
| Blobs | Kept in the commits, limit 50 MB | GitHub refuses files over 100 MB and warns over 50 MB |
| Git prompts | Never: every Git command in the cache runs with `gitEnvironment(…, interactive: false)`, so `GIT_TERMINAL_PROMPT=0`; a refused fetch suggests a credential helper or an SSH key | Store commands run inside agent sessions and hooks with no one to answer; Git's own stored credentials and SSH agents still work |
| Identity | One identity from `git config user.name` and `user.email` in the code repository (else `metafab` and `metafab@localhost`), used for versions, scores, `info()` and commit authors | One answer to "who saved this", wherever a person looks |

## Design

### Configuration (`src/core/config/types.ts`, `parse.ts`, `validate.ts`)

`StoreConfig.backend` becomes `"remote" | "git" | "local"`, and gains `remote?: string`, `ref?: string`, `repository?: string` and `branch?: string`. `validate.ts` adds the spec's rule 5 and the new half of rule 4, each an error on `.factory/metafab.yaml` at the key's line:

- `"repository" cannot be combined with "remote" or "ref"`, fix `Use remote and ref for a store in this repository, or repository and branch for a separate one`
- `"branch" needs "repository"`; `"<key>" is only for backend: git`
- `remote`: follows Git's ref name rules below as a path of one or more components (so `team/store` is valid) and does not start with `-`, else `"remote" must be a Git remote name`. Whether the remote exists is checked when a command runs, not by `check`
- `ref`: starts with `refs/` and not with `refs/tags/` or `refs/remotes/`; Git's ref name rules checked without Git (no `..`, `@{`, `\`, space, control character, `~ ^ : ? * [`; no segment starting with `.` or ending with `.lock`; no `//`; not ending with `/` or `.`), else `"ref" is not a valid ref for the store`
- `branch`: what `git check-ref-format --branch` accepts, checked without Git: the ref name rules above for `refs/heads/<branch>`, and the name does not start with `-` and is not `HEAD`, else `"branch" is not a valid branch name`
- `repository`: matches `https://…`, `ssh://…`, `user@host:path` or `file://…`, and an `https` URL has no user or password, else `"repository" must be a Git URL without credentials`

The unknown-key list for `didYouMean` gains the four keys.

### Target (`src/core/store/git/target.ts`)

```ts
export interface GitTarget { fetchUrl: string; ref: string; id: string; key: string }
export async function resolveGitTarget(repoRoot: string, config: StoreConfig, git?: GitRunner): Promise<GitTarget>;
```

- In this repository: `git remote get-url <remote ?? "origin">` in the repository root. Outside Git, exit 1, `backend: git needs a Git repository, or a repository URL`. A missing remote, exit 1, `This repository has no remote "<remote>"`, fix `Add it, or set store.remote in .factory/metafab.yaml`. `ref` is `config.ref ?? "refs/metafab/store"`.
- In a separate repository: `fetchUrl` is `repository`, `ref` is `refs/heads/<branch ?? "main">`.
- `id` is `git:<canonical URL>#<ref>`. The canonical URL is `stripSourceCredentials(fetchUrl)` (`src/core/sources/redact.ts`) with the host lowercased and a trailing `/` removed, keeping the scheme, user name of an SSH URL, port and path, so two repositories that differ only by port or scheme never share a cache or a state file. `normalizeRepoUrl` is not used here, because it drops those parts on purpose for `origin.repo`. `key` is the first 16 hex of the SHA-256 of `id`, the cache folder name.

**Credentials in URLs.** A remote URL may carry a token, such as `https://x:ghp_…@github.com/…`. `fetchUrl` is kept only in memory and passed to Git as an argument. Nothing written to disk holds it: `meta.json` stores `id`, which has no credentials. Every Git error line that reaches a message, a notice or `--json` goes through `redact` from `src/core/sources/redact.ts` first.

`backendIdFor` in `open.ts` returns the same `id` (it is asynchronous from Plan 2.003, so callers already await it); it runs `git remote get-url`, which reads local configuration only, so `check` still makes no network request.

### Cache (`src/core/store/git/cache.ts`)

`<cacheRoot(env)>/store/<key>/` holds:

```text
repo.git/          a bare repository, created with git init --bare on first use
tree/              a checkout of the fetched tip, in the local backend's layout
pending-blobs/     blobs prepared by putBlobs and not yet committed
meta.json          { "id", "ref", "tip": <sha or null>, "fetchedAt": <time> }   (no URL, so no credentials)
lock/              the cache lock (src/util/lock.ts, waits up to 30 s)
```

**Opening and repairing the cache.** Before its first use in a command, under the cache lock, `openCache` checks that `meta.json` parses and names this `id`, that `git --git-dir=repo.git rev-parse --git-dir` succeeds, and that `tree/` is a directory. If any check fails, including after an interrupted first run, it deletes `repo.git`, `tree` and `meta.json` (keeping `lock/` and `pending-blobs/`), creates them again, and the next fetch fills them. Nothing in the cache is the only copy of anything: the remote holds every committed change, so a rebuild loses nothing but time.

**Git missing.** When `git` is not installed (`runGit` throws `ENOENT`), every Git backend operation, and `backendIdFor` in this-repository mode, exits 1 with `backend: git needs Git, which is not installed`, fix `Install Git, or choose another backend in .factory/metafab.yaml`.

Every Git command in the cache runs through `runGit` with `gitEnvironment` and `disabledHooksConfig` from `src/core/sources/git-process.ts`, so it never prompts (see Decisions) and never runs a hook. The index used to build commits is `repo.git/store-index` (`GIT_INDEX_FILE`), never the code repository's. `tree/lock/` and `tree/` files that the local backend does not own are excluded from commits by the pathspec `:(exclude)lock`.

### Sync (`src/core/store/git/sync.ts`)

```ts
export async function fetchTip(cache: Cache): Promise<{ tip: string | null } | { unreachable: string }>;
export async function checkout(cache: Cache, tip: string | null): Promise<void>;
export async function commitAndPush(cache: Cache, message: string, author: GitIdentity): Promise<"pushed" | "unchanged" | "lost-race" | { refused: string }>;
```

- `fetchTip`: `git ls-remote <fetchUrl> <ref>`. No line means an empty store (`tip: null`). Otherwise `git fetch --no-tags <fetchUrl> +<ref>:refs/metafab/tip`. After every successful fetch, including an empty store, it rewrites `meta.json` with `tip` and `fetchedAt` (temporary file and rename). A network or authentication failure returns `unreachable` with Git's first error line, redacted, and leaves `meta.json` as it was.
- `checkout`: for a tip, `git read-tree --reset -u <tip>` with `--work-tree=tree`, then `git clean -fdq -e lock` there, so `tree/` holds exactly the tip, updating only what changed. For `null`, `tree/` is emptied except `lock/`.
- `commitAndPush`: `git add -A -- . ":(exclude)lock"`, `git write-tree`; when the tree equals the tip's, `unchanged`. Else `git commit-tree <tree> [-p <tip>] -m <message>` with `GIT_AUTHOR_*` and `GIT_COMMITTER_*` from `git config user.name` and `user.email` in the code repository (else `metafab` and `metafab@localhost`), then `git push --porcelain <fetchUrl> <commit>:<ref>`. A `!` line whose reason is `non-fast-forward` or `fetch first` is `lost-race`; any other refusal is `refused` with the reason (for example a pre-receive hook's message). On `pushed`, `meta.json`'s `tip` becomes the commit.

### Backend (`src/core/store/git/backend.ts`)

`class GitBackend implements StoreBackend` wraps a `LocalBackend` over `tree/`, constructed with `limits: { ...DEFAULT_LIMITS, blobBytes: 50 * 1024 * 1024 }` and `identity` (the Git identity above). `LocalBackend`'s constructor gains `identity?: Identity` (`src/core/store/local/`); when given, it is `savedBy` and `recordedBy` and `info().identity`, instead of the local backend's own `local:<name>` default.

- **Reads** (`info`, `list`, `get`, `versions`, `readBlob`, `listScores`, `scoreNames`): the first read in the backend's life takes the cache lock, runs `fetchTip` and `checkout`, and releases it. When `fetchTip` is `unreachable` and `meta.json` has a `fetchedAt`, it keeps the cached `tree/` and adds a notice `Read from the store as fetched at <fetchedAt>` (warning, file `.factory/metafab.yaml`, fix `Check the network or your Git credentials`). With no cache at all, it throws exit 6 `store-unreachable` with Git's line. Later reads use the same state.
- **`putBlobs`**: under the cache lock, checks each blob's size against the 50 MB limit, writes its bytes to a temporary file in `pending-blobs/`, checks the file's size and SHA-256, and renames it to `pending-blobs/<sha256>`. A mismatch removes the temporary file and throws. So a pending blob is complete or absent. Nothing is fetched or pushed.
- **`apply(request, key)`** and **`recordScores(scores)`**: take the cache lock, then up to five times:
  1. `fetchTip` (`unreachable` → exit 6 `store-unreachable`) and `checkout`.
  2. Copy the pending blobs the request names into `tree/blobs/`.
  3. Run the `LocalBackend` method on `tree/`. Its checks and its idempotency record are the local backend's, so a key already in the catalog returns its first outcome.
  4. `commitAndPush` with the request's `message` (for scores, `record <n> scores`). `unchanged` or `pushed` → release the lock and return the outcome. Pending blobs are never removed here: another command on this machine may have staged the same content-addressed blob and still need it. Instead, `putBlobs` and `apply` first delete, under the cache lock, pending blobs older than 24 hours, which no command still running can need. `refused` → exit 6 `store-forbidden` with Git's reason. `lost-race` → wait `250 ms × 2^try` plus up to 250 ms at random, and try again.

  After five lost races: exit 6 `store-busy`, `The store is busy; try again`. Whenever the loop ends without `pushed` or `unchanged` (busy, refused, unreachable, or an error thrown by the local layer), `checkout(meta.tip)` resets `tree/` to the last fetched tip before the error is returned or thrown, so no later read in this or another command sees a change that never landed.
- **`info()`**: `{ protocol: 1, id, name: <id>, identity: { id: "git:<email>", name: <user.name> }, limits, capabilities: [] }`.
- **`notices()`**: returns and clears the notices.

`StoreBackend` (`src/core/store/backend.ts`) gains the optional `notices?(): Problem[]`. `openMirrorContext` (`src/core/store/mirror/context.ts`) makes `ctx.problems` a getter that appends `backend.notices?.() ?? []` each time it is read, so a command that builds its result at the end includes them, in text and `--json`.

### Commands

`login` and `logout` with `backend: git` and no `--url`: summary `The git backend uses Git's own credentials; there is nothing to sign in to`, exit 0.

### Edge cases

- **Two worktrees on one machine** share the cache, and the cache lock serialises them.
- **A push whose response was lost.** The next command fetches a tip that already holds the change; a retry with the same key returns the first outcome, and a new push finds identical content (Plan 2.005's recovery).
- **A non-fast-forward by someone rewriting the ref.** It is a lost race like any other; the next fetch takes the rewritten tip.
- **The ref in a repository with branch protection on `refs/heads/*`.** `refs/metafab/store` is outside it; a host that refuses custom refs gives `store-forbidden` with its message, and the fix suggests `ref: refs/heads/<name>` or a separate repository.
- **Windows.** Paths in the cache are joined with `path.join`; Git runs through `execFile`; `read-tree -u` writes LF as stored, because the cache repository sets `core.autocrlf false` when it is created.
- **A huge history.** `checkout` updates only changed files; the version files grow with every change, which is the trade-off the spec names.

## Tests

All Git remotes are local bare repositories (`file://`); no test reaches the network.

- Contract suite against `GitBackend` in both modes, in `test/core/store/contract.test.ts`.
- Two machines: two `METAFAB_CACHE` folders, two child processes each saving ten changes to different paths at once; every change is on the ref afterwards, and at least one push retried. An overlapping edit from the second machine returns `conflict`.
- Busy: a test wrapper that pushes a competing commit before each of our pushes; the sixth attempt never happens and the command exits 6 with `The store is busy; try again`.
- Unreachable: the bare repository is renamed away; `status` and `show` use the cache and the JSON `problems` hold the warning; `push` exits 6; with no cache at all, `pull` exits 6.
- Refused: a pre-receive hook in the bare repository that rejects; exit 6 with the hook's message; a `list` afterwards does not show the refused change.
- Credentials: with a remote URL holding `user:secret@`, neither `meta.json`, nor any message, notice or `--json` output contains `secret` (a failing fetch makes Git print the URL).
- Identity: a saved version's `savedBy`, a score's `recordedBy`, `info().identity` and the commit author all name the Git user.
- Prompts: with no credentials available, fetch fails at once with exit 6 instead of waiting for input.
- Pending blobs: a blob whose bytes do not match is refused and leaves no file in `pending-blobs/`.
- Metadata: after fetching an empty store, `meta.json` has `tip: null` and a `fetchedAt`, and a later offline read uses it.
- Remote names: `remote: team/store` is valid; `remote: -x` and `remote: a..b` are not. Branches: `branch: -x`, `branch: HEAD` and `branch: a.lock` are refused; `branch: feat/x` is valid.
- Identity of stores: `https://host:8443/a/b.git` and `https://host/a/b.git` get different ids and cache folders.
- Pending blobs: two commands staging the same blob, one finishing first, leave the blob for the other; a pending blob older than 24 hours is removed.
- Repair: a cache with a damaged `meta.json`, one with `repo.git` deleted, and one interrupted after `git init` are each rebuilt, and the command succeeds.
- No Git: with `PATH` emptied for the child process, `pull` exits 1 with `backend: git needs Git`, in both modes.
- Empty store: the first push creates the ref as a root commit; `ls-remote` shows it.
- Isolation: `git clone` of the code repository and a plain `git fetch` do not create `refs/metafab/store`; the cache's commits never contain `lock/`; a hook in the cache repository does not run; the code repository's index and working tree are untouched by every operation.
- Blobs: a 2 MB blob over a lowered limit is refused; pending blobs survive a lost race and are committed with the change.
- Configuration: every rule 5 case; `name` and `url` with `backend: git`; `branch` without `repository`.
- `login` with `backend: git` prints the message and exits 0.
