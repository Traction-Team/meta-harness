# Plan 1.016: Git hooks keep installed skills current

Installed skills are ignored by Git, so a new worktree has none, and a pull, branch switch or rebase leaves them stale until someone runs `metafab build`. This plan adds a team setting, `git-hooks: true` in `metafab.yaml`. With it on, every `build` installs `post-checkout`, `post-merge` and `post-rewrite` hooks that run `metafab build`, and `init` offers to turn it on. `init` also suggests the setup step for Orca worktrees, and the built-in `metafab` skill documents every way to keep the skills current. After this merges, a team that says yes once never has to remember to rebuild locally.

- [Building: Built-in `metafab` skill](../specs/building.md#built-in-metafab-skill)
- [CLI: Set up a factory](../specs/cli.md#set-up-a-factory): `--git-hooks`, `--no-git-hooks`, the `orca.yaml` suggestion
- [Configuration: Top-level keys](../specs/configuration.md#top-level-keys): `git-hooks`

The spec text was agreed and written with this plan (docs commit on `main`). Change it in this pull request only where the build proves it wrong, and say so in the body.

## Decisions

| Topic | Choice | Reason |
| --- | --- | --- |
| Team or personal setting | Team: `git-hooks` in the committed `metafab.yaml`, applied by every `build` | One decision per team; a teammate gets the hooks after their first build |
| Agent session-start hooks, `build --watch` | Not built | Decided 2026-10-31 |
| Which metafab a hook runs | `node_modules/.bin/metafab`, then `metafab` on `PATH`, then `npx --yes @seasb/metafab@<version>` | A new worktree has no `node_modules`, so npx is the usual case; `PATH` lets a global or `npm link` install work offline. The version is pinned to the CLI that wrote the hook, so a checkout never upgrades Metafab silently |
| Foreign hooks, `core.hooksPath` (husky and others) | Leave them alone, warn, and print the lines to add by hand | Decided 2026-10-31: never edit a hook Metafab did not create |
| Where hook sync runs | At the end of `applyBuild`, so `build`, `init`, `import` and `update` all apply it. `check` and `planBuild` never touch hooks | Hooks follow the config like every other build output, but they are local, so `check` (which also runs in CI) ignores them |
| `init` without a terminal and without a flag | Leave `git-hooks` absent (off). Do not exit 2 | Hooks are optional; an agent or CI `init` must not stop on them |
| `import` | Does not ask about hooks | `import` is Plan 1.009's command. A team turns hooks on with `init --git-hooks` or by editing `metafab.yaml` |
| Orca suggestion | Only when `init` creates `metafab.yaml` and `orca.yaml` exists without `metafab build`. Never edits `orca.yaml` | The person asked for a suggestion on first install, not a write into another tool's file |

## Design

### Configuration

- `types.ts`: `Config.gitHooks: boolean`, defaulting to `false`.
- `parse.ts`: read `git-hooks` the way `metafab-skill` is read.
- `validate.ts`: add `git-hooks` to `TOP_LEVEL_KEYS`; a non-boolean value is the error `"git-hooks" must be a boolean.` (rule 3).
- `writers.ts`: `createConfigText` takes an optional `gitHooks`, and a new `setGitHooksText(text, value)` / `setGitHooks(factoryDir, value)` sets the key without losing comments, in the same style as `setUpstreamText`. A new file lists `agents`, then `git-hooks` when given.

### Hooks module (`src/core/hooks/`)

```ts
export const HOOK_NAMES = ["post-checkout", "post-merge", "post-rewrite"] as const;
export type HookName = (typeof HOOK_NAMES)[number];

export interface HookChange { hook: HookName; action: "created" | "updated" | "removed" }

export interface HookSync { changed: HookChange[]; warnings: Problem[] }

/** The full text Metafab writes for one hook. Pure; unit-tested on every platform. */
export function hookScript(hook: HookName, factoryRelDir: string, cliVersion: string): string;

/** Applies the Git hooks rules in docs/specs/building.md#git-hooks. Never throws for Git problems. */
export async function syncGitHooks(root: string, enabled: boolean, cliVersion: string): Promise<HookSync>;
```

`syncGitHooks`:

1. Ask Git with `runGit` (`src/util/git.ts`) from `root`, and read each answer this way:
   - `rev-parse --show-toplevel` and `rev-parse --git-common-dir`. A non-zero exit, or `runGit` throwing because `git` is missing (`ENOENT`), means "not a Git repository": return no changes, and one warning only when `enabled`. `--git-common-dir` prints a relative `.git` in the main worktree and an absolute path in a linked one, so `path.resolve(root, output.trim())`.
   - `config --get core.hooksPath`. Exit 0 means it is set. Exit 1 means unset, which is the normal case. Any other exit gives one warning and no writes.
2. `factoryRelDir` comes from `git rev-parse --show-prefix` run with `cwd: root`, with the trailing `/` removed. Empty means `.`. Do not compute it with `path.relative`: on macOS a temp directory is `/var/...` while Git reports `/private/var/...`. The script quotes it.
3. `core.hooksPath` set: no creates or rewrites. With `enabled`, add one warning whose `fix` holds the command line to add to each hook. Removal (step 4, `enabled` false) still runs on `<common-dir>/hooks/`, because a team may have set `hooksPath` after Metafab wrote hooks there.
4. For each hook in `<common-dir>/hooks/` (create the directory when it is missing, `enabled` is true, and `hooksPath` is unset):
   - Missing and `enabled`: write `hookScript(...)` with mode 0755, `created`.
   - Owned (contains a line exactly `# metafab:start`). Read the factory it serves from its `cd` line: the text between `$(git rev-parse --show-toplevel)/` and the closing quote. When there is no `cd` line or it cannot be parsed (hand-edited, or an older format), treat the hook as this factory's.
     - It names a different `factoryRelDir`: leave it, in every state. Warn only when `enabled` (rule 6 wins over rule 4, so one factory never deletes another's hook).
     - `enabled` and the content matches: nothing.
     - `enabled` and the content differs: rewrite, `updated`.
     - Not `enabled`: delete it, `removed`.
   - Exists, not owned, and `enabled`: leave it and warn.

Exact warnings. `file` is the hook path relative to the root, for example `.git/hooks/post-merge`. For the `core.hooksPath` and No Git rows it is `.factory/metafab.yaml`. `<command>` is `hookCommand(factoryRelDir, cliVersion)`, the single line `(cd "$(git rev-parse --show-toplevel)/<dir>" && if [ -x node_modules/.bin/metafab ]; then node_modules/.bin/metafab build; elif command -v metafab >/dev/null 2>&1; then metafab build; else npx --yes @seasb/metafab@<version> build; fi) || true`. It uses the same resolution order as the hook.

| Case | `message` | `fix` |
| --- | --- | --- |
| Foreign hook | `<file> exists and was not written by Metafab` | `Add this line to <file>: <command>` |
| `core.hooksPath` | `core.hooksPath is set, so Metafab did not install Git hooks` | `Add this line to post-checkout, post-merge and post-rewrite in <hooksPath>: <command>` |
| Another factory's hook | `<file> runs metafab build for <other dir>` | `Git hooks support one factory per repository; set git-hooks: false in one of them` |
| No Git | `git-hooks is true, but this is not a Git repository or git is not installed` | `Install Git, or set git-hooks: false` |
5. Compare content after CRLF → LF. Write LF.

`hookScript` follows the spec example exactly. Its cd line is `cd "$(git rev-parse --show-toplevel)/<factoryRelDir>" 2>/dev/null || exit 0`. The hook script is authoritative. `hookCommand` is the one-line form given to people in warnings, and a test checks that both use the same resolution order and package version. `post-checkout` adds `[ "$3" = "1" ] || exit 0` and `post-rewrite` adds `[ "$1" = "rebase" ] || exit 0`, right after the generated comment. The script must be valid POSIX `sh` (no bashisms), because Git for Windows runs hooks with its bundled `sh`. On Windows, npm writes an extensionless `sh` shim at `node_modules/.bin/metafab` beside the `.cmd` one, so `[ -x ... ]` and `command -v` work under Git's `sh`. This is not tested on Windows CI; record it as a manual check for Plan 1.012's Windows pass.

### Build (`src/core/build/`)

- `BuildReport` gains `hooks: HookChange[]` and `hookWarnings: Problem[]`. Both callers, `src/commands/build.ts` and `runInit`, build their warning list before `applyBuild`, so each merges `report.hookWarnings` into `problems` afterwards; `--json` carries them like any other warning. `applyBuild(plan)` calls `syncGitHooks(plan.root, plan.gitHooks, plan.cliVersion)` after the file writes. `BuildPlan` already has `root`; `planBuild` adds `gitHooks: boolean` (from `config.gitHooks`) and `cliVersion: string`. A hook failure never fails the build: unexpected file errors become warnings.
- `src/commands/build.ts`: the summary prints `+ git hook post-checkout` (and `~`, `-`) after the file lines, and they count in the total. `--json` adds `hooks` to the result.

### Init (`src/core/init/`, `src/commands/init.ts`)

- New boolean options `--git-hooks` and `--no-git-hooks`, declared as two separate options, because Node 20's `parseArgs` has no `allowNegative`. Both together exit 1 with `Pass --git-hooks or --no-git-hooks, not both`, before any write.
- After the adoption consent is settled (so a declined adoption never asks, and a yes is never thrown away), and before any write, decide the hooks value when `git-hooks` is absent from the existing config (or there is none): a flag, else `confirm({ name: "git-hooks", flag: "--git-hooks", description: "Run metafab build automatically after checkout, merge, and rebase?" }, { default: true }, io)` in a terminal, else leave it absent. Declining writes `git-hooks: false`, so the next `init` does not ask again.
- "Absent" means the key is not in the file. Add `gitHooksRaw: boolean | undefined` to `Config`, as `agentsRaw` is done, and test `config.gitHooksRaw === undefined`.
- Write the value with `createConfig` (new file) or `setGitHooks` (existing file). An existing value is never changed, even if a flag is given. Report that in a new `InitReport.notes: string[]` as `git-hooks is already <value> in .factory/metafab.yaml`. `describeInit` prints notes even on an otherwise unchanged run (after `Already initialised`), and `--json` includes `notes`.
- The closing build installs the hooks through `applyBuild`. `InitReport` gains `hooks: HookChange[]`, printed like `build`'s hook lines and included in `--json`. `describeInit` counts hook changes in `seemsComplete`, so an `init` that only rewrote hooks does not print `Already initialised`.
- Orca suggestion: when this run created `metafab.yaml`, `orca.yaml` exists at the root, and its text does not contain `metafab build`, add to `InitReport.suggestions: string[]` the text `Add "npx --yes @seasb/metafab build" to scripts.setup in orca.yaml so new Orca worktrees get the factory skills.` `describeInit` prints suggestions last, and `--json` includes `suggestions` (empty array when none).
- Replace `init`'s private `cliVersion()` with the one from `src/util/version.ts` (Plan 1.015).
- Dangling links (from the cold review of PR #14): `ensureFactoryFiles` in `run.ts` checks `.factory/AGENTS.md` with `pathExists`, and `ensureGitattributes` reads `.gitattributes` with `readFile` and treats `ENOENT` as missing, so a dangling symbolic link counts as missing and `writeFile` creates its target, possibly outside the repository. Add a preflight beside `assertFactoryFileReadable`, run before `ensureFactoryFiles` and any other write, that checks both paths with `lstat`. Export the `.gitattributes` half as `assertGitattributesWritable(root, command: "init" | "import")` from `gitattributes.ts`, with `command` in the message and fix (`so metafab <command> will not write through it`, `then run metafab <command> again`): `import` also calls `ensureGitattributes`, and Plan 1.018 (which owns `src/core/import/**`) calls the same check from `runImport`. For `.gitattributes`, "would write" means `addGitattributesLines` reports a change for the link's current content (a dangling link counts as empty). A symbolic link at either path (dangling or not) that `init` would write through stops `init` with exit 1, code `factory-unreadable`, message `<path> is a symbolic link, so metafab init will not write through it`, fix `Replace it with a regular file, then run metafab init again`. A link to an existing file that needs no write is left alone. The exit code is 1, not 5: this matches 1.014's refusal of an unreadable `.factory/factory.yaml`, and a link the user made is not build output Metafab failed to own. Add the rule to [CLI: Set up a factory](../specs/cli.md#set-up-a-factory).

## Tests

Every Git test uses a temporary repository and local commits only. Each test isolates Git from the machine: `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` point at empty files in the temp directory, and each repository sets `user.name` and `user.email`. A developer's global `core.hooksPath` must not change a result. The shell-executing tests are skipped on Windows (`it.skipIf(process.platform === "win32")`). On Windows, the content tests still run.

- `hookScript("post-merge", ".", "1.0.0")` equals the literal example in [building.md#git-hooks](../specs/building.md#git-hooks), compared as a string and not as a snapshot. Each warning in the table above is asserted with its exact `message` and `fix`
- `hookScript`: snapshot per hook. `post-checkout` exits for a file checkout (`$3 = 0`). `post-rewrite` exits for `amend`. The factory directory is quoted (a directory with a space)
- Config: `git-hooks: "yes"` is a type error. A missing key gives `gitHooks: false`. `setGitHooksText` keeps comments and other keys
- `syncGitHooks` enabled: creates three 0755 files. A second run changes nothing. Changing the CLI version rewrites all three as `updated`
- A foreign `post-merge` (no marker): unchanged, with one warning that names it and gives the line. The other two hooks are still created
- `core.hooksPath` set: no files written, one warning
- `core.hooksPath` set after hooks were written, then `git-hooks: false`: the owned hooks in `.git/hooks/` are removed
- Disabled: owned hooks removed, a foreign hook untouched
- `git` missing (`PATH` without git): no changes, one warning when enabled, and `build` still exits 0
- Linked worktree: `build` run inside `git worktree add` output writes to the shared `.git/hooks/`, not to `.git/worktrees/<name>/hooks/`
- Hook warnings appear in `build --json` `problems` and in `init`'s output
- Not a Git repository: no changes. Enabled gives one warning
- End to end, with a stub `metafab` on `PATH` (a shell script that appends to a log file in the temp directory): after `build` with hooks on, `git worktree add ../wt -b x` logs one build in `../wt`, `git merge` logs one, `git rebase` logs two (Git runs `post-checkout` for the rebase's checkout and then `post-rewrite`; the second build changes nothing, which is accepted), `git commit --amend` logs none, and `git checkout -- file` logs none
- A hook whose build fails still lets the Git command succeed and prints `metafab: build failed. Run metafab build.`
- Monorepo: a factory in `packages/app/` writes `cd ".../packages/app"`. A second factory in another directory sees the owned hook and warns
- `init` in a terminal: answering yes writes `git-hooks: true` and installs hooks; answering no writes `false`; without a terminal and without flags the key stays absent and the exit code is 0. `--git-hooks` and `--no-git-hooks` skip the question. Both flags together is a usage error. An existing value is not changed
- `init` with `orca.yaml` and no `metafab build` in it: the suggestion is in the summary and in `suggestions`. With `metafab build` already in `orca.yaml`, or on a second `init`: no suggestion
- `build --json` includes `hooks`
- `init` with `.factory/AGENTS.md` or `.gitattributes` as a dangling link (`-> ../outside`): exit 1 with the message above, the link's target is not created, and no factory file (`factory.yaml`, `metafab.yaml`) was written. A `.gitattributes` link to an existing file that already has the lines: unchanged, exit 0. Skipped on Windows (`it.skipIf(process.platform === "win32")`), as the other symlink tests in `test/core/init/` are
