# Plan 1.012: Release v1

Publish `@seasb/metafab` 1.0.0 from a tagged release workflow with provenance, with a package README, and turn on Git hooks in this repository once the package is on npm.

On 12 Nov (prioritise-roadmap) this plan was split. Its hardening steps moved to [Plan 1.021](1.021-source-hardening.md) (fab sources) and [Plan 1.022](1.022-verification.md) (CI recipe, Windows pass, error messages, `--json`). Agent tool verification moved to Plan 1.022. The first fab moved to [Plan 1.024](1.024-first-fab.md), which generalises the Dragonfly factory as `@seasb/fab-basic` instead of porting Mark IV. This plan keeps only the package release.

## Specs

- [README: Version 1 scope](../specs/README.md#version-1-scope)
- [CLI: Installation](../specs/cli.md#installation)

Spec edits this plan makes, all in `README.md`:

- The glossary's fab examples and the quick-start name `github:Traction-Team/fab-basic` first and `@seasb/fab-basic` as the optional npm form; the quick-start imports the Git source and passes `--setup`.
- The quick-start stages what `--setup` creates: `git add .factory AGENTS.md .gitignore .gitattributes opencode.json orca.yaml docs/` (no `CLAUDE.md`: `build` never creates one, so naming it fails `git add` in a fresh repository; a repository that already has one stages it too), and its commit messages say "Add the fab-basic factory" and "Update the fab-basic factory to 1.3.0".
- The "installs factory parts" table's Template row becomes "Not installed. Workflows use its repository path. A template named by `requires` in `factory.yaml` is copied by `import` and `update` to create a missing repository file (Plan 1.023)".

 The `@seasb/fab-mark4` examples in `sharing.md`, `configuration.md` and the tests stay: they are illustrations, not a package anyone installs.

## Decisions

| Topic | Choice | Reason |
| --- | --- | --- |
| npm authentication | npm trusted publishing (OIDC) for `.github/workflows/release.yml` on this repository, configured on npmjs.com by the person before the first tag, with `npm publish` allowed as well as the `npm stage publish` every configuration gets. No `NPM_TOKEN` secret | No long-lived token to leak; provenance comes with it. Configurations created after 3 Sep 2026 allow only `npm stage publish` unless `npm publish` is chosen, and the workflow runs `npm publish` |
| npm bootstrap | The person publishes a placeholder `@seasb/metafab@0.0.1` by hand from a scratch directory before configuring the trusted publisher, and deprecates it once `1.0.0` is out. `1.0.0` itself is never published by hand | npm offers a trusted publisher only for a package that already exists ([npm trust prerequisites](https://docs.npmjs.com/cli/v12/commands/npm-trust#prerequisites)), so the first publish cannot come from the workflow |
| Node in the release workflow | `>=22.14.0 <23` | Trusted publishing needs Node 22.14.0 or later and npm 11.5.1 or later ([trusted publishing](https://docs.npmjs.com/trusted-publishers)); `22` on its own does not state the floor |
| Release trigger | A pushed tag `v<version>` whose version equals `package.json`'s; the workflow fails before publishing when they differ | A tag can never publish a different version than the one reviewed |
| Version bump | In this pull request: `package.json` and `package-lock.json` go from `0.1.0` to `1.0.0` | The tag is cut from `main` after this merges |

## Design

- `package.json` gains `"repository": { "type": "git", "url": "git+https://github.com/<owner>/meta-harness.git" }` (the real remote, from `git remote get-url origin`) and `"publishConfig": { "access": "public", "provenance": true }`. npm refuses provenance when `repository` does not match the workflow's repository.
- `.github/workflows/release.yml`: on `push` of tags `v*`; Node `>=22.14.0 <23`. A `verify` job with `permissions: { contents: read }` runs `npm ci` and `npm run verify`. A `publish` job that `needs: verify`, with `id-token: write`, runs `npm ci --ignore-scripts`, checks the tag equals `v` + `package.json` version, builds, and runs `npm publish`. The tests stay out of the job with the OIDC token: the first `v1.0.0` run had them in it, and npm signed provenance for the tests' own publishes to their local registry, which rejected them (fixed after #29). A failed step before `npm publish` publishes nothing; a re-run after a successful publish fails on npm's duplicate version and changes nothing.
- `README.md`: install options (`npx`, `pnpm dlx`, `bunx`, a devDependency), the quick-start from the spec with `--setup`, and links to the specs.
