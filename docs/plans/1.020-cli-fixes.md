# Plan 1.020: Discovery stays in the repository, command help, and pre-release CLI fixes

In a fresh repository with no factory, `metafab import` walked out of the repository to `~/.factory/`, a folder that Factory.ai Droid creates, took `$HOME` as the repository root and tried to adopt the home directory's skills. Only the adoption check stopped it from writing. This plan makes factory discovery stop at the Git top level (and look only in the current directory outside Git), makes every command refuse a `.factory/` that belongs to Droid, and gives each command its own `--help`. It also closes four small follow-ups from PRs #17 and #19: readdir walkers that skip every entry on a filesystem that reports no entry types, a second prompt that hangs when piped answers arrive in one chunk, a misleading warning for a symlinked Git hook, and `update` and `import` not printing the hook changes their build made. After it merges, `metafab` never reads or writes a `.factory/` outside the current repository, never touches Droid's folder, and `metafab <command> --help` shows the command's options.

Spec edits this plan makes (the builder makes them in the PR):

In `cli.md`, [Finding the factory](../specs/cli.md#finding-the-factory), the first two paragraphs become:

> Every command except `init` and `import` uses the nearest factory. Inside a Git repository, it looks for `.factory/` in the current directory, then in each parent directory up to the repository's top level, and never above it. In a monorepo, the nearest factory wins. Outside a Git repository, it looks only in the current directory. When no `.factory/` is found, the command stops with exit code 1 and suggests `metafab init`.
>
> The repository is the one Git reports for the current directory, so a linked worktree, a submodule, and a repository inside another repository's directory each stop at their own top level, and `GIT_DIR` and `GIT_WORK_TREE` are honoured. When `git` is not installed or cannot answer, the nearest directory that contains a `.git` entry is the top level. A directory inside a Git directory with no work tree, such as a bare repository, is refused with exit code 1.
>
> `init` and `import` also use the nearest factory when one exists. Otherwise they create `.factory/` at the top level of the current Git repository, or in the current directory outside one.
>
> Factory.ai Droid also keeps its files in a `.factory/` directory, in projects and in the home directory. A `.factory/` that has no `factory.yaml` but has `settings.json` or `droids/` belongs to Droid. When the nearest `.factory/` is Droid's, every command, `init` included, stops with exit code 5 before it fetches or writes anything: `<path> belongs to Factory.ai Droid, not Metafab`. Metafab never adopts, writes or deletes files in it. Droid never writes `factory.yaml`, so a Metafab factory that has `settings.json` or `droids/` but has lost its `factory.yaml` gets back in use when the person adds a valid `.factory/factory.yaml` by hand, with `format: 1` and `name: <name>` (see [factory.yaml](factory-format.md)); `init` cannot do this for them, because it refuses the folder too.

## Design

### Discovery (`src/core/discovery.ts`)

From intake: *Factory discovery walks out of the Git repository, and `.factory/` is another tool's folder*, Sebastian, 12 Nov 2026 (fab-trial feature-build trial). In `~/Dev/fab-trial`, a fresh Git repository with no `.factory/`, `metafab import github:traction-team/meta-harness#main` stopped with exit 5, `adoption-blocked`, listing `~/.claude/skills/.DS_Store`, `~/.claude/skills/orca-cli` and other home-directory entries: `findFactory` (`src/core/discovery.ts`) walks to `/`, found `~/.factory/` (Droid's `settings.json`, `skills/`) and took `$HOME` as the root. `resolveNewFactoryRoot` asks Git for the top level only after that walk fails. The code followed the spec, so the spec changes first (above). The trial's workaround was `mkdir .factory` before `import`; after this plan it is not needed.

New types and functions:

```ts
export interface RepositoryScope {
  /** Directories to search, nearest first: the current directory up to and including the top level. Only the current directory outside Git. */
  searched: string[];
  /** The top level, spelled like the current directory's path; undefined outside Git. */
  topLevel?: string;
  /** How the top level was decided. */
  via: "git" | "dot-git" | "none";
}

export interface DiscoveryOptions {
  /** The command name for fix lines, such as "build" or "pipeline add". */
  command?: string;
  git?: GitRunner;   // runGit by default
}

export async function repositoryScope(cwd: string, git: GitRunner = runGit): Promise<RepositoryScope>;
export async function findFactory(cwd: string, options?: DiscoveryOptions): Promise<FactoryLocation>;
export async function resolveNewFactoryRoot(cwd: string, options?: DiscoveryOptions): Promise<string>;
```

Every command passes its own name (`findFactory(context.cwd, { command: "build" })`, `resolveNewFactoryRoot(context.cwd, { command: "init" })`, and so on, in each `src/commands/*.ts`). Tests that injected a runner as the second argument pass `{ git }` instead.

`repositoryScope`:

1. `start = path.resolve(cwd)`. Run `git rev-parse --show-toplevel` with `cwd: start`.
2. Exit 0 with non-empty output: `gitTop = path.resolve(stdout.trim())` (also turns `C:/x` into `C:\x`). Build the chain `start, parent, …` up to the filesystem root and take it up to the first directory whose identity equals `gitTop`'s, using 1.019's `sameFile(a, b)` (`stat(…, { bigint: true })`, equal `dev` and `ino`; see Decisions). Discovery wraps each call so a `stat` failure (a directory it cannot reach, or Git's path not existing as spelled) counts as no match rather than an error. When none matches (the current directory was reached through a symbolic link from outside the repository), retry with the chain from `await realpath(start)`; then `searched` and `topLevel` use the real spellings from that chain (Decisions, "The root's spelling"). When that does not match either (for example a Cygwin Git printing `/cygdrive/c/...`), use the `.git` fallback (step 5). `via: "git"`.
3. Exit 128 with `/not a git repository/i` in stderr (this includes Git's "Stopping at filesystem boundary" and ceiling cases): outside Git, `searched: [start]`, `via: "none"`.
4. Exit 128 with `/must be run in a work tree/i`: throw `MetafabError("<cwd> is inside a Git directory that has no work tree.", { exitCode: Failed, code: "no-work-tree" })`, problem file `.`, fix `Run metafab from a checkout of the repository`.
5. Spawn failure (Git not installed) or any other failure (for example "detected dubious ownership"): walk up from `start`; the first directory with a `.git` entry (`lstat` succeeds; file or directory, so worktrees and submodules count) is the top level, `via: "dot-git"`. No `.git` entry up to the filesystem root: outside Git, `searched: [start]`, `via: "none"`.

`GIT_DIR` and `GIT_WORK_TREE` reach Git through `runGit`'s `gitEnv`, so Git's answer already honours them: with `GIT_DIR` set and no `GIT_WORK_TREE`, Git calls the current directory the top level, and discovery checks only it. Git hooks written by Plan 1.016 `cd` to the factory directory first, so a hook's `metafab build` finds `.factory/` at its first step either way (checked: Git 2.4x sets no `GIT_DIR` for `post-checkout`). An end-to-end test runs a real `post-checkout` hook for a factory at `packages/app` (see Tests, Hooks).

`findFactory` searches `scope.searched` in order with `isDirectory(<dir>/.factory)` (unchanged: follows a symlinked `.factory`, skips a file). On the first hit it calls `assertNotDroid(factoryDir, cwd, options.command)` and returns `{ root, factoryDir }`. With no hit:

- Inside Git: `No .factory directory found in <cwd> or its parents up to the repository root <topLevel>.`; problem file `normalizeProblemPath(".factory", cwd)`, message `No factory found between <cwd> and the repository root.`, fix `Run metafab init`.
- Outside Git: `No .factory directory found in <cwd>. Outside a Git repository, Metafab looks only in the current directory.`; fix `Run metafab init, or run metafab in the directory that contains .factory/`.
- Exit 1, code `factory-not-found` (unchanged), `details: { cwd, repositoryRoot: topLevel ?? null }`.

`resolveNewFactoryRoot` computes the scope once, runs the same search (so a Droid folder is refused here too), and with no hit returns `scope.topLevel ?? path.resolve(cwd)`. It no longer throws `git-failed` (the fallback in step 5 replaces it); `GIT_FAILED_CODE` and `isNotARepository` go.

`assertNotDroid(factoryDir, cwd, command)`: when `lstat(<factoryDir>/factory.yaml)` fails with `ENOENT` and `lstat` finds `settings.json` or `droids` (any entry type), throw:

```
MetafabError("<display> belongs to Factory.ai Droid, not Metafab.", {
  exitCode: ExitCode.NotOwned, code: "droid-factory",
  details: { factoryDir, markers: ["settings.json", "droids"] /* those found */ },
  problems: [{ level: "error", file: <display>,
    message: "<display> has <markers joined with " and "> and no factory.yaml, so it belongs to Factory.ai Droid",
    fix: "If this is Factory.ai Droid's folder, leave it, or run metafab in a repository without it. If it is a Metafab factory, add <display>/factory.yaml with the lines `format: 1` and `name: <name>`, then run metafab <command> again" }],
})
```

`<name>` is `deriveFactoryName(path.basename(root))` (`src/core/edit/paths.ts`), the name `init` would have written for that directory, so the suggested file passes `rule7FactoryYaml` and the name rules as written. `<command>` is `options.command`; when absent (direct calls in tests), the fix ends `then run metafab again`. The fix never suggests `metafab init`, because `init` refuses the same folder. Adding `factory.yaml` always ends the refusal: the check looks only for that file's absence, and Droid never writes it. Metafab does not create `factory.yaml` itself, so the person decides whose folder it is.

`<display>` is `normalizeProblemPath(factoryDir, cwd)` (for example `.factory` or `../../.factory`; an absolute path when on another Windows drive). A `.factory/` with `factory.yaml` is Metafab's even if it also has `settings.json`. A `.factory/` with neither marker and no `factory.yaml` is a Metafab factory that `init` completes, as today. Because `init` and `import` call `resolveNewFactoryRoot` before anything else (in `initCommand.run` and `importCommand.run`), the refusal happens before any fetch, prompt or write; `build`, `check` and every other command refuse through `findFactory`. The repository is unchanged.

Cases this covers, each with a test:

| Situation | Result |
| --- | --- |
| `init` in `repo/packages/app`, no factory | `.factory/` at `repo/` (unchanged) |
| `build` in `repo/packages/app`, factory at `repo/` | Found |
| Repository at `~/Dev/x`, `~/.factory/` exists (Droid's) | `factory-not-found` for `build`; `init`/`import` create `~/Dev/x/.factory/` |
| `$HOME` is itself a Git repository (dotfiles) and the run is in `$HOME` | `~/.factory/` is the nearest; Droid's → exit 5 |
| Repository nested in another repository's directory, or a submodule | Stops at the inner top level; the outer factory is not used |
| Linked worktree (`.git` file) | Stops at the worktree's top level |
| Outside Git, factory in a parent | Not found; message explains the current-directory rule |
| Git not installed, inside a checkout | `.git` fallback finds the top level |
| Git refuses (dubious ownership) | `.git` fallback |
| Inside `.git/` or a bare repository | exit 1, `no-work-tree` |
| Current directory reached through a symlink | realpath chain; same result as from the real path (skipped on Windows) |

No network is used; Git is spawned with `execFile` (`runGit`). Discovery writes nothing, so a second run and an interrupted run are the same as the first.

### Command help (`src/help.ts`, new; `src/cli.ts`; `src/commands/*.ts`)

From intake: *Command help shows the command list, not the command's options*, Sebastian, 12 Nov 2026 (end-to-end trial of publish, import and update). `metafab publish --help`, `import --help`, `init --help` and `update --help` each print the global list: `GLOBAL_FLAGS` and `splitGlobalFlags` in `src/cli.ts` treat `--help` / `-h` as a global flag, and the `parsed.values.help` branch in `main` prints `helpText`, the global list. So `--dry-run`, `--tag`, `--agents`, `--force`, `--adopt`, `--to` and the source forms were only in the specs.

Human output (columns padded to the longest flag):

Import a fab as the factory upstream

Arguments:

A command with no arguments (`build`, `map`, `check`, `detach`, `publish`, `update`) prints no `Arguments:` heading and no blank line for it: the description is followed directly by `Options:`. Every command has an `Options:` section, because `--json` and `-h, --help` are always listed.

`main` builds the help result as every command does: `summary` (the rendered text) is set only when JSON is off. With JSON on, the result is (the shape the spec edit to [JSON output](../specs/cli.md#json-output) states) `{ ok: true, command: "help", exitCode: 0, problems: [], help: CommandHelp }` with no `summary` key; an option with no placeholder has no `value` key. The global `metafab --help --json` becomes `{ ok: true, command: "help", exitCode: 0, problems: [], commands: [{ command, usage, description }, ...] }` with no `summary` (today it is `{ ok, command, exitCode, summary }`). No existing test asserts the JSON form of the global help (`test/cli/cli.test.ts` and `test/cli/e2e.test.ts` check only text), so the new test in `test/cli/help.test.ts` pins it.

### One line reader per run (`src/input.ts`)

From intake: *A second prompt hangs when answers arrive on one piped stdin chunk*, build-plan task sub-agent, PR #17, 8 Nov 2026. With 1.016, `init` in a terminal can ask two questions (adoption, then Git hooks). A test feeding both answers in one piped chunk hung on the second, so the test passes `--no-git-hooks` instead (`test/core/init/init.test.ts`, "accepting the adoption question moves the skill"). Cause: `question` in `src/input.ts` opens a new `readline` interface per question; the first consumes the buffered input holding the second answer, and closing it drops that. Users at a real terminal are probably not affected, because each answer arrives separately.

Design:

```ts
interface LineReader { next(): Promise<string | undefined>; close(): void }
const readers = new Map<NodeJS.ReadableStream, LineReader>();
function readerFor(stdin: NodeJS.ReadableStream): LineReader;
/** Closes every open reader. `main` calls it in `finally`. */
export function closeInput(): void;
```

- `readerFor` creates one `createInterface({ input: stdin, crlfDelay: Infinity })` per stream (no `output`, so `terminal` stays false as today and Ctrl-C keeps its default: the process ends by signal), queues each `line` event, and resolves waiting `next()` calls in order. It calls `rl.pause()` while no question waits and `rl.resume()` in `next()`, so a child process that later reads standard input (such as an `npm` one-time-password prompt) is not starved. On `close` (end of input) every waiting and later `next()` resolves `undefined`, and the reader is removed from the map.
- `question(text, required, io)` writes `text` with `io.stderr` (as the custom `Writable` did) and awaits `next()`. `undefined` throws `new NeedsInput([required])`: exit 2, nothing written, because every `ask`/`confirm` call (`promptForTargets` in `src/core/init/targets.ts`; the adoption and `git-hooks` questions in `runInit`; the adoption question in `runImport`; `askDescription` in `src/commands/create.ts`) runs before the command's first write; the builder confirms this with the call sites, and the tests below check the repository is unchanged.
- `crlfDelay: Infinity` plus the existing `trim()` makes a CRLF answer (Windows, or a piped file) one answer with no `\r`.
- `main` calls `closeInput()` in a `finally`, so an open reader on `process.stdin` never keeps the process alive.
- Remove the `--no-git-hooks` workaround from that test and feed both answers in one chunk.

### Readdir walkers trust the Dirent type (`src/util/fs.ts` and callers)

From intake: *Tree readers skip every entry when readdir reports an unknown type*, cold review of PR #19, 8 Nov 2026. Plan 1.018 made `restore` classify entries with `lstat`, because some NFS and FUSE mounts report `DT_UNKNOWN` from `readdir`. The readers the merge depends on still trust the `Dirent` type: `snapshotTree` (`src/core/import/file-tree.ts`) and `copyFactoryTree` (`src/core/import/copy.ts`) branch on `isFile()` / `isDirectory()` / `isSymbolicLink()`. On such a mount `snapshotTree` returns no local entries, so `metafab update` plans an add or take-theirs at every path and overwrites local edits while reporting them as additions, and `import` copies nothing. Not reproducible on APFS or ext4.

Add to `src/util/fs.ts`:

```ts
/** A directory entry whose type is always known. */
export interface DirEntry {
  readonly name: string;
  isFile(): boolean;
  isDirectory(): boolean;
  isSymbolicLink(): boolean;
}

/**
 * Lists `directory` with `readdir(directory, { withFileTypes: true })`. An
 * entry the filesystem reported with no type (every Dirent predicate false,
 * DT_UNKNOWN) is typed from `lstat` instead. An entry that vanished before the
 * `lstat` (ENOENT) is dropped. Any other `lstat` error (EACCES, EIO, ...) is
 * thrown unchanged, exactly like an error from `readdir` itself, so the
 * caller's existing handling for an unreadable directory applies: it never
 * silently skips an entry it could not classify.
 */
export async function readdirTyped(directory: string): Promise<DirEntry[]>;
```

What a caller does with that thrown error is what it does today when `readdir` fails, so no new handling is added:

- Callers that catch and report: `walkFactoryFiles` (`check`, and `update`'s `assertResolved`) adds one `cannotReadProblem(<dir>)` (`Cannot read <dir>`, exit 1); `walk` in `src/core/build/skill.ts` and `discoverSkills` add one `Cannot read directory <dir>` problem; `readDirectoryIfExists` and `deselectedSymlinkConflict` in `build/plan.ts` report their permission problem or conflict; `treeProblems`, `hasSkillFile` and `hasChildSkill` keep their documented skip, because another check reports the directory.
- Callers that let it propagate (`snapshotTree`, `snapshotDirectories`, `copyFactoryTree`, `containsFile`, `collectTree`, `listFiles`, `captureDirectory`, `restoreDirectory`): the command fails as it does for an unreadable directory today. `snapshotTree` and `snapshotDirectories` run before `update` and `import` write anything, so the repository is unchanged.

`readdirTyped` returns a narrow interface, not a faked `Dirent`: a real `Dirent` already satisfies `DirEntry` and is returned as it is; an untyped one is replaced by a plain `{ name, isFile, isDirectory, isSymbolicLink }` built from the `Stats` (a FIFO, socket or device answers false to all three, as its Dirent would). No caller in `src/` uses `parentPath`, `path` or the FIFO/socket/device predicates (checked with grep), so callers adapt by:

- replacing `readdir(x, { withFileTypes: true })` with `readdirTyped(x)` (their `try`/`catch` stays, because `readdir` errors are unchanged);
- replacing the explicit types `import("node:fs").Dirent[]` with `DirEntry[]` (in `readDirectoryIfExists` and `deselectedSymlinkConflict` in `src/core/build/plan.ts`, and any `Dirent` annotation the typecheck finds);
- nothing else: sorting by `name` and the three predicates work as before.

Every typed `readdir` in `src/` switches to it:

- `src/core/import/file-tree.ts`: `snapshotTree` and `snapshotDirectories`
- `src/core/import/copy.ts`: `copyFactoryTree`
- `src/core/update/run.ts`: `containsFile`
- `src/core/update/restore.ts`: `captureDirectory` and `restoreDirectory` (they already `lstat` each entry; switched so the guard test has no exceptions)
- `src/core/edit/create.ts`: `hasSkillFile` and `hasChildSkill`
- `src/core/adopt.ts`: `treeProblems`, the destination scan in the adoption planner, and `collectTree`
- `src/core/build/plan.ts`: `readDirectoryIfExists` and `deselectedSymlinkConflict`
- `src/core/build/skill.ts`: `walk`
- `src/core/check/markers.ts`: `walkFactoryFiles`
- `src/core/factory/discovery.ts`: `discoverSkills`
- `src/util/fs.ts`: `listFiles`

The name-only `readdir` calls (in `src/core/update/spelling.ts`, `src/core/publish/stage.ts`, `src/core/sources/path.ts` and `src/core/sources/npm.ts`) do not use types and stay. On a normal filesystem no entry is untyped, so no extra `lstat` runs and output is unchanged.

### Symlinked hook warning (`src/core/hooks/sync.ts`)

- Running `metafab import <fab>` in a fresh Git repository under a home directory that has Droid's `~/.factory/` creates `.factory/` in the repository
- `metafab <command> --help` prints that command's usage for every command

## Open questions

1. Should Droid detection look for more of Droid's files (`mcp.json`, `commands/`, `hooks/`)? Proposal: no. `settings.json` and `droids/` were agreed; `commands/` or `hooks/` could be a Metafab skill group in a factory that has no `factory.yaml` yet, so adding them could refuse a real factory.
2. When a Droid `.factory/` is nearer than a Metafab factory higher in the same repository (a package that uses Droid inside a Metafab monorepo), should read-only commands skip it and keep looking? Proposal: no, refuse as agreed; the person runs `metafab` from the factory's directory. Revisit if a real repository needs both.
