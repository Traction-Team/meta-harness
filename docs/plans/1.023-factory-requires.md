# Plan 1.023: A factory declares the repository files it needs

A fab carries `.factory/` and nothing else, but its workflows often need files elsewhere in the repository: an `opencode.json` that defines the sub-agents the workflows start, an `orca.yaml` setup step, a settings file the scripts read. Today an importing team finds out only when a workflow fails. After this plan, `factory.yaml` can list those files under `requires`, each with a description and an optional template in `.factory/templates/`. `import` shows them in its review summary and, with consent, creates the missing ones from their templates; it never overwrites, never writes through a link, and never creates a case variant of an existing path. `update` reports a requirement that is new upstream and offers to create it the same way. `check` warns about each required file that is missing. `build` does nothing with them. Scripts never run on import. The first fab (Plan 1.024) depends on this.

From intake: *a fab's workflows need repository files the fab cannot carry*, Sebastian, fab-trial feature-build trial, 12 Nov 2026. The meta-harness factory imported into `sebastiankade/fab-trial` cleanly, but the trial had to add or edit by hand:

- `opencode.json` at the root: every workflow dispatches `subagent_type: "agent-coding"`, which only this repository's `opencode.json` defines. A fab carries `.factory/` only, so an importing repository gets workflows that call a sub-agent it does not have, with no warning.
- `orca.yaml`: the `scripts.setup` step that runs `metafab build` in new worktrees. (`init` suggests it only when `orca.yaml` already exists.)
- `.factory/AGENTS.md`: a full rewrite, because it describes Metafab itself.
- `.factory/workflows/start-plan/SKILL.md`: the hard-coded Orca repo id, `name:MetaFab` and `../meta-harness-<branch>`.
- The docs layout the scripts and workflows assume: `docs/specs/`, `docs/roadmap.md` with `updated`, `docs/plans/`, `docs/intake/`, `docs/changelog/`.

The two local edits showed in `metafab diff` as expected. The note bears on the first fab: a general fab needs these as parameters or documented setup, not as text edits that then show in every `metafab diff` and risk every `update`. This plan answers the "carry it, declare it, or leave it to the README" question with *declare it* (`opencode.json`, `orca.yaml`, the docs layout). The `.factory/AGENTS.md` rewrite and the hard-coded values in `start-plan` are answered by Plan 1.024's settings file (`docs/factory.md`), which a requirement creates; and repository-specific standing instructions go in the root `AGENTS.md` outside the generated block, which `build` already preserves.

> ### Creating required files
>
> A fab's `factory.yaml` can list repository files its workflows need under [`requires`](factory-format.md#required-repository-files). During the preflight, `import` looks at each one in the repository:
>
> - **Present.** A file or a link (even a dangling one) exists at the path, or any other entry that is not a directory, such as a socket. Metafab never changes it.
> - **Blocked.** The path cannot be created without changing other content: a directory is at the path, a parent is a file or a symbolic link, or the path or a parent differs only in letter case from an existing entry. >

## Decisions

Agreed with the person on 2026-11-12 (shared brief decisions 5, 6, 7):

| Topic | Choice | Reason |
| --- | --- | --- |
| Where the need is declared | `requires:` in `factory.yaml`: `path`, `description`, optional `template` inside `.factory/` | One place a fab author, `import`, `update` and `check` all read |
| What import does | Shows every requirement in the review summary and, with consent, creates the missing ones; never overwrites | The trial's hand setup becomes one reviewed step |
| Scripts | None run on import in v1; creation is a byte copy of a template | Running fab code on import is the riskiest thing a fab could do; deferred |
| Per-repository values | Not a Metafab feature. A fab ships a template for a repository-owned settings file (Plan 1.024: `docs/factory.md`), created by `requires`; the fab never ships the file, so `update` never conflicts on it | Keeps Metafab a copier; no template variables |
| What check reports | Missing or blocked required file is a **warning** | It does not make the factory invalid, and a repository can choose not to create a file |

Proposed in this plan, for approval:

| Topic | Choice | Reason |
| --- | --- | --- |
| Template location | Must be under `.factory/templates/`, not `SKILL.md`, not inside a skill directory (rule 13) | Templates are never installed (format), and `templates/<x>/SKILL.md` would make `<x>` a skill |
| Template path spelling | Repository-relative, `.factory/templates/...` | Workflow guidance 4 already asks for repository-relative paths; easy to grep |
| Files only | A requirement is a file: a path ending in `/` breaks rule 12, and an existing directory at the path is reported blocked, never present | Git does not track empty directories; scripts treat a missing directory as empty |
| Forbidden targets | `.factory`, `.claude/skills`, `.agents/skills`, root `AGENTS.md`, `CLAUDE.md`, `.gitignore`, `.gitattributes`, and any path below one of them (any case) | Those are the fab itself or files `build`, `init` and `import` write; a requirement there would fight them |
| Consent without a terminal | Exit 2 naming `--setup`, before any write; `--no-setup` declines | Same rule as adoption consent at import (cli.md rule 6); a JSON caller decides once and re-runs |
| Default answer in a terminal | Yes | The step only adds files that do not exist; nothing is replaced |
| Present means a non-directory at the path | A file, link (even dangling) or other entry that is not a directory counts as present and is never touched; a directory counts as blocked | Never write through or beside something a person put there |
| Case variants | A path or parent that differs only in case from an existing entry is blocked on every filesystem | Same behaviour everywhere, as `import` already does for `.factory/` |
| A creation failure after the copy | A warning per file, import continues, exit 0 | The factory is already copied and recorded; failing then would leave the same tree with a worse message. `check` keeps reporting it |
| Update | Offers only requirements that are new in the merged `factory.yaml`, asking before the first write (versioned and unversioned alike); a dry run never asks or writes; notes a changed template of a present file | A person already decided about the old ones; their files are theirs |
| Build | Does nothing with `requires` | `build` must stay fast and repeatable and must not create files outside its owned output |
| Format version | Stays 1; `requires` is added before 1.0.0 ships | No released CLI rejects it |

## Design

### Types (`src/core/factory/types.ts`)

```ts
export interface Requirement {
  /** Repository-relative, `/`-separated. */
  path: string;
  description: string;
  /** Repository-relative, starts with `.factory/templates/`. */
  template?: string;
  /** Line of the entry in `factory.yaml`. */
  line: number;
}
```

`FactoryYaml` gains `requires: Requirement[]`: empty when the key is absent, when its value is null (`requires:` with nothing after it), and when it is `[]`. All three mean no requirements and give no problem. `FactoryYamlParseResult` gains `requires?: Requirement[]`, filled even when `yaml` is undefined, as `pipeline` is.

Paths inside `.factory/` that Metafab's trees and skills use (`Skill.relDir`, `FileTree` keys, `plan.conflicts`, `plan.sideFiles`, `changes.updated`) are relative to `.factory/`, while `template` is repository-relative. Every comparison between them uses `factoryRelative(template) = template.slice(".factory/".length)`, a helper in `src/core/requires/paths.ts`; rule 13 guarantees the prefix.

### Parsing and rule 12 (`src/core/factory/factory-yaml.ts`, `validate.ts`)

- `KNOWN_FACTORY_FIELDS` gains `"requires"`, so the unknown-field fix lists it.
- New `parseRequirement(itemNode, parsed, file, problems): Requirement | undefined`, shaped like `parsePipelineEntry`. Messages (all `level: "error"`, the entry's or key's line):
  - not a mapping: `requires entry must be a mapping`, fix `Use - path: <file>\n  description: <text>` (the second key indented two spaces, under `path`)
  - unknown key: `Unknown key "<key>" in a requires entry`, fix `didYouMean(key, ["path", "description", "template"])` or `Remove the key or use path, description or template`
  - missing `path` / `description`: `requires entry is missing "path"` (or `"description"`), fix `Add a path: <file> key` / `Add a one-line description`
  - wrong type, empty or multi-line: `"<key>" in a requires entry must be a non-empty, single-line string`, fix `Write the <key> on one line`
  - `requires` not a list: `"requires" must be a list`, fix `Write each required file as a - path: entry`
- Rule 12 in `validate.ts`: `rule12RequirementPath(file, requirement): Problem[]` uses `requirementPathProblem(path)` from `src/core/requires/paths.ts`, which returns the first broken rule as a phrase. The message is `Required path "<path>" <phrase>`, for example `Required path "../x" leaves the repository`, `... is inside .factory/`, `... is a file Metafab writes`, `... uses a Windows device name`, `... is read by Git as .git`; fix `Use a repository-relative file path outside .factory/, such as docs/factory.md`. `rule12UniqueRequirements(file, requirements)`: `Required path "<b>" repeats "<a>"` (equal ignoring case) or `Required path "<b>" is inside required path "<a>"`, fix `Remove one of the entries`.
- `isDotGitName` moves from `src/core/publish/stage.ts` to `src/util/git-names.ts` unchanged; `stage.ts` imports it. The publish tests pin that nothing else changes.

### Rule 13 (`src/core/factory/requires.ts`, new; called from `load.ts`)

`export async function requirementTemplateProblems(factory: Factory, requires: Requirement[], file: string): Promise<Problem[]>`. For each entry with a `template`:

- not starting with `.factory/templates/`, or the rest failing `requirementPathProblem`: `Template "<t>" must be a file in .factory/templates/`, fix `Move the template into .factory/templates/ and update the path`
- base name `SKILL.md` in any case, or any directory from `.factory/templates/` down to the template's own directory (each prefix of `factoryRelative(template)`'s directory, starting at `templates`) holds an entry whose name, lowercased, is `skill.md`: `Template "<t>" is part of a skill, so it would be installed`, fix `Move it out of the skill directory`. The check reads those directories itself with `readdirTyped` rather than using `factory.skills`, so it matches the spec exactly: it is case-insensitive (a `Skill.md` that discovery would skip on a case-sensitive filesystem still counts) and it checks directories whose name starts with `.`, which discovery ignores. A directory it cannot read gives the existing `Cannot read directory <d>` problem
- `lstat` absent: `Template "<t>" does not exist`, fix `Add the file or correct the path`
- not a regular file after resolving a link with `realpath`, or a link resolving outside `.factory/`: `Template "<t>" is not a regular file inside .factory/`, fix `Replace it with a file`
- a read error other than absent: the existing `Cannot read file <t>` wording.

`loadFactory` calls it after `parseFactoryYaml` and `discoverSkills`, so `check`, `build`, `publish`'s staged validation and `validateFab` all get rules 12 and 13 for free. A fab that breaks them is rejected by `import` with exit 4 (existing `invalidFab`). A `publish.exclude` that removes a template fails the staged validation with exit 4 and the rule 13 message (existing "broke a reference" step).

### Inspection (`src/core/requires/inspect.ts`, new)

```ts
export type RequirementState = "present" | "missing" | "blocked" | "created" | "declined" | "failed";
export interface RequirementResult {
  path: string;
  description: string;
  template?: string;
  state: RequirementState;
  /** Why it is blocked or failed, as a phrase for the summary. */
  reason?: string;
  /**
   * For `blocked`: the repository-relative path of the existing entry in the
   * way (the directory at the path, the file or link parent, or the case
   * variant). `check`'s fix line names it.
   */
  clash?: string;
}
export async function inspectRequirement(root: string, requirement: Requirement): Promise<RequirementResult>;
```

It walks the path's segments from `root`. For each parent segment it reads the parent directory once with `readdirTyped` from `src/util/fs.ts` (Plan 1.020's helper, which falls back to `lstat` for `DT_UNKNOWN`; its test that fails on a new raw `readdir(..., { withFileTypes: true })` covers this module too) and folds names with the same `toLowerCase` folding `conflicts.ts` uses:

- an exact-name entry that is a directory: continue; a symbolic link or a file: `blocked`, reason `<parent> is a symbolic link` / `<parent> is a file`, `clash` the parent; anything else (a socket, a FIFO, a block or character device): `blocked`, reason `<parent> is not a directory`, `clash` the parent
- no exact name but a folded match: `blocked`, reason `<existing> differs only in letter case`, `clash` the existing entry
- no entry: the rest is `missing`

For the last segment: exact entry that is a directory → `blocked`, reason `<path> is a directory`, `clash` the path; any other exact entry, including a dangling link, a socket or a FIFO → `present`; a folded match → `blocked` with `clash` set; nothing → `missing`. Nothing follows a link. An unreadable parent (`EACCES`) → `blocked`, reason `Cannot read <parent>`, `clash` the parent.

### Consent and creation (`src/core/requires/setup.ts`, new)

```ts
export const SETUP_QUESTION = "Create the missing files from the fab's templates? Existing files are never changed.";
export function setupRequired(results: RequirementResult[]): RequiredValue; // name "setup", flag "--setup"
export async function decideSetup(results: RequirementResult[], choice: boolean | undefined, io: InputIO, tty: boolean): Promise<boolean | "needs-input">;
export async function createRequirements(root: string, results: RequirementResult[]): Promise<RequirementResult[]>;
export function describeRequirementList(results: RequirementResult[]): string; // the list printed before the question
```

`describeRequirementList` returns the creatable entries only (state `missing` with a `template`), in the order given, which is `factory.yaml` order: a first line `The factory needs these files, which are missing:`, then one line per entry, `  <path>  <description>` (two spaces before the path, the path padded to the longest creatable path plus two spaces), each ending in `\n`. Present, blocked and template-less entries are not listed; the review summary shows them after the import. `decideSetup` writes the string to stderr (`io.stderr`), never to stdout, so `--json` output stays one JSON object.

- `creatable(results)` = `missing` entries with a `template`. When empty, `decideSetup` returns `false` without asking and nothing is required.
- `decideSetup`: a `choice` from the flags wins; else a terminal prints `describeRequirementList` to stderr, then `confirm({ name: "setup", flag: "--setup", description: SETUP_QUESTION }, { default: true }, io)`; else `"needs-input"`. The caller collects it with the adoption value and throws one `NeedsInput` listing both. The `description` of the required value is `Create the missing repository files the factory needs: <paths>. Pass --setup to create them or --no-setup to skip`.
- `createRequirements` re-inspects each creatable entry (the state may have changed since the preflight), then `mkdir(parent, { recursive: true })` and `writeFile(target, bytes, { flag: "wx", mode })`, `bytes` read from `<root>/<template>` with `readFile` (no encoding, so CRLF, a BOM or binary content are copied exactly). At import those are the fab's committed bytes: a Git fetch takes committed blob bytes with no conversion (sharing.md, Supported sources), npm and tarball sources are unpacked as published, and `copyFactoryTree` writes them into `.factory/` unchanged, so no checkout rule has touched them when the template is read. At update they are the merged `.factory/` copy, which for a template new upstream is upstream's committed bytes; `mode` 0o755 when `stat(template).mode & 0o111` else 0o644, then `chmod` (a no-op on Windows). `EEXIST` → `present`. Any other error → `failed` with `reason` the error code, and a warning `Problem` `{ file: <path>, message: "Could not create <path>: <code>", fix: "Copy <template> to <path>" }`. It returns the updated results; it never throws for a single file.
- Not created because declined: state `declined`.

### Check (`src/core/requires/check.ts`, new; called from `src/core/check/index.ts`)

`export async function requirementWarnings(factory: Factory): Promise<Problem[]>`: for each requirement, `inspectRequirement(factory.root, requirement)`:

### Edge cases

- **Windows.** Paths are POSIX in `factory.yaml` and joined with `path.join` on disk. `\`, `:`, device names and trailing dots or spaces are refused by rule 12, so a fab cannot name a path Windows cannot create. `chmod` is a no-op. Case folding gives the same result on NTFS, APFS and ext4.
- **CRLF.** Templates are copied as bytes. At import they are the fab's committed bytes, so a fab that commits an LF template creates an LF file on every platform. Later, when a person clones the repository, `.factory/** text=auto eol=lf` keeps the checked-out template LF too. Git applies the repository's own rules to the created file when it is added.
- **No terminal / `--json`.** Exit 2 with `required` naming `--setup` only when something could be created; otherwise no question and no exit 2. `--json` in a terminal still asks, as adoption does today.
- **Second run.** `import` refuses (upstream exists). `update` offers only new requirements, so a second update offers nothing. `check` keeps warning until the file exists.
- **Interrupted run.** Files are created one by one after the factory copy. An interrupted import leaves some created; the rest are `check` warnings with the copy fix line. `git status` shows every created file.
- **No Git.** Nothing here uses Git.
- **No network.** Nothing here fetches; a fab that cannot be fetched fails earlier with exit 3, unchanged.
- **Symbolic links.** A link at the path is present and never followed; a linked parent blocks; a template link inside `.factory/` is read through, as `build` does.
- **Paths escaping the repository.** Refused by rule 12 (`..`, absolute, drive letters via `:`). Inspection never follows a link, so a linked parent cannot redirect a write.
- **Factory without `factory.yaml`.** No requirements; nothing changes.
