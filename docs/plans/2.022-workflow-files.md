# Plan 2.022: A workflow can be a plain Markdown file that agents read from `.factory/`

Today a workflow is a skill and nothing else: only a directory with `SKILL.md` below `.factory/workflows/` is a workflow, and every workflow is installed into each harness's skill directory. The person does not want workflows in the harness's skill list. They want agents to learn about workflows from `AGENTS.md` and read them in place. This plan adds two forms that are never installed, `workflows/<name>.md` and `workflows/<name>/workflow.md`, behind `format: 3`. A `SKILL.md` anywhere, including below `workflows/`, is still installed as a skill. [Plan 2.023](2.023-agents-md-workflows.md) writes the table in root `AGENTS.md` that tells agents where each workflow is.

## Specs

- [Factory format](../specs/factory-format.md): Core rule, Directory layout, Workflows, `factory.yaml`, Pipeline rules, Validation, Reserved names
- [Environments: Where directives apply](../specs/environments.md#where-directives-apply)
- [Sharing](../specs/sharing.md): format detection, unknown formats

This plan changes all four; see Design.

## Decisions

Agreed with the person on 2026-11-28:

| Topic | Choice | Reason |
| --- | --- | --- |
| What installs as a skill | Every `SKILL.md`, as today, wherever it is. Workflow files are never installed | "Anytime you use a SKILL.md file it should be imported as a skill." A team that wants its workflows as skills keeps `SKILL.md` |
| Workflow forms | `workflows/<name>.md`, `workflows/<name>/workflow.md` (room for supporting files), and `workflows/<name>/SKILL.md` as today | The person's two forms, plus the existing one |
| Where agents read a workflow file | The source in `.factory/`, unrendered. Nothing is generated, gitignored or drift-checked for it | The person: "leave them in `.factory` and have the agents read them from there". Plan 2.023's `AGENTS.md` section says how to read the import and switch directives in place. A team that wants rendered text uses `SKILL.md` |
| Frontmatter | `description` is required, one line. There is no `name`: the name is the file or folder name. Any other field is kept and ignored | The person: "no name field, description". `name` is ignored, not rejected, so a renamed `SKILL.md` keeps working |
| Dependencies between workflows | None in frontmatter | The person: the pipeline in `factory.yaml` already gives the order |
| `workflow.md` and `SKILL.md` in one folder | Allowed: the folder is one workflow, `workflow.md` is the file agents read, and `SKILL.md` installs as a skill of the same name. The installed skill copies `workflow.md` as a supporting file, rendered like every `.md` in a skill folder | The person: "we shouldn't be overly strict for no reason". Leaving the build's copy rule alone keeps one rule: a skill folder installs whole |
| `<name>.md` beside a `<name>/` folder that holds `workflow.md` or `SKILL.md` | Error: two workflows named `<name>` | The person agreed |
| Where workflow files count | Only directly in `workflows/`: `workflows/<name>.md` and `workflows/<name>/workflow.md`. Deeper `.md` files are supporting files | The person agreed |
| Names | Workflow files follow the skill name rules (rule 5) and rule 10, and every workflow and skill name is unique across the factory | The person agreed. A workflow that is also a skill is one name, not two |
| Format | Workflow files need `format: 3`. In format 1 and 2 they are ordinary files and `check` warns once per file | Metafab 2.0 then says "Unknown factory format 3 ... upgrade @seasb/metafab" instead of "Pipeline names unknown workflow", which is what fab-basic hit |
| Conditional `skills:` entries | Unchanged: they name skills. A workflow file is not a skill, so naming one is the existing unknown-skill error | A workflow file that differs by environment uses `when` and `switch` inside it |
| `create workflows/<name>` | Format 3 writes `workflows/<name>.md`; `--skill` writes `workflows/<name>/SKILL.md`. Format 1 and 2 write `SKILL.md` as today | The person agreed |

## Design

**Format 3.** `FACTORY_FORMATS` becomes `[1, 2, 3]` and `FORMAT_FEATURES` gains `workflowFiles: 3`. Format 3 has every format 2 feature. The rule 7 fix becomes `Set format: 3 to use workflow files, or format: 2 for env and skills, or format: 1`. `formatListText()` now prints `1, 2 or 3`, so the unknown-format fixes for fabs say `Use format 1, 2 or 3, or upgrade @seasb/metafab`.

**Model.** In `factory/types.ts`:

```ts
export interface Workflow {
  name: string;
  /** Repository-relative path of the file an agent reads, such as `.factory/workflows/build-plan.md`. */
  file: string;
  description?: string;
  /** The skill installed for this workflow, when its folder holds SKILL.md. */
  skill?: Skill;
  /** Line of `description` in `file`, for problems. */
  descriptionLine?: number;
}
```

`Factory.workflows: Workflow[]`, sorted by name, holds every workflow: each workflow file, and each skill with `isWorkflow`. A skill workflow's `file` is its `SKILL.md`, unless its folder also holds `workflow.md`, which is then the `file` and gives the `description`. `workflows(factory)` in `load.ts` returns `factory.workflows`. `Skill.isWorkflow` keeps its meaning: a skill below `workflows/`.

**Discovery** (`discoverSkills` gains a `workflows` result, filled only when `supportsFeature(format, "workflowFiles")`). In `.factory/workflows/`:

1. Each regular file directly in it whose name ends in `.md` (lowercase, so `README.MD` does not count) is the workflow named by the file name without `.md`.
2. Each directory directly in it that holds a regular file `workflow.md` is the workflow named by the directory.
3. Names starting with `.` are skipped, as everywhere in `.factory/`.
4. A workflow file's frontmatter follows the skill frontmatter grammar (`parseFrontmatter`). A file with no frontmatter is a workflow with no description, which rule 1 reports.
5. Other files in a `workflow.md` folder, and its subdirectories, are supporting files. A `SKILL.md` in a subdirectory of it is a skill, discovered as today.
6. Discovery of `SKILL.md` does not change.

When the factory's format is 1 or 2, discovery records each path that rules 1 or 2 would have matched, and the loader adds one warning per path: `<path> is a workflow file, which needs format: 3`, fix `Set format: 3 in .factory/factory.yaml, or rename it to <dir>/SKILL.md`. It is not a workflow, so a pipeline that names it gets the existing unknown-workflow error.

**Validation** (`validate.ts`), with the existing rule numbers:

- Rule 1: a workflow file has `description`, a non-empty single-line string. The problem names the file and the frontmatter line, or line 1.
- Rule 4: names are unique across skills and workflows. `workflows/x.md` beside `workflows/x/workflow.md` or `workflows/x/SKILL.md` is an error on both paths: `Two workflows are named "x"`, fix `Keep one of them`. A workflow file named like a skill elsewhere, such as `workflows/review.md` and `skills/review/SKILL.md`, is the existing duplicate-name error. A folder with both `workflow.md` and `SKILL.md` is one workflow, never a duplicate.
- Rules 5 and 10: a workflow file's name follows the name rules and does not start with `metafab`. The fix for a bad name says `Rename it to a workflow name, or move it out of .factory/workflows/`, which covers a `workflows/README.md`.
- Rule 8: pipeline entries name an entry of `Factory.workflows`. `rule8PipelineWorkflows` takes workflows, not skills.

**Directives.** In format 3, directives and imports in a workflow file, and in the `.md` files beside `workflow.md`, are validated as in skills (`env/validate.ts`): conditions, switches, import paths relative to the file, loops. `build` never copies or renders a workflow file outside a skill folder. A `workflow.md` inside a folder that also holds `SKILL.md` is part of that skill, so `compileSkill` copies and renders it as it does every file there; the compiler does not change. The environments spec's table gains the row: workflow files, all directives, validated by `check` and read in place.

**Build.** `build` installs nothing new and removes nothing new: workflow files are not skills. A workflow that changes from `x/SKILL.md` to `x.md` loses its installed skill on the next build through the existing removal of owned directories with no source.

**Commands.**

- `create`: in format 3, a path of exactly `workflows/<name>` writes `.factory/workflows/<name>.md` with `description` frontmatter and a `# <name>` heading, unless `--skill` is given, which writes `workflows/<name>/SKILL.md` as today. Any other path, and any path in format 1 or 2, behaves as today; `--skill` there changes nothing. When any form of `<name>` exists, it fails with the existing already-exists error, naming the existing file.
- `init --adopt`: `AdoptionFactory` in `adopt.ts` becomes `Pick<Factory, "skills" | "workflows">`, and the name preflight refuses a candidate skill whose name is any workflow's name, such as an unowned `.claude/skills/x/` when `.factory/workflows/x.md` exists. It refuses before any move, with exit 5 and the existing name-clash problem, so both the installed directory and `.factory/` are unchanged.
- `pipeline add`: `requireWorkflow` checks `Factory.workflows`. The not-found fix names `.factory/workflows/<name>.md` in format 3, and `<name>/SKILL.md` before.
- `map`: standalone workflows come from `Factory.workflows`.
- `publish`: `excludedWorkflowProblems` checks the workflow's `file` (and its folder, for `workflow.md`). `readme.ts` lists `Factory.workflows` with their descriptions, and skills that are not workflows under Skills.
- `import` and `update` review summary (`summary.ts`): a workflow is new when `workflows/x.md` or `workflows/x/workflow.md` appears, as well as `workflows/x/SKILL.md`. Its title is the file's first `# ` heading. Merging is by file, so it needs no change.
- Fab sources: `metafab.format: 3` in a fab's `package.json` and `format: 3` in its `factory.yaml` are accepted through `isFactoryFormat`.

**Built-in `metafab` skill.** "Find and edit factory source files" lists the three forms and says only `SKILL.md` installs. "Create workflows and skills" gives `create workflows/<name>` and `--skill`. One line says workflow files need `format: 3` and Metafab 2.1.

**Failure.** Every problem above goes through `check` with file, line and fix, exit 1, and `build` refuses as it does for any factory error. A read error on a workflow file is `Cannot read file <path>`, as for `SKILL.md`. No command leaves the repository half-changed: `create` keeps its existing checks before writing.

**Second run.** `build` on an unchanged format 3 factory reports `Up to date.`

**Windows and case.** Names are compared as written; `Build.md` is the name `Build`, which rule 5 refuses. On a case-insensitive file system `x.md` and `X.md` cannot both exist. Paths in problems use `/`. CRLF frontmatter parses as today.

**Specs.** `factory-format.md`: the core rule says a workflow is a `SKILL.md` below `workflows/` or one of the two workflow-file forms; the layout lists them; Workflows explains the forms, the frontmatter and that only `SKILL.md` installs; Workflow guidance rule 1 says the description says when to use it, for the `AGENTS.md` table and for skill discovery; format 3 in the intro, `format` row and rule 7; pipeline rule 3 says standalone workflows are listed, not installed, unless they are skills. Format 3 inherits everything format 2 has, so every place a spec limits a feature to format 2 says "format 2 and later" or "`format: 2` or `3`": in `factory-format.md`, the format intro, the `format` row, the YAML grammar's accepted values (`format` is the integer `1`, `2` or `3`), rule 7, rule 14 and the `env`/`skills` rows; in `environments.md`, the "Format 2 factories only" header and rules that name format 2; in `automations.md`, its header and rule 1; in `building.md`, Compiled skills step 3, the conditional-skill rule and Root `AGENTS.md` rule 8. Run `rg -n 'format: ?2|format 2' docs/specs` and settle each hit. `sharing.md`: Metafab 2.1 knows formats 1 to 3; format 3 needs 2.1. `cli.md`: Installation (format 3 needs 2.1; 2.0 refuses it with exit 4 at `import` and exit 1 at `check`), and `create --skill`.

## Tests

All in temporary directories, extending the existing test files:

- **Discovery and validation** (`test/core/factory`): a format 3 fixture with `a.md`, `b/workflow.md` plus `b/notes.md`, `c/SKILL.md`, `d/workflow.md` plus `d/SKILL.md`, and a pipeline naming `a`, `b`, `c` and `d` checks clean. `Factory.workflows` gives `a` → `.factory/workflows/a.md`, `d` → `d/workflow.md` with its skill set, and `b/notes.md` is not a workflow. Errors with file and line: a missing description, a two-line description, `README.md` (name rule), `metafab-x.md` (rule 10), `e.md` beside `e/workflow.md`, `f.md` beside `skills/f/SKILL.md`. A wrong implementation that treats `b/notes.md` as a workflow, or reports `d` as a duplicate, fails.
- **Format gate**: the same files in a format 2 factory warn once each, and a pipeline naming `a` is an unknown-workflow error.
- **Build** (`test/core/build`): after `build`, `.claude/skills/` holds `c` and `d` and not `a` or `b`; the installed `d/` holds `SKILL.md` and `workflow.md`, rendered for the selection; nothing under any skill destination comes from `a.md` or `b/`. Renaming `c/SKILL.md` to `c.md` and building again removes the installed `c`.
- **Format 3 keeps format 2 features** (`test/core/automations`, `test/core/build`): a format 3 fixture with one automation and a `skills:` condition `{ when: env.harness == amp }` on a skill. `automations list` shows the automation and `automations prompt` prints its body; `build --env harness=amp` installs the skill and `build --env harness=claude` removes it. A leftover `format === 2` check fails this.
- **Consumers of `Factory.workflows`**: `pipeline add a` and `pipeline add b` succeed on the format 3 fixture (`test/core/edit`); `map` lists a standalone `h.md` under standalone workflows; the generated fab README lists `a` and `b` with their descriptions under Workflows and not under Skills (`test/core/publish`); `publish` refuses with `Pipeline names excluded workflow` when `publish.exclude` covers `workflows/a.md`, and again when it covers `workflows/b/**`.
- **Directives** (`test/core/env`): `a.md` imports `../partials/p.md` and `b/workflow.md` imports `../../partials/p.md`, and both check clean, so imports resolve from the file that holds them; swapping the two paths makes both errors. A broken import in `a.md`, a `switch` on an unknown variable in `b/workflow.md`, and an unclosed `when` in the supporting file `b/notes.md` are each an error with that file's path and the directive's line, in format 3.
- **Adoption** (`test/core/adopt`): in a format 3 factory with `.factory/workflows/x.md`, `init --adopt` with an unowned `.claude/skills/x/SKILL.md` exits 5, and both `.claude/skills/x/` and `.factory/` are byte for byte unchanged.
- **Create** (`test/core/edit`): format 3 `create workflows/g` writes `g.md` with the description; `--skill` writes `g/SKILL.md`; format 2 writes `SKILL.md` with or without `--skill`; an existing `g.md` blocks `create workflows/g --skill`.
- **Sharing** (`test/core/sources`, `test/core/import`): a format 3 Git fab and an npm fab with `metafab.format: 3` import; the review summary lists `workflows/a.md` as a new workflow with its heading; a format 4 fab is refused with `Use format 1, 2 or 3, or upgrade @seasb/metafab`.
